## 一、产品定义

### 一句话定义

臻海艺术运营后台是一个**内部使用的四角色分级工作台**，让平台运营、财务客服、数据观察者、内容版权审核四类岗位，在不污染 C 端展示数据的前提下，各自看到并操作自己职责范围内的藏品、市场、用户与看板数据。

### 目标用户

内部员工，共四类角色（非C 端用户）。四类角色的职责、每日高频操作、最怕什么都见第五章用户画像。

### 核心问题

**源站 `h5.shengtai.cyou` 是纯 C 端 H5，96 个 JS 分包中没有任何 admin 分包，84 条 API 路径全部是用户侧（item / nft / order / user / wallet）。后台管理在源站不存在，接口契约无对照物。**

这意味着三件事：

1. **没有可复刻的原型**。运营现在要改一个藏品的价格或下一个挂单，只能直接改数据库，改完没人知道谁改的、什么时候改的。
2. **没有权限边界**。四类岗位如果共用一个数据库账号，那么"数据观察者"这个角色的存在就没有意义——他能看到的和能改的都一样。
3. **没有写操作留痕**。当前所有 C 端数据都是源站同步的镜像，运营的任何写操作如果直接落库，就会污染 C 端展示数据，且不可回滚、不可追溯。

### 核心定位（我们解决什么）

提供一个**带 RBAC 分级、写操作可标记、可审计**的内部管理入口，让运营能在本地库上做调整，同时保证：
- C 端展示数据不被后台写操作污染（写操作带 `is_local_override` 标记）
- 每一笔写操作都有操作人、时间、前后值的记录
- 越权访问在服务端被拦截，而非仅在前端隐藏按钮

### 2.2 关键核实结论一：作者信息存在哪张表

需求文档提出「`item_authors` 是 0 行但 `item_copyrights` 有 6 行——做版权审核时要去核实作者信息实际存在哪张表」。**我已核实，结论如下：**

**作者信息就在 `item_authors` 表，该表不空，有 2 行：**

| id | name | works_count | follower_count |
|---|---|---|---|
| 2103038557930151938 | 臻海艺术 | 3 | 0 |
| 2109922931380424706 | 闹翻天 | 2 | 0 |

`items.author_id` 外键关联完整：**5 个藏品全部能关联到作者，孤儿记录 0 条**。作者与藏品的对应关系为：

| 藏品 | author_id | 作者 |
|---|---|---|
| 臻海蓝卡 | 2103038557930151938 | 臻海艺术 |
| 八仙过海·韩湘子 | 2109922931380424706 | 闹翻天 |
| 八仙过海·蓝采和 | 2109922931380421702 | 闹翻天 |
| 张果老·纸驴云符 | 2109922931380421702 | 闹翻天 |
| 八仙过海·张果老 | 2109922931380421702 | 闹翻天 |

**这对产品设计有三个直接影响：**

1. **版权审核模块可以做实，不需要降级为"空态引导"。** 我原本预判版权审核会因作者表为空而成为空壳页，实测证明不成立。
2. **但 `item_copyrights` 表与 `items` 表没有外键关联。** `item_copyrights` 的关联字段是 `name`（版权名称），实测 6 条版权中 **4 条在 items 表中找不到同名藏品**（孤儿记录）。仅「臻海蓝卡」「八仙过海·韩湘子」「八仙过海·蓝彩和」三条能对上，还有 1 条名为「第1个版权」、2 条名为「1」（脏数据）。
3. **所以版权审核模块的核心设计难点不是"没有数据"，而是"关联关系脆弱"。** 审核员看到的是 6 条版权条目，但其中一半对不上任何藏品，且无法从版权条目反向跳转到藏品。这必须在 PRD 里明确定位为「待治理」，而不是假装关联完善。

### 2.3 关键核实结论二：实名审核的真实存量

`users` 表 36 行，实测分布：

| status | has_real_name | 数量 |
|---|---|---|
| normal | 0（未实名） | **35** |
| normal | 1（已实名） | **1** |

**这是本PRD 最严重的数据现状问题：36 个用户里只有 1 个已实名，35 个未实名，且未实名用户的 `real_name` 与 `id_card` 字段全为空字符串。**

直接后果：
- 用户实名审核列表有 36 条记录，但**其中 35 条没有任何可审核的实名信息**，点进去是空详情。
- 实名审核模块**不能作为 MVP 的"可演示闭环"**。它可以做列表、可以做状态筛选、可以做"标记为已实名"的写操作，但**审核链路无法端到端跑通**——因为没有第三方实名核验数据源，也没有可核对的姓名与证件号。
- 这个模块的价值定位必须调整：从"审核员逐单审批"降级为"**实名状态台账 + 异常标记**"。这才是与现有数据匹配的诚实定位。

### 2.4 关键核实结论三：数据本身的脏点

后台是给内部员工每天用的工具，脏数据会直接变成运营工单。实测发现：

| 脏点 | 实测 | 影响模块 |
|---|---|---|
| `items.status` 枚举不统一 | 5 个藏品出现 3 种值：`on`（2 个）、`sold_out`（1 个）、`1`（2 个） | 商品管理。筛选/上下架操作会漏数据 |
| `items.content` 大面积为空 | 5 个藏品中 **4 个** content 为空 | 商品管理。详情页是空壳 |
| `item_copyrights.name` 脏数据 | 6 条中 2 条 name 为字符串 `1`，1 条为「第1个版权」 | 版权审核。列表直接显示会显得系统不可靠 |
| `item_copyrights` 孤儿记录 | 6 条中 **4 条**在 items 中无同名藏品 | 版权审核 |
| `nfts.sell_status` 与挂单不一致 | 10 个 nfts 的 `sell_status='on_sale'`，但 `sell_status` 字段实际存的是数字 `1`；另有 6 个 `sell_status='none'` | 二级市场监控 |
| 金额单位不统一 | `items.price` 单位为**元**（388.00），而 `items.secondary_low_price` / `trade_amount` / `last_trade_amount` / `nft_trade_logs.sold_price` 单位为**分**（105100 = 1051元） | 商品管理、二级市场监控。**这是最容易出错的点** |

**金额单位混用必须在 PRD 里作为强制约束写明。** 建表注释里已经明确警告过「源站单位为分，DAO 层 /100」，但后台要做的是反向——展示时要 /100，录入时要 *100。若不明确，后台算出来的成交额会差 100 倍。

## 三、竞品分析

### 3.1 竞品清单与信息架构

调研对象为三类：海外 NFT 交易平台后台、海外艺术品交易平台后台、国内数字藏品平台后台。

---

#### 竞品 A：OpenSea 后台（OpenSea Studio）

**类型**：海外 NFT 交易平台，全球最大。

**信息架构（导航分组）**：

| 分组 | 子项 |
|---|---|
| 藏品管理 | 集合（Collection）列表、集合编辑、单个物件管理、批量编辑 |
| 发行 | Drop 创建、Drop 配置、白名单设置 |
| 交易监控 | 活动（Activity）、拍卖（Auctions）、报价（Offers）、成交记录 |
| 用户 | 用户列表、用户详情、举报与标记 |
| 内容审核 | 举报队列、内容政策（Content Moderation）、DMCA 申诉 |
| 统计 | 集合统计、创作者统计 |

**关键功能做法**：

1. **集合审核与上架分离**。新建集合默认为 `unverified`（未认证）状态，不进入搜索栏和侧边栏。创作者需提交认证申请，平台审核后才获得展示权。
2. **多人协作权限**。集合可添加 collaborator，被授权的编辑者可以修改集合设置、创建新物件。但**只有集合所有者**能修改创作者收益地址和收益比例。文档中明确写「只添加你信任的协作者」。
3. **分级佣金可视化**。支付页面重构后可清楚看到二级销售佣金，以及从单个 NFT 和捆绑 NFT 销售中分别获得多少佣金。
4. **内容分级标记**。创建集合时需勾选「是否包含露骨和敏感内容」等标记，该标记会传导到物件级。

**它们的短板/差评**：

- **协作者权限颗粒度粗**。文档只能表达「能改集合设置」和「不能改收益地址」的粗粒度区分，一旦协作者被恶意授权，平台没有细粒度的撤销或变更审计能力。
- **认证流程是黑盒**。审核周期文档写「可能需要一天」，没有状态机、没有进度反馈，创作者只能干等。
- **无批量审核**。Content Moderation 是队列式的逐条处理，举报量上升后效率极低。

---

#### 竞品 B：SuperRare 后台

**类型**：海外艺术品交易平台，以策展和稀缺性为特色。

**信息架构**：

| 分组 | 子项 |
|---|---|
| 策展管理 | 策展池（Curation）、白名单策展、精选系列 |
| 拍卖 | 拍卖列表、竞拍管理、竞价记录 |
| 订单 | 订单列表、订单详情、履约状态 |
| 用户 | 创作者管理、收藏家管理 |
| 内容 | 内容政策、举报处理 |

**关键功能做法**：

1. **策展池作为准入闸门**。作品先进入策展池（Curated Pool），经人工挑选后才进入市场可见状态。这与 OpenSea 的「unverified 标签 + 提交认证」是不同的实现路径，但目标一致：把未经审核的内容挡在C 端之外。
2. **订单履约状态独立管理**。订单有独立的履约状态机，与支付状态分离。这对处理纠纷很关键——付款成功但未交付，是一个独立可查询的状态。

**它们的短板/差评**：

- **策展池不透明**。创作者无法查询自己的作品当前在策展池的哪一环、还差什么，进度全靠猜。
- **纠纷处理无痕迹**。用户举报订单纠纷后，平台内部如何裁决、是否通知双方，外部不可见。
- **艺术品属性弱**。艺术品是 1-of-1 唯一件，而国内数字藏品大量是同质化批量发行，SuperRare 的模型无法直接套用。

---

#### 竞品 C：Blur（NFT 交易聚合平台）

**类型**：以交易速度为核心竞争力的聚合平台。

**信息架构**：

| 分组 | 子项 |
|---|---|
| 交易 | 交易池（Pools）、跨平台挂单聚合、成交历史 |
| 集合 | 集合列表、集合造假检测（Wash Trading 检测） |
| 用户 | 用户画像、地址标签 |
| 数据 | 交易量排行榜、稀有度排行 |

**关键功能做法**：

1. **反刷盘（Wash Trading）监控**。Blur 的核心竞争力建立在交易数据可信上，因此后台把「识别对刷」作为一等能力。这直接对应到「二级市场监控」模块。
2. **挂单聚合与异常价识别**。同一 NFT 在多个渠道挂单，异常低价挂单会被标记。
3. **地址维度的用户画像**。以链上地址而非账号 ID 为主键。

**它们的短板/差评**：

- **反刷盘只有分数没有解释**。系统给出「可疑度评分」，但运营看不懂为什么被判定为可疑，无法向用户解释。
- **链上数据依赖强**。国内平台没有公开链上数据可查，无法直接套用。

---

#### 竞品 D：国内数字藏品平台（以鲸探的行业实践为参照）

**类型**：国内合规导向的数字藏品平台。鲸探的 C 端不开放二级交易，但**其后台侧的合规治理做法是行业公开可参考的范本**。

**行业标准要求**（来源：区块链数字藏品应用系统技术要求团体标准，及中国文化产业协会《数字藏品行业自律发展倡议》）：

标准第 8.1.2 条对**业务平台**明确要求：

| 标准条款 | 要求 | 对应后台模块 |
|---|---|---|
| a) | 具备个人/企业用户身份注册功能 | 用户管理 |
| b) | 具备身份注销功能，并删除相关用户信息 | 用户管理 |
| e) | **对数字藏品进行原创性审查**，对可能存在侵权的作品做**过滤和标识** | **内容版权审核** |
| f) | **注册发行前进行评审**，评估法律法规、监管政策风险，评估通过才能发行 | 商品上架审核 |
| j) | **限制转移**，如发行购买一段时间（半年）后才能转移 | 规则配置 |
| n) | 支持对数字藏品**全生命周期合规风险评估** | 二级市场监控 |

《自律发展倡议》第十四条要点：平台应依法具备资质、坚持实名制、加强知识产权保护能力建设、抵制金融化炒作。

**鲸探的审核做法**：所有上架藏品需经专家团队筛选，杜绝盗版或低质内容。

**它们的短板**：
- **审核标准不公开**。用户不知道审核要过几关、每关查什么。
- **审核时效无承诺**。没有 SLA，用户投诉后无法预期处理时间。
- **二级交易监控能力弱**。因产品设计上不支持二级交易，反而缺乏对二级市场的风控经验——这正是我们这个复刻项目的缺口所在。

### 3.3 我们的市场空白

三个真实空白，按可实现性排序：

**空白一：写操作与C 端展示的隔离机制。**
所有竞品的后台都是直接写生产库——后台改了就是改了。这在复刻项目里是致命的：我们同步的C 端数据是源站镜像，运营改了就回不去了。**没有任何一个竞品需要解决这个问题，因为他们没有「镜像数据」这个前提。** 这是我们的天然差异点。

**空白二：越权拦截的工程化落地。**
竞品的 RBAC 大多是「前端隐藏按钮 + 后端接口不校验」的半成品状态——运营看不到按钮但可以直接调接口。我们要求服务端逐接口校验权限，这是可以做出差异的。

**空白三：审核状态的透明化。**
OpenSea 的认证流程用户只能等，国内平台审核标准不公开。我们的版权审核只有 2 个作者、6 条版权记录，**数据量小到可以做到每条都给出明确的人工结论和理由**。这是小数据量带来的独有优势，不该浪费。

### 4.3 越权防护要求

| 层级 | 要求 |
|---|---|
| 路由守卫 | 前端路由按角色过滤菜单，无权限菜单不渲染 |
| **服务端校验（强制）** | **每个写接口必须在服务端校验当前账号的角色权限，不得仅依赖前端隐藏按钮。这是硬性要求** |
| 敏感字段脱敏 | `viewer` 与 `reviewer` 角色访问用户详情时，`id_card` 默认掩码显示（如 `3***********1234`），仅 `ops`/`support` 且有明确操作意图时可见完整值，且该次查看须记入审计日志 |
| 权限最小化起步 | 新角色默认只给R 权限，写权限按需单独开通，禁止创建时预授 |
| 职责分离（SoD） | 同一账号不得同时持有 `ops` 与 `reviewer`——避免自己上架自己审批 |
| 操作全量留痕 | 所有写操作记录：操作人、角色、时间、IP、对象、字段、前值、后值 |

> 依据：NIST SP 800-53 AC-6（最小权限）、AC-5（职责分离）、AU-6（审计记录）。业界实践共识是「审核证据的权限与角色管理权限必须分离，否则权限体系在一周内就会失控」。

## 五、用户画像

### 5.1 平台运营（ops）

| 项目 | 内容 |
|---|---|
| **职责** | 每日维护藏品上下架状态、调整价格与推荐位、处理挂单异常 |
| **每日高频操作** | ①打开藏品列表确认今日在售情况 ②处理待上架/待下架的藏品 ③调整异常挂单价 ④给热门藏品打推荐标记 ⑤核对当日成交概况 |
| **最怕什么** | **怕自己改错了且改不回去。** 尤其是价格——把 388 元改成 38800 元这类错误，因为无留痕、无回滚，往往几天后才发现 |
| **对后台的核心期待** | 「改错了能一键还原」——所以写操作必须留前值，必须有操作日志 |

### 5.2 财务/客服（support）

| 项目 | 内容 |
|---|---|
| **职责** | 响应用户申诉、查订单与钱包流水、冻结违规用户 |
| **每日高频操作** | ①按用户 ID 或手机号查用户详情 ②查该用户的订单记录 ③查钱包余额与收支 ④处理「我的藏品不见了」「提现没到账」这类申诉 ⑤对违规用户做冻结 |
| **最怕什么** | **怕看不到完整信息。** 用户报「钱被扣了但没收到藏品」，客服看不到订单和链上记录就只能回复用户，实际上是查了但没用。另外**直接接触用户身份证号，没有脱敏是重大风险** |
| **对后台的核心期待** | 「一个用户的所有信息在一个页面上看完，不用跳来跳去」+「身份证号默认看不到，需要时再点开」 |

### 5.3 数据观察者（viewer）

| 项目 | 内容 |
|---|---|
| **职责** | 每日看平台运营数据、交易趋势、藏品热度，为决策提供依据 |
| **每日高频操作** | ①打开总览看板看今日UV/成交额/挂单数 ②看近7 日交易趋势 ③看哪些藏品热度高 ④导出数据做外部分析 |
| **最怕什么** | **最怕误操作。** 观察者的价值全在数据准确性上，一次误改就毁掉他全部工作的可信度。所以这个角色必须**绝对只读**——不是「前端不给点」，而是服务端拒绝任何写请求 |
| **对后台的核心期待** | 「我怎么点都不会出事」。所以看板页要明确标注「只读模式」，让角色本身成为可见提示 |

### 5.4 内容/版权审核（reviewer）

| 项目 | 内容 |
|---|---|
| **职责** | 审核藏品内容合规性、审核版权信息真实性、处理原创性异议 |
| **每日高频操作**（当前数据量下） | ①打开版权审核队列看待审条目 ②逐条核对版权图与藏品 ③对不上的版权条目标记为「关联异常」 ④查看藏品内容详情判断合规 |
| **最怕什么** | **怕没有判定依据。** 行业标准要求「对可能存在侵权的作品做过滤和标识」，但没说什么算侵权。审核员面对 4 条对不上藏品的版权记录时，如果系统只显示「待审核」三个字，他只能凭感觉点通过或驳回 |
| **对后台的核心期待** | 「告诉我每条为什么被判为异常」。所以版权审核队列要直接展示关联诊断结果（是否匹配到藏品、匹配方式是什么），而不是让人自己去查 |

## 六、用户故事（Given / When / Then）

### 6.1 平台运营

**故事1：调整藏品价格并能还原**

- Given 运营角色已登录，藏品「臻海蓝卡」当前一级价为 388.00 元
- When 运营将该价格调整为 499.00 元并提交
- Then 系统写入新价格并记录一条操作日志（含操作人「运营A」、时间、改前值 388.00、改后值 499.00、字段 `items.price`）
- And 该次修改被标记 `is_local_override = 1`
- And 运营在「操作日志」页可看到这条记录，并可通过「还原」按钮将价格恢复为 388.00，还原动作本身也生成一条新日志

**故事 2：处理待下架藏品**

- Given 藏品「臻海蓝卡」的 `status` 为 `sold_out`
- When 运营在藏品列表中筛选 `status = on`，共返回 2 条记录
- Then 列表中不出现「臻海蓝卡」
- And 若运营切换到筛选「全部状态」，则能查到「臻海蓝卡」并看到其状态为「已售罄」
- And 页面在顶部提示「当前状态枚举存在历史脏数据（检测到 3 种状态值），建议前往数据治理」

### 6.2 财务/客服

**故事 3：完整查阅单个用户的交易全景**

- Given 客服角色已登录，已知用户手机号为某真实在库手机号
- When 客服搜索该用户并打开详情页
- Then 页面在同一屏内展示：用户基本信息、实名状态、钱包余额（可用/冻结）、该用户全部 NFT 持有列表、该用户全部订单记录（当前库中共 2 条订单）
- And 页面分模块加载，某模块无数据时该模块显示空态而非整页报错

**故事 4：身份证号默认脱敏 + 留痕查看**

- Given 客服角色已登录，打开某用户详情页
- When 客服查看「实名信息」区块
- Then 身份证号以掩码形式显示（如 `3***********1234`），不可直接复制
- When 客服点击「查看完整证件号」并二次确认
- Then 系统展示完整值，且本次查看行为写入审计日志（含查看人、时间、被查看用户 ID）

### 6.3 数据观察者

**故事 5：看板只读，任何写路径都被拒**

- Given 观察者角色已登录，进入总览看板
- When 观察者点击页面上的任意可交互元素（筛选器、时间范围切换、导出）
- Then 筛选与时间切换正常生效（读操作正常）
- And 当观察者通过任意途径尝试调用写接口时
- Then 服务端返回权限拒绝（HTTP 403），并记录一次越权尝试日志
- And 页面顶部持续显示「只读模式」标识

**故事 6：导出数据用于外部分析**

- Given 观察者角色已登录，在交易趋势图上选择了近 7 日区间
- When 观察者点击「导出」
- Then 系统生成导出文件，文件内仅包含所选区间的数据
- And 导出动作记入操作日志（含导出人、导出时间、数据区间、行数）

### 6.4 内容/版权审核

**故事 7：版权审核队列直接暴露关联异常**

- Given 审核角色已登录，打开版权审核队列
- Then 队列共显示 6 条版权记录（来自 `item_copyrights` 实测数据）
- And 每条记录直接展示关联诊断结果：「臻海蓝卡」「八仙过海·韩湘子」「八仙过海·蓝采和」3 条标记为「已匹配藏品」；其余 3 条标记为「关联异常」，并显示「未找到同名藏品」及最近一次匹配尝试时间
- And 名称为「1」和「第1个版权」的记录额外标记「名称为无效占位值，需人工补全」

**故事 8：审核结论必须留理由**

- Given 审核角色已登录，对某版权记录打开审核详情
- When 审核选择「驳回」并提交
- Then 系统强制要求填写驳回理由（不填写无法提交）
- And 提交后生成一条审核记录，含审核人、时间、结论、理由、被审核对象 ID
- And 该记录进入版权审核日志页，不可删除

## 七、MVP 范围锁定

按 RICE 公式评分：`RICE = (Reach × Impact × Confidence) / Effort`

评分标尺：Reach 1-10（1=极少影响，10=全部用户）；Impact 0.25/0.5/1/2/3（3=巨大影响，0.25=微小）；Confidence 50%/80%/100%；Effort 1-10 人月（1=半天，10=3个月以上）。

### 7.1 MVP 优先级表

| 优先级 | 功能 | 验收标准摘要 | Reach | Impact | Confidence | Effort | RICE |
|---|---|---|---|---|---|---|---|
| **P0** | 藏品列表与详情查询 | 5 个藏品可查；按 status/cid/是否可二级交易筛选；脏状态枚举有提示；详情显示作者（JOIN `item_authors`）与成交概况 | 9 | 3 | 100% | 1 | **27.0** |
| **P0** | 藏品上下架与内容编辑（带 `is_local_override`） | 改 `status`、content、推荐标记成功并留痕；C端列表不受影响；可一键还原 | 8 | 3 | 100% | 2 | **12.0** |
| **P0** | 挂单监控列表与强制下架 | 10 条挂单可查；显示卖家/藏品/价格/状态；可强制下架并留痕；金额单位正确（分→元） | 8 | 3 | 100% | 1.5 | **16.0** |
| **P0** | 异常价格标记与备注 | 可对挂单加异常标记与备注；异常判定阈值可配置；标记后操作人可见 | 6 | 2 | 80% | 1 | **9.6** |
| **P1** | 只读数据看板（总览 + 交易趋势 + 藏品热度） | 三张图基于真实数据渲染；全站无写入口；服务端拒绝写请求并记越权日志 | 9 | 2 | 100% | 2 | **9.0** |
| **P1** | 用户列表与详情（订单 + NFT + 钱包一体） | 36 用户可查；详情单屏聚合；身份证号掩码 | 9 | 2 | 100% | 2 | **9.0** |
| **P1** | 实名状态台账 | 显示 35 未实名/ 1 已实名的真实分布；支持录入实名材料（ops/support）；不做审核流 | 7 | 2 | 100% | 1.5 | **9.3** |
| **P1** | 版权审核队列 | 6 条版权全展示；关联诊断（3 匹配 / 3 异常）；审核结论 + 理由必填留痕 | 5 | 2 | 80% | 2 | **4.0** |
| **P2** | 操作审计日志查询 | 可按操作人/对象/时间检索；记录含前后值；支持还原操作 | 7 | 2 | 100% | 1.5 | **9.3** |
| **P2** | 用户冻结/解冻 | 改`users.status`；需二次确认；解冻不受限，冻结需填理由 | 5 | 2 | 80% | 1 | **8.0** |
| **P2** | 异常成交监控（基于 `nft_trade_logs`） | 10 条成交记录可查；同藏品短时间内重复同价成交可标记 | 5 | 1 | 80% | 1.5 | **2.7** |

### 7.2 MVP 交付边界

MVP = **P0 + P1 共 8 项功能**。

P2 三项（三级）在 MVP 首期可不交付，但**「操作审计日志」的数据写入必须在 P0 阶段就实装**——即使查询页面延后，底层留痕不能延后，否则 P0 的写操作上线时是裸奔的。这是本PRD 的一条强约束。

## 九、数据现状对功能的影响分析

这是本 PRD 最重要的一章。以下逐模块说明：哪些功能会因底表为空成为空壳页，以及对应的空态与引导设计。

### 9.1 空壳页风险清单

| 模块 | 底表 | 实测行数 | 空壳风险 | 严重度 |
|---|---|---|---|---|
| 版权审核 | `item_copyrights` | 6 | **否**，有数据。但4 条关联异常 | 中 |
| 版权审核 | `item_authors` | **2**（非0） | **否**，可用。但作者信息仅 2 条 5 个藏品 | 中 |
| 用户实名审核 | `users` | 36 | **部分空壳**——35 个未实名无材料 | **高** |
| 用户实名审核 | `wallet_transactions` | 0 | **是**，无法展示资金流水 | 高 |
| 二级市场监控 | `nft_sell_orders` | 10 | **否**，可用 | 低 |
| 二级市场监控 | `nft_trade_logs` | 10 | **否**，可用 | 低 |
| 二级市场监控 | `nft_market_apply_orders` | 0 | **是**，求购 tab 全空 | 中 |
| 商品管理 | `items` | 5 | **否**，但 4 个 content 为空 | 中 |
| 数据看板 | `users` / `orders` / `nft_trade_logs` | 36 / 2 / 10 | **部分空壳**——趋势图样本极少 | **高** |
| 用户冻结 | `users` | 36 | 否，可用 | 低 |

### 9.2 空态设计原则

**核心原则：区分「真的没有数据」和「功能没做完」。**

空态必须让运营一眼看出是哪种情况，否则第一周就会被当成 Bug 报上来。三种空态必须视觉上可区分：

| 空态类型 | 文案原则 | 视觉标识 | 附加信息 |
|---|---|---|---|
| **功能未开放** | 「该模块依赖的数据表当前无数据，功能待数据积累后启用」 | 中性灰 + 说明图标 | 列出依赖表名与当前行数，说明启用条件 |
| **筛选无结果** | 「当前筛选条件下无匹配结果」 | 中性灰 + 搜索图标 | 提供「清除筛选」操作 |
| **配置缺失** | 「存在 N 条记录缺少必要关联信息」 | 警示色 + 警示图标 | 提供跳转数据治理的入口 |

**禁止的文案**：不得出现「暂无数据」四个字了事，不得出现「Welcome」「Sign up today」「Lorem ipsum」类空洞占位，不得用「暂无数据」掩盖「数据没接」和「数据真的没有」的区别。

### 9.3 分模块空态与引导设计

#### 模块 A：数据看板（最高风险）

**问题**：订单仅 2 条，成交记录 10 条，日活无法统计（无埋点数据）。「近 7 日交易趋势」图只有 2 个数据点，「近 30 日」只有 10 个散点。画折线图是荒谬的。

**设计决策：看板不画折线图，改为指标卡 + 分布列表。**

| 指标卡 | 内容 | 数据来源 |
|---|---|---|
| 总用户数 | 36 | `users` |
| 已实名用户 | 1（占比显示 2.8%） | `users` WHERE `has_real_name=1` |
| 藏品总数 | 5（1 个已售罄） | `items` |
| 在售挂单数 | 10 | `nft_sell_orders` WHERE `status=1` |
| 累计成交记录 | 10 | `nft_trade_logs` |
| 累计成交额 | 按 `sold_price` 求和÷100 转元 | `nft_trade_logs` |
| 挂单总金额 | 按 `price` 求和 ÷100 转元 | `nft_sell_orders` |

**替代折线图的三种可视化**：
1. **藏品成交排行**（横向条形图）：5 个藏品按成交记录数排序，臻海蓝卡与八仙过海系列各自占多少，一眼可见。
2. **成交价区间分布**（柱状状态）：10 条成交记录的价格落在哪些区间。当前数据为103000-105100 分（即 1030-1051 元），集中在单一区间。
3. **用户活跃分布**（列表）：36 个用户按钱包余额区间分组，替代无法统计的 DAU。

**空态处理**：若某指标卡因依赖表为空（如提现相关），显示「依赖表 `wallet_transactions` 当前 0 行，本指标待数据积累后启用」，并明确不展示 0——因为「0 条流水」和「这个指标没做」是两回事。

#### 模块 B：用户实名审核（诚实降级）

**问题**：36 个用户中 35 个 `has_real_name=0` 且 `real_name`/`id_card` 全为空。审核列表 36 条，点进去 35 条是空的。这是最容易被当成 Bug 的模块。

**设计决策：定位从「审核流程」改为「实名状态台账 + 异常标记」。**

**实名状态列表**（首屏，四列）：

| 列 | 内容 |
|---|---|
| 用户 | 手机号（掩码）+ 用户ID |
| 实名状态 | 未实名 35 个/ 已实名 1 个（用状态标签区分，不用颜色区分） |
| 实名信息 | 未实名时显示「无材料」（灰色文字），已实名时显示掩码证件号 |
| 注册时间 / 最后登录 | 来自 `users.created_at` / `last_login_at` |

**详情页**：
- 未实名用户：明确显示「该用户未提交实名材料，无可审核内容」，并展示 `has_real_name=0` 的证据（空值截图式的空态区块），**而不是空白页**
- 已实名用户：正常展示，实名信息区块可见
- **新增能力**：支持运营/客服手动录入实名材料（姓名 + 证件号），录入后 `has_real_name=1`。这是当前数据下唯一能让该模块产生实际价值的动作。录入必须留痕，且证件号写入后立即掩码显示

**不做的事**：不做「审核通过/驳回」状态机（因为没有待审队列可审），不做批量实名导入。

#### 模块 C：二级市场监控

**问题**：`nft_market_apply_orders` 为 0 行，若做成含「寄售/求购/委托」三个 tab 的页面，其中 2 个 tab 全空。

**设计决策：不做三tab，做单一挂单列表 + 可选的空tab 标注。**

- 主列表基于 `nft_sell_orders`（10 条，有数据）
- 「求购」和「委托」tab保留但标注「该市场类型当前 0 条数据，源站暂无求购单」，委托 tab 实测有 10 条数据（`nft_market_trust_orders`），因此委托 tab **可展示**
- 因此最终形态：寄售 tab（10 条，实数据）、委托 tab（10 条，实数据）、求购 tab（0 条，空态标注）

**挂单列表字段**：挂单ID、藏品（名称 + 图）、NFT 编号（token）、卖家（用户ID）、挂单价（分→元，**注意单位**）、状态（在售 10 条）、操作（强制下架）

**金额单位强制约束**：所有金额字段展示前统一除以 100。`nft_sell_orders.price=500` 表示 5.00 元而非 500 元。这个坑必须在前端统一封装，架构师需要在设计文档中明确。

**异常价格预警设计**：当前 10 条挂单价全部为 500 分（5.00 元），10 条成交价在 103000-105100 分。挂单价远低于成交价，**这本身就是异常信号**——挂单价仅为成交价的约 1/20。

建议的默认规则（阈值可配置）：
- 单个挂单价 < 该藏品最近成交价 × 50% → 标记「疑似异常低价」
- 同一卖家短期内挂单数 ≥ 3 → 标记「疑似批量挂单」

当前数据下会命中「疑似异常低价」。这是好的——**功能上线第一天就有真实信号，说明监控有价值**，而不是空跑。

#### 模块 D：版权审核

**问题**：不是空表，但关联关系脆弱——6 条版权中 4 条在 `items` 表无同名藏品（含 2 条 name 为 `1` 的脏数据）。

**设计决策：把「关联诊断」作为队列的一等列，而不是让人工去查。**

**版权审核队列**：

| 列 | 内容 |
|---|---|
| 版权名称 | 显示 `name` 原值。name 为 `1` 或纯数字时，额外标红提示「名称为无效占位值」 |
| 版权图 | 缩略图 |
| 关联藏品 | 系统自动匹配结果：3 条显示匹配到的藏品名（臻海蓝卡、八仙过海·韩湘子、八仙过海·蓝采和），4 条显示「关联异常：未找到同名藏品」 |
| 排序 | `sort` 值 |
| 审核状态 | 待审核 / 已通过 / 已驳回 |
| 操作 | 通过 / 驳回（驳回必填理由） |

**关联匹配逻辑的已知缺陷（必须写明给架构师）**：
当前 `item_copyrights` 与 `items` 之间**没有外键**，唯一可能的连接是 `name = items.name` 字符串精确匹配。这机制脆弱：
- 「第1个版权」这类名称本就对不上
- 2 条 name 为 `1` 的记录匹配结果不确定
- 若藏品改名，关联即断裂

**产品侧建议**：本期接受这个脆弱性（因为只有 6 条数据，人工可核），但**必须做成配置项而非硬编码**——未来若要建真正的版权-藏品关联表，能改配置切换到新字段。同时页面上要明确告诉审核员「当前关联基于名称字符串匹配，可靠性有限」，避免审核员误以为系统已做了严格校验。

**与标准要求的对照**：团体标准第8.1.2 条 e) 要求「对数字藏品进行原创性审查，对可能存在侵权的作品做过滤和标识」。本期版权审核队列 + 标识功能可视为该要求的最小落地。完整版需要接入图像指纹比对，本期不具备条件。

#### 模块E：商品与藏品管理

**问题**：`items.content` 5个藏品中 4 个为空，详情页图文区是空的。

**设计决策**：详情页的图文区块为空态要明确写「该藏品未录入图文详情」，并给运营一个「去编辑」的直接入口。同时要展示「藏品内容完整度」指标（如「1/5 个藏品有图文详情」），让运营知道还有哪些没填。

**status 枚举脏数据处理**：
实测 5 个藏品有 3 种 status 值（`on` 2个、`sold_out` 1个、`1` 2个）。后台筛选器**必须同时识别 `on` 和 `1` 为「在售」**。筛选下拉选项固定为：全部 / 在售 / 已售罄 / 预热中 / 全部隐藏，并把实际出现的原始值作为副标展示（如「在售（含历史值：1）」）。

**作者信息展示**：5 个藏品全部能关联到作者（`item_authors` 2 条：臻海艺术、闹翻天）。详情页展示作者名 + 头像 + 简介 + 作品数。注意 `works_count` 字段值（臻海艺术 3、闹翻天 2）与实际藏品数（臻海艺术 1 个、闹翻天 4 个）**不一致**，展示时应以实时统计为准并提示字段偏差。

### 9.4 数据治理建议（不属MVP，但需架构师知晓）

以下脏数据建议在联调前或联调中由架构师评估处理，本PRD 不强制：

1. `items.status` 枚举统一（`1` → `on`）
2. `item_copyrights` 脏 name 清理（2 条 `1`、1 条「第1个版权」）
3. `items.content` 补齐或明确标注为空
4. `nfts.sell_status` 语义修正（当前存的是数字 `1`，但注释说是字符串枚举）
5. `item_authors.works_count` 与实际藏品数对齐
6. `nfts.sell_status` 与 `nft_sell_orders.status` 的一致性核对（10 个 nfts 标on_sale 且有对应挂单，但 6 个 nfts 为 none，需确认这 6 个是否真的未挂单）

| 类别 | 要求 | 优先级 |
|---|---|---|
| 性能 | 列表页首屏 < 2s（当前数据量极小，36/5/10 条，本可轻松达成）；看板聚合接口 p95 < 500ms | P0 |

### 埋点实现要求（业务侧要求，具体实现由架构师定）

| 事件类别 | 必埋事件 | 说明 |
|---|---|---|
| 登录 | `admin_login`、`admin_logout`、`admin_login_failed` | 登录失败需连续 5次告警 |
| 浏览 | `admin_page_view` | 携带角色与页面标识，用于识别观察者是否真的只读 |
| 核心写操作 | `admin_item_status_changed`、`admin_listing_forced_off`、`admin_realname_filled`、`admin_copyright_reviewed` | 必须携带 `is_local_override` 标记 |
| 异常 | `admin_permission_denied` | 越权被拒，是越权防护是否有效的唯一验证手段 |
| 导出 | `admin_data_exported` | 携带导出数据区间与行数 |

**属性规范**：每个事件附`operator_id`、`operator_role`、`timestamp`、`page`、`is_local_override`。
**禁止采集**：不记录 `id_card` 原文、不记录 `real_name` 原文、不记录用户输入的驳回理由全文。
