## 一、产品定义

### 一句话定义

臻海艺术运营后台是一个**内部使用的四角色分级工作台**，让平台运营、财务客服、数据观察者、内容版权审核四类岗位，在不污染 C 端展示数据的前提下，各自看到并操作自己职责范围内的藏品、市场、用户与看板数据。

### 目标用户

内部员工，共四类角色（非C 端用户）。四类角色的职责、每日高频操作、最怕什么都见第五章用户画像。

### 核心问题

**源站 `h5.shengtai.cyou` 是纯 C 端 H5，96 个 JS 分包中没有任何 admin 分包，84 条 API 路径全部是用户侧（item / nft / order / user / wallet）。后台管理在源站不存在，接口契约无对照物。**

这意味着三件事：

1. **没有可复刻的原型**。运营现在要改一个藏品的价格或下一个挂单，只能直接改数据库，改完没人知道谁改的、什么时候改的。
2. **没有权限边界**。四类岗位如果共用一个数据库账号，那么"数据观察者"这个角色的存在就没有意义——他能看到的和能改的都一样。
3. **没有写操作留痕**。当前所有 C 端数据都是源站同步的镜像，运营的任何写操作如果直接落库，就会污染 C 端展示数据，且不可回滚、不可追溯。

### 核心定位（我们解决什么）

提供一个**带 RBAC 分级、写操作可标记、可审计**的内部管理入口，让运营能在本地库上做调整，同时保证：
- C 端展示数据不被后台写操作污染（写操作带 `is_local_override` 标记）
- 每一笔写操作都有操作人、时间、前后值的记录
- 越权访问在服务端被拦截，而非仅在前端隐藏按钮

### 2.2 关键核实结论一：作者信息存在哪张表

需求文档提出「`item_authors` 是 0 行但 `item_copyrights` 有 6 行——做版权审核时要去核实作者信息实际存在哪张表」。**我已核实，结论如下：**

**作者信息就在 `item_authors` 表，该表不空，有 2 行：**

| id | name | works_count | follower_count |
|---|---|---|---|
| 2103038557930151938 | 臻海艺术 | 3 | 0 |
| 2109922931380424706 | 闹翻天 | 2 | 0 |

`items.author_id` 外键关联完整：**5 个藏品全部能关联到作者，孤儿记录 0 条**。作者与藏品的对应关系为：

| 藏品 | author_id | 作者 |
|---|---|---|
| 臻海蓝卡 | 2103038557930151938 | 臻海艺术 |
| 八仙过海·韩湘子 | 2109922931380424706 | 闹翻天 |
| 八仙过海·蓝采和 | 2109922931380421702 | 闹翻天 |
| 张果老·纸驴云符 | 2109922931380421702 | 闹翻天 |
| 八仙过海·张果老 | 2109922931380421702 | 闹翻天 |

**这对产品设计有三个直接影响：**

1. **版权审核模块可以做实，不需要降级为"空态引导"。** 我原本预判版权审核会因作者表为空而成为空壳页，实测证明不成立。
2. **但 `item_copyrights` 表与 `items` 表没有外键关联。** `item_copyrights` 的关联字段是 `name`（版权名称），实测 6 条版权中 **4 条在 items 表中找不到同名藏品**（孤儿记录）。仅「臻海蓝卡」「八仙过海·韩湘子」「八仙过海·蓝彩和」三条能对上，还有 1 条名为「第1个版权」、2 条名为「1」（脏数据）。
3. **所以版权审核模块的核心设计难点不是"没有数据"，而是"关联关系脆弱"。** 审核员看到的是 6 条版权条目，但其中一半对不上任何藏品，且无法从版权条目反向跳转到藏品。这必须在 PRD 里明确定位为「待治理」，而不是假装关联完善。

### 2.3 关键核实结论二：实名审核的真实存量

`users` 表 36 行，实测分布：

| status | has_real_name | 数量 |
|---|---|---|
| normal | 0（未实名） | **35** |
| normal | 1（已实名） | **1** |

**这是本PRD 最严重的数据现状问题：36 个用户里只有 1 个已实名，35 个未实名，且未实名用户的 `real_name` 与 `id_card` 字段全为空字符串。**

直接后果：
- 用户实名审核列表有 36 条记录，但**其中 35 条没有任何可审核的实名信息**，点进去是空详情。
- 实名审核模块**不能作为 MVP 的"可演示闭环"**。它可以做列表、可以做状态筛选、可以做"标记为已实名"的写操作，但**审核链路无法端到端跑通**——因为没有第三方实名核验数据源，也没有可核对的姓名与证件号。
- 这个模块的价值定位必须调整：从"审核员逐单审批"降级为"**实名状态台账 + 异常标记**"。这才是与现有数据匹配的诚实定位。

### 2.4 关键核实结论三：数据本身的脏点

后台是给内部员工每天用的工具，脏数据会直接变成运营工单。实测发现：

| 脏点 | 实测 | 影响模块 |
|---|---|---|
| `items.status` 枚举不统一 | 5 个藏品出现 3 种值：`on`（2 个）、`sold_out`（1 个）、`1`（2 个） | 商品管理。筛选/上下架操作会漏数据 |
| `items.content` 大面积为空 | 5 个藏品中 **4 个** content 为空 | 商品管理。详情页是空壳 |
| `item_copyrights.name` 脏数据 | 6 条中 2 条 name 为字符串 `1`，1 条为「第1个版权」 | 版权审核。列表直接显示会显得系统不可靠 |
| `item_copyrights` 孤儿记录 | 6 条中 **4 条**在 items 中无同名藏品 | 版权审核 |
| `nfts.sell_status` 与挂单不一致 | 10 个 nfts 的 `sell_status='on_sale'`，但 `sell_status` 字段实际存的是数字 `1`；另有 6 个 `sell_status='none'` | 二级市场监控 |
| 金额单位不统一 | `items.price` 单位为**元**（388.00），而 `items.secondary_low_price` / `trade_amount` / `last_trade_amount` / `nft_trade_logs.sold_price` 单位为**分**（105100 = 1051元） | 商品管理、二级市场监控。**这是最容易出错的点** |

**金额单位混用必须在 PRD 里作为强制约束写明。** 建表注释里已经明确警告过「源站单位为分，DAO 层 /100」，但后台要做的是反向——展示时要 /100，录入时要 *100。若不明确，后台算出来的成交额会差 100 倍。

## 三、竞品分析

### 3.1 竞品清单与信息架构

调研对象为三类：海外 NFT 交易平台后台、海外艺术品交易平台后台、国内数字藏品平台后台。

---

#### 竞品 A：OpenSea 后台（OpenSea Studio）

**类型**：海外 NFT 交易平台，全球最大。

**信息架构（导航分组）**：

| 分组 | 子项 |
|---|---|
| 藏品管理 | 集合（Collection）列表、集合编辑、单个物件管理、批量编辑 |
| 发行 | Drop 创建、Drop 配置、白名单设置 |
| 交易监控 | 活动（Activity）、拍卖（Auctions）、报价（Offers）、成交记录 |
| 用户 | 用户列表、用户详情、举报与标记 |
| 内容审核 | 举报队列、内容政策（Content Moderation）、DMCA 申诉 |
| 统计 | 集合统计、创作者统计 |

**关键功能做法**：

1. **集合审核与上架分离**。新建集合默认为 `unverified`（未认证）状态，不进入搜索栏和侧边栏。创作者需提交认证申请，平台审核后才获得展示权。
2. **多人协作权限**。集合可添加 collaborator，被授权的编辑者可以修改集合设置、创建新物件。但**只有集合所有者**能修改创作者收益地址和收益比例。文档中明确写「只添加你信任的协作者」。
3. **分级佣金可视化**。支付页面重构后可清楚看到二级销售佣金，以及从单个 NFT 和捆绑 NFT 销售中分别获得多少佣金。
4. **内容分级标记**。创建集合时需勾选「是否包含露骨和敏感内容」等标记，该标记会传导到物件级。

**它们的短板/差评**：

- **协作者权限颗粒度粗**。文档只能表达「能改集合设置」和「不能改收益地址」的粗粒度区分，一旦协作者被恶意授权，平台没有细粒度的撤销或变更审计能力。
- **认证流程是黑盒**。审核周期文档写「可能需要一天」，没有状态机、没有进度反馈，创作者只能干等。
- **无批量审核**。Content Moderation 是队列式的逐条处理，举报量上升后效率极低。

---

#### 竞品 B：SuperRare 后台

**类型**：海外艺术品交易平台，以策展和稀缺性为特色。

**信息架构**：

| 分组 | 子项 |
|---|---|
| 策展管理 | 策展池（Curation）、白名单策展、精选系列 |
| 拍卖 | 拍卖列表、竞拍管理、竞价记录 |
| 订单 | 订单列表、订单详情、履约状态 |
| 用户 | 创作者管理、收藏家管理 |
| 内容 | 内容政策、举报处理 |

**关键功能做法**：

1. **策展池作为准入闸门**。作品先进入策展池（Curated Pool），经人工挑选后才进入市场可见状态。这与 OpenSea 的「unverified 标签 + 提交认证」是不同的实现路径，但目标一致：把未经审核的内容挡在C 端之外。
2. **订单履约状态独立管理**。订单有独立的履约状态机，与支付状态分离。这对处理纠纷很关键——付款成功但未交付，是一个独立可查询的状态。

**它们的短板/差评**：

- **策展池不透明**。创作者无法查询自己的作品当前在策展池的哪一环、还差什么，进度全靠猜。
- **纠纷处理无痕迹**。用户举报订单纠纷后，平台内部如何裁决、是否通知双方，外部不可见。
- **艺术品属性弱**。艺术品是 1-of-1 唯一件，而国内数字藏品大量是同质化批量发行，SuperRare 的模型无法直接套用。

---

#### 竞品 C：Blur（NFT 交易聚合平台）

**类型**：以交易速度为核心竞争力的聚合平台。

**信息架构**：

| 分组 | 子项 |
|---|---|
| 交易 | 交易池（Pools）、跨平台挂单聚合、成交历史 |
| 集合 | 集合列表、集合造假检测（Wash Trading 检测） |
| 用户 | 用户画像、地址标签 |
| 数据 | 交易量排行榜、稀有度排行 |

**关键功能做法**：

1. **反刷盘（Wash Trading）监控**。Blur 的核心竞争力建立在交易数据可信上，因此后台把「识别对刷」作为一等能力。这直接对应到「二级市场监控」模块。
2. **挂单聚合与异常价识别**。同一 NFT 在多个渠道挂单，异常低价挂单会被标记。
3. **地址维度的用户画像**。以链上地址而非账号 ID 为主键。

**它们的短板/差评**：

- **反刷盘只有分数没有解释**。系统给出「可疑度评分」，但运营看不懂为什么被判定为可疑，无法向用户解释。
- **链上数据依赖强**。国内平台没有公开链上数据可查，无法直接套用。

---

#### 竞品 D：国内数字藏品平台（以鲸探的行业实践为参照）

**类型**：国内合规导向的数字藏品平台。鲸探的 C 端不开放二级交易，但**其后台侧的合规治理做法是行业公开可参考的范本**。

**行业标准要求**（来源：区块链数字藏品应用系统技术要求团体标准，及中国文化产业协会《数字藏品行业自律发展倡议》）：

标准第 8.1.2 条对**业务平台**明确要求：

| 标准条款 | 要求 | 对应后台模块 |
|---|---|---|
| a) | 具备个人/企业用户身份注册功能 | 用户管理 |
| b) | 具备身份注销功能，并删除相关用户信息 | 用户管理 |
| e) | **对数字藏品进行原创性审查**，对可能存在侵权的作品做**过滤和标识** | **内容版权审核** |
| f) | **注册发行前进行评审**，评估法律法规、监管政策风险，评估通过才能发行 | 商品上架审核 |
| j) | **限制转移**，如发行购买一段时间（半年）后才能转移 | 规则配置 |
| n) | 支持对数字藏品**全生命周期合规风险评估** | 二级市场监控 |

《自律发展倡议》第十四条要点：平台应依法具备资质、坚持实名制、加强知识产权保护能力建设、抵制金融化炒作。

**鲸探的审核做法**：所有上架藏品需经专家团队筛选，杜绝盗版或低质内容。

**它们的短板**：
- **审核标准不公开**。用户不知道审核要过几关、每关查什么。
- **审核时效无承诺**。没有 SLA，用户投诉后无法预期处理时间。
- **二级交易监控能力弱**。因产品设计上不支持二级交易，反而缺乏对二级市场的风控经验——这正是我们这个复刻项目的缺口所在。

### 3.2 竞品横向对比

| 维度 | OpenSea | SuperRare | Blur | 国内数藏平台 | **臻海艺术后台（我们）** |
|---|---|---|---|---|---|
| 藏品准入机制 | unverified 标签 + 提交认证 | 策展池人工挑选 | 集合造假检测 | 专家团队筛选 | **本地库审核队列 + is_local_override 隔离** |
| 审核状态机 | 有，但流程黑盒 | 有，不透明 | 不适用 | 无公开 | **明示状态机 + 操作留痕** |
| 批量审核 | 无 | 无 | 不适用 | 不适用 | **MVP 不做，列入 Backlog** |
| 协作权限 | 有（粗粒度） | 无公开 | 不适用 | 不适用 | **RBAC 四角色 + 越权拦截** |
| 二级市场监控 | 交易记录 | 拍卖记录 | 挂单聚合 + 反刷盘 | 弱（不支持二级） | **挂单监控 + 异常价预警** |
| 纠纷处理 | 举报队列 | 独立履约状态 | 不适用 | 不适用 | **挂单状态强制 + 操作日志** |
| 实名审核 | KYC 流程成熟 | 基础 | 地址标签 | 强制实名制 | **实名状态台账（降级定位）** |
| 写操作留痕 | 有 | 不确定 | 不确定 | 不适用 | **必须有，且支持回溯** |
| 敏感字段脱敏 | 不明确 | 不明确 | 不明确 | 不明确 | **身份证号默认掩码** |

### 3.3 我们的市场空白

三个真实空白，按可实现性排序：

**空白一：写操作与C 端展示的隔离机制。**
所有竞品的后台都是直接写生产库——后台改了就是改了。这在复刻项目里是致命的：我们同步的C 端数据是源站镜像，运营改了就回不去了。**没有任何一个竞品需要解决这个问题，因为他们没有「镜像数据」这个前提。** 这是我们的天然差异点。

**空白二：越权拦截的工程化落地。**
竞品的 RBAC 大多是「前端隐藏按钮 + 后端接口不校验」的半成品状态——运营看不到按钮但可以直接调接口。我们要求服务端逐接口校验权限，这是可以做出差异的。

**空白三：审核状态的透明化。**
OpenSea 的认证流程用户只能等，国内平台审核标准不公开。我们的版权审核只有 2 个作者、6 条版权记录，**数据量小到可以做到每条都给出明确的人工结论和理由**。这是小数据量带来的独有优势，不该浪费。

### 4.3 越权防护要求

| 层级 | 要求 |
|---|---|
| 路由守卫 | 前端路由按角色过滤菜单，无权限菜单不渲染 |
| **服务端校验（强制）** | **每个写接口必须在服务端校验当前账号的角色权限，不得仅依赖前端隐藏按钮。这是硬性要求** |
| 敏感字段脱敏 | `viewer` 与 `reviewer` 角色访问用户详情时，`id_card` 默认掩码显示（如 `3***********1234`），仅 `ops`/`support` 且有明确操作意图时可见完整值，且该次查看须记入审计日志 |
| 权限最小化起步 | 新角色默认只给R 权限，写权限按需单独开通，禁止创建时预授 |
| 职责分离（SoD） | 同一账号不得同时持有 `ops` 与 `reviewer`——避免自己上架自己审批 |
| 操作全量留痕 | 所有写操作记录：操作人、角色、时间、IP、对象、字段、前值、后值 |

> 依据：NIST SP 800-53 AC-6（最小权限）、AC-5（职责分离）、AU-6（审计记录）。业界实践共识是「审核证据的权限与角色管理权限必须分离，否则权限体系在一周内就会失控」。

## 五、用户画像

### 5.1 平台运营（ops）

| 项目 | 内容 |
|---|---|
| **职责** | 每日维护藏品上下架状态、调整价格与推荐位、处理挂单异常 |
| **每日高频操作** | ①打开藏品列表确认今日在售情况 ②处理待上架/待下架的藏品 ③调整异常挂单价 ④给热门藏品打推荐标记 ⑤核对当日成交概况 |
| **最怕什么** | **怕自己改错了且改不回去。** 尤其是价格——把 388 元改成 38800 元这类错误，因为无留痕、无回滚，往往几天后才发现 |
| **对后台的核心期待** | 「改错了能一键还原」——所以写操作必须留前值，必须有操作日志 |

### 5.2 财务/客服（support）

| 项目 | 内容 |
|---|---|
| **职责** | 响应用户申诉、查订单与钱包流水、冻结违规用户 |
| **每日高频操作** | ①按用户 ID 或手机号查用户详情 ②查该用户的订单记录 ③查钱包余额与收支 ④处理「我的藏品不见了」「提现没到账」这类申诉 ⑤对违规用户做冻结 |
| **最怕什么** | **怕看不到完整信息。** 用户报「钱被扣了但没收到藏品」，客服看不到订单和链上记录就只能回复用户，实际上是查了但没用。另外**直接接触用户身份证号，没有脱敏是重大风险** |
| **对后台的核心期待** | 「一个用户的所有信息在一个页面上看完，不用跳来跳去」+「身份证号默认看不到，需要时再点开」 |

### 5.3 数据观察者（viewer）

| 项目 | 内容 |
|---|---|
| **职责** | 每日看平台运营数据、交易趋势、藏品热度，为决策提供依据 |
| **每日高频操作** | ①打开总览看板看今日UV/成交额/挂单数 ②看近7 日交易趋势 ③看哪些藏品热度高 ④导出数据做外部分析 |
| **最怕什么** | **最怕误操作。** 观察者的价值全在数据准确性上，一次误改就毁掉他全部工作的可信度。所以这个角色必须**绝对只读**——不是「前端不给点」，而是服务端拒绝任何写请求 |
| **对后台的核心期待** | 「我怎么点都不会出事」。所以看板页要明确标注「只读模式」，让角色本身成为可见提示 |

### 5.4 内容/版权审核（reviewer）

| 项目 | 内容 |
|---|---|
| **职责** | 审核藏品内容合规性、审核版权信息真实性、处理原创性异议 |
| **每日高频操作**（当前数据量下） | ①打开版权审核队列看待审条目 ②逐条核对版权图与藏品 ③对不上的版权条目标记为「关联异常」 ④查看藏品内容详情判断合规 |
| **最怕什么** | **怕没有判定依据。** 行业标准要求「对可能存在侵权的作品做过滤和标识」，但没说什么算侵权。审核员面对 4 条对不上藏品的版权记录时，如果系统只显示「待审核」三个字，他只能凭感觉点通过或驳回 |
| **对后台的核心期待** | 「告诉我每条为什么被判为异常」。所以版权审核队列要直接展示关联诊断结果（是否匹配到藏品、匹配方式是什么），而不是让人自己去查 |

## 六、用户故事（Given / When / Then）

### 6.1 平台运营

**故事1：调整藏品价格并能还原**

- Given 运营角色已登录，藏品「臻海蓝卡」当前一级价为 388.00 元
- When 运营将该价格调整为 499.00 元并提交
- Then 系统写入新价格并记录一条操作日志（含操作人「运营A」、时间、改前值 388.00、改后值 499.00、字段 `items.price`）
- And 该次修改被标记 `is_local_override = 1`
- And 运营在「操作日志」页可看到这条记录，并可通过「还原」按钮将价格恢复为 388.00，还原动作本身也生成一条新日志

**故事 2：处理待下架藏品**

- Given 藏品「臻海蓝卡」的 `status` 为 `sold_out`
- When 运营在藏品列表中筛选 `status = on`，共返回 2 条记录
- Then 列表中不出现「臻海蓝卡」
- And 若运营切换到筛选「全部状态」，则能查到「臻海蓝卡」并看到其状态为「已售罄」
- And 页面在顶部提示「当前状态枚举存在历史脏数据（检测到 3 种状态值），建议前往数据治理」

### 6.2 财务/客服

**故事 3：完整查阅单个用户的交易全景**

- Given 客服角色已登录，已知用户手机号为某真实在库手机号
- When 客服搜索该用户并打开详情页
- Then 页面在同一屏内展示：用户基本信息、实名状态、钱包余额（可用/冻结）、该用户全部 NFT 持有列表、该用户全部订单记录（当前库中共 2 条订单）
- And 页面分模块加载，某模块无数据时该模块显示空态而非整页报错

**故事 4：身份证号默认脱敏 + 留痕查看**

- Given 客服角色已登录，打开某用户详情页
- When 客服查看「实名信息」区块
- Then 身份证号以掩码形式显示（如 `3***********1234`），不可直接复制
- When 客服点击「查看完整证件号」并二次确认
- Then 系统展示完整值，且本次查看行为写入审计日志（含查看人、时间、被查看用户 ID）

### 6.3 数据观察者

**故事 5：看板只读，任何写路径都被拒**

- Given 观察者角色已登录，进入总览看板
- When 观察者点击页面上的任意可交互元素（筛选器、时间范围切换、导出）
- Then 筛选与时间切换正常生效（读操作正常）
- And 当观察者通过任意途径尝试调用写接口时
- Then 服务端返回权限拒绝（HTTP 403），并记录一次越权尝试日志
- And 页面顶部持续显示「只读模式」标识

**故事 6：导出数据用于外部分析**

- Given 观察者角色已登录，在交易趋势图上选择了近 7 日区间
- When 观察者点击「导出」
- Then 系统生成导出文件，文件内仅包含所选区间的数据
- And 导出动作记入操作日志（含导出人、导出时间、数据区间、行数）

### 6.4 内容/版权审核

**故事 7：版权审核队列直接暴露关联异常**

- Given 审核角色已登录，打开版权审核队列
- Then 队列共显示 6 条版权记录（来自 `item_copyrights` 实测数据）
- And 每条记录直接展示关联诊断结果：「臻海蓝卡」「八仙过海·韩湘子」「八仙过海·蓝采和」3 条标记为「已匹配藏品」；其余 3 条标记为「关联异常」，并显示「未找到同名藏品」及最近一次匹配尝试时间
- And 名称为「1」和「第1个版权」的记录额外标记「名称为无效占位值，需人工补全」

**故事 8：审核结论必须留理由**

- Given 审核角色已登录，对某版权记录打开审核详情
- When 审核选择「驳回」并提交
- Then 系统强制要求填写驳回理由（不填写无法提交）
- And 提交后生成一条审核记录，含审核人、时间、结论、理由、被审核对象 ID
- And 该记录进入版权审核日志页，不可删除

## 七、MVP 范围锁定

按 RICE 公式评分：`RICE = (Reach × Impact × Confidence) / Effort`

评分标尺：Reach 1-10（1=极少影响，10=全部用户）；Impact 0.25/0.5/1/2/3（3=巨大影响，0.25=微小）；Confidence 50%/80%/100%；Effort 1-10 人月（1=半天，10=3个月以上）。

### 7.1 MVP 优先级表

| 优先级 | 功能 | 验收标准摘要 | Reach | Impact | Confidence | Effort | RICE |
|---|---|---|---|---|---|---|---|
| **P0** | 藏品列表与详情查询 | 5 个藏品可查；按 status/cid/是否可二级交易筛选；脏状态枚举有提示；详情显示作者（JOIN `item_authors`）与成交概况 | 9 | 3 | 100% | 1 | **27.0** |
| **P0** | 藏品上下架与内容编辑（带 `is_local_override`） | 改 `status`、content、推荐标记成功并留痕；C端列表不受影响；可一键还原 | 8 | 3 | 100% | 2 | **12.0** |
| **P0** | 挂单监控列表与强制下架 | 10 条挂单可查；显示卖家/藏品/价格/状态；可强制下架并留痕；金额单位正确（分→元） | 8 | 3 | 100% | 1.5 | **16.0** |
| **P0** | 异常价格标记与备注 | 可对挂单加异常标记与备注；异常判定阈值可配置；标记后操作人可见 | 6 | 2 | 80% | 1 | **9.6** |
| **P1** | 只读数据看板（总览 + 交易趋势 + 藏品热度） | 三张图基于真实数据渲染；全站无写入口；服务端拒绝写请求并记越权日志 | 9 | 2 | 100% | 2 | **9.0** |
| **P1** | 用户列表与详情（订单 + NFT + 钱包一体） | 36 用户可查；详情单屏聚合；身份证号掩码 | 9 | 2 | 100% | 2 | **9.0** |
| **P1** | 实名状态台账 | 显示 35 未实名/ 1 已实名的真实分布；支持录入实名材料（ops/support）；不做审核流 | 7 | 2 | 100% | 1.5 | **9.3** |
| **P1** | 版权审核队列 | 6 条版权全展示；关联诊断（3 匹配 / 3 异常）；审核结论 + 理由必填留痕 | 5 | 2 | 80% | 2 | **4.0** |
| **P2** | 操作审计日志查询 | 可按操作人/对象/时间检索；记录含前后值；支持还原操作 | 7 | 2 | 100% | 1.5 | **9.3** |
| **P2** | 用户冻结/解冻 | 改`users.status`；需二次确认；解冻不受限，冻结需填理由 | 5 | 2 | 80% | 1 | **8.0** |
| **P2** | 异常成交监控（基于 `nft_trade_logs`） | 10 条成交记录可查；同藏品短时间内重复同价成交可标记 | 5 | 1 | 80% | 1.5 | **2.7** |

### 7.2 MVP 交付边界

MVP = **P0 + P1 共 8 项功能**。

P2 三项（三级）在 MVP 首期可不交付，但**「操作审计日志」的数据写入必须在 P0 阶段就实装**——即使查询页面延后，底层留痕不能延后，否则 P0 的写操作上线时是裸奔的。这是本PRD 的一条强约束。

## 八、明确不做（Out-of-Scope）

| 功能 | 原因 | 何时考虑 |
|---|---|---|
| **提现审核** | **依赖 `wallet_transactions` 表，该表当前实测 0 行。做出来就是空壳页。** 且提现审核涉及资金安全，其正确性无法用空数据验证——一个 0 行的审核页无法证明审核逻辑是对的。**特别说明：这是用户明确要求移出 MVP 的功能，理由成立** | 满足以下全部条件时重启：①`wallet_transactions` 表有真实数据（建议 ≥ 1000 行）②C端提现链路已跑通并有提现申请产生 ③支付通道对账已完成，可验证余额变动正确 |
| 支付流水管理（`order_payments`） | 该表实测 0 行，与提现审核同源问题 | 同上，且订单支付回调链路已实装 |

## 九、数据现状对功能的影响分析

这是本 PRD 最重要的一章。以下逐模块说明：哪些功能会因底表为空成为空壳页，以及对应的空态与引导设计。

### 9.1 空壳页风险清单

| 模块 | 底表 | 实测行数 | 空壳风险 | 严重度 |
|---|---|---|---|---|
| 版权审核 | `item_copyrights` | 6 | **否**，有数据。但4 条关联异常 | 中 |
| 版权审核 | `item_authors` | **2**（非0） | **否**，可用。但作者信息仅 2 条 5 个藏品 | 中 |
| 用户实名审核 | `users` | 36 | **部分空壳**——35 个未实名无材料 | **高** |
| 用户实名审核 | `wallet_transactions` | 0 | **是**，无法展示资金流水 | 高 |
| 二级市场监控 | `nft_sell_orders` | 10 | **否**，可用 | 低 |
| 二级市场监控 | `nft_trade_logs` | 10 | **否**，可用 | 低 |
| 二级市场监控 | `nft_market_apply_orders` | 0 | **是**，求购 tab 全空 | 中 |
| 商品管理 | `items` | 5 | **否**，但 4 个 content 为空 | 中 |
| 数据看板 | `users` / `orders` / `nft_trade_logs` | 36 / 2 / 10 | **部分空壳**——趋势图样本极少 | **高** |
| 用户冻结 | `users` | 36 | 否，可用 | 低 |

### 9.2 空态设计原则

**核心原则：区分「真的没有数据」和「功能没做完」。**

空态必须让运营一眼看出是哪种情况，否则第一周就会被当成 Bug 报上来。三种空态必须视觉上可区分：

| 空态类型 | 文案原则 | 视觉标识 | 附加信息 |
|---|---|---|---|
| **功能未开放** | 「该模块依赖的数据表当前无数据，功能待数据积累后启用」 | 中性灰 + 说明图标 | 列出依赖表名与当前行数，说明启用条件 |
| **筛选无结果** | 「当前筛选条件下无匹配结果」 | 中性灰 + 搜索图标 | 提供「清除筛选」操作 |
| **配置缺失** | 「存在 N 条记录缺少必要关联信息」 | 警示色 + 警示图标 | 提供跳转数据治理的入口 |

**禁止的文案**：不得出现「暂无数据」四个字了事，不得出现「Welcome」「Sign up today」「Lorem ipsum」类空洞占位，不得用「暂无数据」掩盖「数据没接」和「数据真的没有」的区别。

### 9.3 分模块空态与引导设计

#### 模块 A：数据看板（最高风险）

**问题**：订单仅 2 条，成交记录 10 条，日活无法统计（无埋点数据）。「近 7 日交易趋势」图只有 2 个数据点，「近 30 日」只有 10 个散点。画折线图是荒谬的。

**设计决策：看板不画折线图，改为指标卡 + 分布列表。**

| 指标卡 | 内容 | 数据来源 |
|---|---|---|
| 总用户数 | 36 | `users` |
| 已实名用户 | 1（占比显示 2.8%） | `users` WHERE `has_real_name=1` |
| 藏品总数 | 5（1 个已售罄） | `items` |
| 在售挂单数 | 10 | `nft_sell_orders` WHERE `status=1` |
| 累计成交记录 | 10 | `nft_trade_logs` |
| 累计成交额 | 按 `sold_price` 求和÷100 转元 | `nft_trade_logs` |
| 挂单总金额 | 按 `price` 求和 ÷100 转元 | `nft_sell_orders` |

**替代折线图的三种可视化**：
1. **藏品成交排行**（横向条形图）：5 个藏品按成交记录数排序，臻海蓝卡与八仙过海系列各自占多少，一眼可见。
2. **成交价区间分布**（柱状状态）：10 条成交记录的价格落在哪些区间。当前数据为103000-105100 分（即 1030-1051 元），集中在单一区间。
3. **用户活跃分布**（列表）：36 个用户按钱包余额区间分组，替代无法统计的 DAU。

**空态处理**：若某指标卡因依赖表为空（如提现相关），显示「依赖表 `wallet_transactions` 当前 0 行，本指标待数据积累后启用」，并明确不展示 0——因为「0 条流水」和「这个指标没做」是两回事。

#### 模块 B：用户实名审核（诚实降级）

**问题**：36 个用户中 35 个 `has_real_name=0` 且 `real_name`/`id_card` 全为空。审核列表 36 条，点进去 35 条是空的。这是最容易被当成 Bug 的模块。

**设计决策：定位从「审核流程」改为「实名状态台账 + 异常标记」。**

**实名状态列表**（首屏，四列）：

| 列 | 内容 |
|---|---|
| 用户 | 手机号（掩码）+ 用户ID |
| 实名状态 | 未实名 35 个/ 已实名 1 个（用状态标签区分，不用颜色区分） |
| 实名信息 | 未实名时显示「无材料」（灰色文字），已实名时显示掩码证件号 |
| 注册时间 / 最后登录 | 来自 `users.created_at` / `last_login_at` |

**详情页**：
- 未实名用户：明确显示「该用户未提交实名材料，无可审核内容」，并展示 `has_real_name=0` 的证据（空值截图式的空态区块），**而不是空白页**
- 已实名用户：正常展示，实名信息区块可见
- **新增能力**：支持运营/客服手动录入实名材料（姓名 + 证件号），录入后 `has_real_name=1`。这是当前数据下唯一能让该模块产生实际价值的动作。录入必须留痕，且证件号写入后立即掩码显示

**不做的事**：不做「审核通过/驳回」状态机（因为没有待审队列可审），不做批量实名导入。

#### 模块 C：二级市场监控

**问题**：`nft_market_apply_orders` 为 0 行，若做成含「寄售/求购/委托」三个 tab 的页面，其中 2 个 tab 全空。

**设计决策：不做三tab，做单一挂单列表 + 可选的空tab 标注。**

- 主列表基于 `nft_sell_orders`（10 条，有数据）
- 「求购」和「委托」tab保留但标注「该市场类型当前 0 条数据，源站暂无求购单」，委托 tab 实测有 10 条数据（`nft_market_trust_orders`），因此委托 tab **可展示**
- 因此最终形态：寄售 tab（10 条，实数据）、委托 tab（10 条，实数据）、求购 tab（0 条，空态标注）

**挂单列表字段**：挂单ID、藏品（名称 + 图）、NFT 编号（token）、卖家（用户ID）、挂单价（分→元，**注意单位**）、状态（在售 10 条）、操作（强制下架）

**金额单位强制约束**：所有金额字段展示前统一除以 100。`nft_sell_orders.price=500` 表示 5.00 元而非 500 元。这个坑必须在前端统一封装，架构师需要在设计文档中明确。

**异常价格预警设计**：两条规则并行。① **批量挂单**（同一卖家在售 ≥3）：臻海蓝卡 10 条挂单分属 3 个卖家，其中 2 个卖家分别持 5 条与 3 条 → **首日可命中 8 条**。② **异常低价**（挂单价 < 最近成交价 × 50%）：该 iid 挂单 500 分、成交 400 分，阈值 200 分 → **当前数据不命中**，属数据事实而非实现缺陷，详见 §17.5.5。

建议的默认规则（阈值可配置）：
- 单个挂单价 < 该藏品最近成交价 × 50% → 标记「疑似异常低价」
- 同一卖家短期内挂单数 ≥ 3 → 标记「疑似批量挂单」

当前数据下会命中「疑似异常低价」。这是好的——**功能上线第一天就有真实信号，说明监控有价值**，而不是空跑。

#### 模块 D：版权审核

**问题**：不是空表，但关联关系脆弱——6 条版权中 4 条在 `items` 表无同名藏品（含 2 条 name 为 `1` 的脏数据）。

**设计决策：把「关联诊断」作为队列的一等列，而不是让人工去查。**

**版权审核队列**：

| 列 | 内容 |
|---|---|
| 版权名称 | 显示 `name` 原值。name 为 `1` 或纯数字时，额外标红提示「名称为无效占位值」 |
| 版权图 | 缩略图 |
| 关联藏品 | 系统自动匹配结果：3 条显示匹配到的藏品名（臻海蓝卡、八仙过海·韩湘子、八仙过海·蓝采和），4 条显示「关联异常：未找到同名藏品」 |
| 排序 | `sort` 值 |
| 审核状态 | 待审核 / 已通过 / 已驳回 |
| 操作 | 通过 / 驳回（驳回必填理由） |

**关联匹配逻辑的已知缺陷（必须写明给架构师）**：
当前 `item_copyrights` 与 `items` 之间**没有外键**，唯一可能的连接是 `name = items.name` 字符串精确匹配。这机制脆弱：
- 「第1个版权」这类名称本就对不上
- 2 条 name 为 `1` 的记录匹配结果不确定
- 若藏品改名，关联即断裂

**产品侧建议**：本期接受这个脆弱性（因为只有 6 条数据，人工可核），但**必须做成配置项而非硬编码**——未来若要建真正的版权-藏品关联表，能改配置切换到新字段。同时页面上要明确告诉审核员「当前关联基于名称字符串匹配，可靠性有限」，避免审核员误以为系统已做了严格校验。

**与标准要求的对照**：团体标准第8.1.2 条 e) 要求「对数字藏品进行原创性审查，对可能存在侵权的作品做过滤和标识」。本期版权审核队列 + 标识功能可视为该要求的最小落地。完整版需要接入图像指纹比对，本期不具备条件。

#### 模块E：商品与藏品管理

**问题**：`items.content` 5个藏品中 4 个为空，详情页图文区是空的。

**设计决策**：详情页的图文区块为空态要明确写「该藏品未录入图文详情」，并给运营一个「去编辑」的直接入口。同时要展示「藏品内容完整度」指标（如「1/5 个藏品有图文详情」），让运营知道还有哪些没填。

**status 枚举脏数据处理**：
实测 5 个藏品有 3 种 status 值（`on` 2个、`sold_out` 1个、`1` 2个）。后台筛选器**必须同时识别 `on` 和 `1` 为「在售」**。筛选下拉选项固定为：全部 / 在售 / 已售罄 / 预热中 / 全部隐藏，并把实际出现的原始值作为副标展示（如「在售（含历史值：1）」）。

**作者信息展示**：5 个藏品全部能关联到作者（`item_authors` 2 条：臻海艺术、闹翻天）。详情页展示作者名 + 头像 + 简介 + 作品数。注意 `works_count` 字段值（臻海艺术 3、闹翻天 2）与实际藏品数（臻海艺术 1 个、闹翻天 4 个）**不一致**，展示时应以实时统计为准并提示字段偏差。

### 9.4 数据治理建议（不属MVP，但需架构师知晓）

以下脏数据建议在联调前或联调中由架构师评估处理，本PRD 不强制：

1. `items.status` 枚举统一（`1` → `on`）
2. `item_copyrights` 脏 name 清理（2 条 `1`、1 条「第1个版权」）
3. `items.content` 补齐或明确标注为空
4. `nfts.sell_status` 语义修正（当前存的是数字 `1`，但注释说是字符串枚举）
5. `item_authors.works_count` 与实际藏品数对齐
6. `nfts.sell_status` 与 `nft_sell_orders.status` 的一致性核对（10 个 nfts 标on_sale 且有对应挂单，但 6 个 nfts 为 none，需确认这 6 个是否真的未挂单）

## 十、非功能需求

| 类别 | 要求 | 优先级 |
|---|---|---|
| 性能 | 列表页首屏 < 2s（当前数据量极小，36/5/10 条，本可轻松达成）；看板聚合接口 p95 < 500ms | P0 |
| 权限安全 | **每个写接口服务端校验角色权限**；敏感字段（`id_card`/`real_name`）按角色脱敏；越权尝试记入审计日志 | P0 |
| 写操作隔离 | 所有运营写操作携带 `is_local_override` 标记，且**不得影响 C 端读取逻辑**——需在验收时专门回归C 端 58 页 | P0 |

## 十四、三大模块移动端信息架构（390px）

> **本章为 v1.1 新增。起因**：后台形态锁定为移动端（与 C 端一致），而 v1.0 第九章的模块设计（藏品 6 列、挂单 7 列、版权 6 列、实名台账 4 列）是**按 PC 宽表口径写的**，在 390px 视口下无法承载。本章按移动端重做 MVP 三模块的信息架构。
>
> **未重做的部分**：数据看板（P1）与版权审核（P1）不在本次 MVP 三模块内，其移动端形态在二期按本章同一套规则（14.1 视口预算 + 14.5 通用规则）推导，v1.0 §9.3 的业务结论仍然有效。

### 14.1 移动端视口预算（先算清楚能放多少东西）

以 **390×844 逻辑视口**为基准（示例基准，非实测设备型号）：

| 区域 | 高度 | 依据 |
|---|---|---|
| 顶部导航栏 | 44px | C 端 token `--nav-bar-height: 44px`（实测） |
| 搜索栏（常驻吸顶） | 44px | 移动端单行搜索标准高度 |
| 底部导航 | 约 79.6px | 沿用 C 端 `nb-tabbar` 规格 `4.78125rem`；390px 下 `html{font-size: calc(100vw / 23.4375)}` = 16.64px，故 4.78125 × 16.64 ≈ 79.6px（实测 token 推导） |
| **列表可视高度** | **约 676px** | 844 − 44 − 44 − 79.6 |

**卡片高度取 88px（设计取值，非实测）** → 首屏可见约 **7 张卡片**。真实数据量的落屏换算：

| 列表 | 实测行数 | 折算屏数（÷7 张/屏） | 是否需要分页 |
|---|---|---|---|
| 藏品 `items` | 5 | 0.7 屏 | 否 |
| NFT `nfts` | 16 | 2.3 屏 | 否 |
| 挂单 `nft_sell_orders` | 10 | 1.5 屏 | 否 |
| 委托 `nft_market_trust_orders` | 10 | 1.5 屏 | 否 |
| 成交 `nft_trade_logs` | 10 | 1.5 屏 | 否 |
| 用户 `users` | 36 | 5.1 屏 | 否（但**必须**有搜索） |

**结论：MVP 六个列表全部不分页，全量渲染 + 顶部计数条。** 理由：最大 36 条 = 5.1 屏滚动，仍在可接受范围；分页控件本身要吃掉 44px 高度（占可视高度 6.5%），为 36 条数据付这个代价不划算。

**分页启用阈值定在 50 条**：50 条 ≈ 7 屏滚动，超过后线性查找成本显著上升，需引入无限滚动（每页 20 条）。该阈值写入验收标准 AC-32，作为架构师的统一规则，不做逐模块判断。

> **v1.3 修订（本段阈值已变更，「六个列表全部不分页」的结论不变）**
>
> 双端化后，分页阈值由 50 条**下调为跨端统一 40 条**（原移动端 50 / 设计师 PC 25 两者取一，理由见 17.6 第 4 条与 17.6.1）。**关键结论：当前六个列表最大 36 条（users），≤40，因此「六个列表全部不分页」这一结论在双端下完全成立，无需为 PC 破例。**
>
> | 项 | v1.2 | v1.3 |
> |---|---|---|
> | 移动端阈值 | ≤50 不分页，>50 无限滚动（每页 20） | **≤40 不分页，>40 加载更多（每页 20）** |
> | 桌面端阈值 | 无（无分页） | **≤40 不分页，>40 页码（每页 25）** |
> | 跨端一致性 | — | **两端阈值相同，`total` 口径相同**（AC-51） |
>
> 修订后规则写入 **AC-51 / AC-52**，替代 AC-32 中的 50 条阈值；AC-32 的其余部分（「≤阈值不分页、不展示分页控件」）继续有效。

### 14.2 模块一：商品与藏品管理（`items` 5 / `nfts` 16 / `item_authors` 2）

#### 列表页：卡片流，每卡露 4 个主字段

卡片采用「左图右文」结构（缩略图 64×64，`--radius-sm: 6px`）：

| 位置 | 字段 | 说明 |
|---|---|---|
| 左侧 | 藏品缩略图 64×64 | 单一视觉锚点，帮助快速定位 |
| 右第 1 行 | **藏品名** | `--font-h3` 15px，单行截断显示省略号 |
| 右第 2 行 | **作者名** · **在售状态标签** | 作者取自 `item_authors`（2 条：臻海艺术、闹翻天）；状态用「文字 + 色块」双编码，不单靠颜色（WCAG） |
| 右第 3 行 | **一级价 ¥388.00** | `items.price` 单位为元，直接展示。副文案「二级最低 ¥1051.00」由 `secondary_low_price` 分转元 |
| 条件警示行 | 脏数据提示 | 仅命中时出现：未录入图文详情（5 个中 4 个命中）/ 状态值为历史脏值（`1`） |

**不露的字段下沉到哪里**（这是本轮重设计的核心）：

| 列表不露的字段 | 下沉位置 | 理由 |
|---|---|---|
| `items.content`（4/5 为空） | 详情 Tab 2「图文」 | 富文本，列表放不下；空态在详情页才说得清 |
| `cid` / 分类 / 库存 | 详情 Tab 1「概览」 | 低频查询字段 |
| `is_recommend` / `is_popular` | 详情 Tab 1「概览」（开关控件） | 写操作，需在详情页配合二次确认 |
| 关联 `nfts`（16 条中归属该藏品的部分） | 详情 Tab 3「持有」 | 一对多，列表塞不进 |
| `create_time` / `update_time` | 详情 Tab 1「概览」底部 | 低频 |
| 该对象的操作日志 | 详情 Tab 4「日志」 | 长列表 |

#### 详情页：4 个 Tab

**Tab 数量上限为什么是 4**——390px 减去左右各 16px 内边距 = 358px 可用宽。Vant `van-tabs`（示例，非指定）每个 Tab 左右内边距合计约 24px。按每 Tab 文案 2 个汉字（15px × 2 = 30px）计，单 Tab 占 54px，4 个 = 216px，富余；若 5 个 Tab 且文案 4 字（60 + 24 = 84px），5 × 84 = 420px > 358px，**溢出**。

> **硬规则（写入 AC-30）：详情页 Tab 数量上限 4 个，且每个 Tab 文案不超过 2 个汉字。** 超过用「概览内折叠区块」消化，不增加 Tab。

| Tab | 内容 |
|---|---|
| 1 概览 | 基础信息 + 作者 + 状态 + 价格 + 推荐标记开关 + 创建/更新时间 |
| 2 图文 | `content` 富文本；为空时显示「该藏品未录入图文详情」并给「去编辑」入口（v1.0 §9.3 模块 E 结论保留） |
| 3 持有 | 该藏品关联 `nfts` 列表（token 编号 / 持有人 / 挂单状态） |
| 4 日志 | 该对象的 `admin_operation_logs` |

#### 操作入口：单主操作 + 底部 ActionSheet

PC 后台习惯把 5~6 个操作按钮平铺在每行右侧。390px 下一行放不下任何一个按钮列。方案：

- **卡片右下角只保留 1 个主操作按钮**：藏品模块主操作 = **上/下架**（依据 5.1 画像：运营每日高频第 ② 项就是处理上下架）
- **次级操作收进卡片右上角「更多」竖三点图标**（44×44 触摸目标）→ 点击唤起 `van-action-sheet`（底部弹出层），内含：编辑图文详情 / 调整价格 / 推荐标记 / 查看操作日志 / 还原本地覆盖
- **高风险操作（下架、调价）走三步**：ActionSheet 选中 → `van-dialog` 二次确认（AC-16）→ 原因必填（AC-17）→ 管理员密码（AC-18）
- `viewer` 角色：不渲染主操作与「更多」入口。**由服务端 `permissions` 决定，不是前端隐藏**（AC-24）

#### 搜索与筛选

| 元素 | 移动端形态 |
|---|---|
| 搜索 | `van-search` **常驻吸顶**（44px）。理由：390px 下搜索框只有一行高度，收起再展开反而多一次点击，且会丢失当前列表位置。支持按藏品名 / 作者名模糊搜 |
| 筛选 | **收起为「筛选」胶囊按钮**，右侧红点显示已生效条件数。点击 → `van-popup position="bottom"` 底部弹层（`van-dropdown-menu` 的下拉形态在长列表里会挤压列表，不用） |
| 筛选项 | 状态（全部 / 在售 / 已售罄 / 预热 / 隐藏，**「在售」须同时识别 `on` 与 `1`**，见 v1.0 §9.3 模块 E）· 作者（臻海艺术 / 闹翻天，2 个）· 内容完整度（有图文 / 无图文） |
| 弹层底部 | 固定「重置」「确定」两个按钮（AC-27） |

### 14.3 模块二：二级市场监控（`nft_sell_orders` 10 / `nft_market_trust_orders` 10 / `nft_market_apply_orders` 0 / `nft_trade_logs` 10）

#### 顶部 4 个 Tab

寄售 10 / 委托 10 / 求购 0 / 成交 10（均 2 汉字，符合 Tab 硬规则）。

#### 挂单卡片：4 个主字段

| 行 | 内容 |
|---|---|

| 第 2 行 | 卖家（手机号掩码 `138****8888`） |

## 十五、外部参考采纳项验收标准（EARS 格式）

> 依据 `SINAN_REFERENCE_MAP.md`「二、可直接借鉴」共 7 条来源、拆解为 **13 项采纳条目**。每项落成 1 条可验收标准，编号 AC-16 ~ AC-28。
> EARS 格式：`While / When / If / Where` + `系统` + `必须 / 应该` + 行为。

| 编号 | 采纳项（来源） | EARS 验收标准 |
|---|---|---|
| **AC-16** | 高风险操作二次弹窗确认（第十章） | **When** 管理员触发任一被标记为高风险的写操作（藏品上下架、藏品调价、挂单强制下架、用户冻结/解冻），**系统必须**中断当前操作流并弹出二次确认层，且该确认层**必须**显式列出「操作对象 + 将发生的变更 + 变更后值」；**If** 管理员未点击确认，**系统必须**不执行任何写操作。**移动端形态**：确认层为全宽 `van-dialog`，**不得**使用 PC 风格的居中窄弹窗（390px 下窄弹窗内按钮易误触） |
| **AC-17** | 高风险操作强制填写原因（第十章） | **If** 管理员在二次确认层点击「确认」但原因输入框为空或少于 5 个字符，**系统必须**阻止提交，并在该字段下方以 `--color-danger`（`#ff4d4f`）标红提示「请填写操作原因（不少于 5 字）」；提交成功后，**原因必须**写入 `admin_operation_logs.reason` |
| **AC-18** | 高风险操作管理员密码二次验证（第十章） | **When** 高风险操作的二次确认被提交，**系统必须**要求二次输入当前管理员登录密码并在**服务端**校验；**If** 连续 3 次校验失败，**系统必须**终止本次操作并写入登录失败告警埋点。**说明**：采用密码而非短信验证码——源站无短信通道证据，不臆造 |
| **AC-19** | 手机号脱敏（3.7） | **While** 任意角色查看用户列表或用户详情，**系统必须**将手机号渲染为 `138****8888`（保留前 3 后 4，中间 4 位掩码）；**且脱敏必须在服务端返回前完成，不得仅在前端遮盖**（防止接口直连拿到原文） |
| **AC-20** | 姓名脱敏（3.7） | **While** 任意角色查看用户实名信息，**系统必须**将姓名渲染为 `张*`（保留姓氏，其余以 `*` 替代）；单字名渲染为「姓 + 1 个 `*`」。**If** `real_name` 为空字符串（当前 35 个用户为此状态），**系统必须**渲染为「未提交」，**不得**渲染为 `*` 或 `**`——否则会被误读为「有值但被遮住」 |
| **AC-21** | 身份证脱敏（3.7） | **While** 任意角色查看证件号，**系统必须**保留前 3 位与末 1 位、中间 14 位以 `*` 替代（18 位证件号），服务端下发前完成；**If** `id_card` 为空字符串，**系统必须**渲染为「未提交」 |
| **AC-22** | 脱敏值查看通道：二次密码 + 强制留痕（3.7） | **When** 具备权限的角色（`ops` / `support`）点击任一脱敏字段的「查看完整值」，**系统必须**先弹出管理员密码二次验证；验证通过后展示完整值，**且必须在 60 秒后自动重新掩码**；**且每一次查看必须**写入一条不可删除的审计记录（查看人、角色、时间、IP、被查看用户 ID、字段名）。**While** 当前角色为 `viewer`，**系统必须**不渲染「查看完整值」入口（服务端不返回原文，非前端隐藏） |
| **AC-23** | 审计日志全覆盖（3.9） | **When** 管理员执行任一写操作（新增 / 修改 / 删除 / 审批 / 还原 / 导出），**系统必须**在**同一事务内**向 `admin_operation_logs` 写入一条记录，包含：操作人 ID、操作人角色、操作时间、来源 IP、操作对象类型、对象 ID、变更字段名、前值、后值、`is_local_override` 标记、操作原因。**If** 上述任一字段缺失，**本次写操作必须**整体回滚并判定验收不通过。**Where** 写操作为批量，**系统必须**按对象逐条写日志，**不得**合并为一条 |
| **AC-24** | 权限下发与前端存储（第五章） | **When** 管理员登录成功，**系统必须**在同一次响应内返回该账号的 `menus` 与 `permissions` 全量清单；前端**必须**将其存入 Pinia（示例，非指定）并以此做按钮级与路由级校验。**前端必须不得**硬编码权限清单或角色判断 |
| **AC-25** | 401 / 403 / 409 统一处理语义（第五章 + 十二条） | **If** 任意接口返回 401，**系统必须**清除本地登录态并跳转登录页，且保留来源路由以便登录后回跳；**If** 返回 403，**系统必须**弹出越权提示层并记录 `admin_permission_denied` 埋点；**If** 返回 409（版本冲突 / 状态冲突），**系统必须**以对象当前真实状态刷新页面并提示「数据已被他人变更，请重新操作」，**不得**静默重试。**说明**：仅借鉴语义，本项目错误码与参考文档不同 |
| **AC-26** | 统一空状态插图（十一章 12） | **Where** 任一列表或详情区块无数据，**系统必须**复用同一空态组件（C 端已有 `src/components/UvEmpty.vue`）渲染，并按 §9.2 三类空态（功能未开放 / 筛选无结果 / 配置缺失）分别给出插图与文案。**系统必须不得**出现「暂无数据」四字了事 |
| **AC-27** | 列表搜索 + 分页 + 重置（十一章 18） | **When** 管理员打开任一带筛选的列表页，**系统必须**在筛选面板底部同时提供「重置」与「确定」；**When** 点击「重置」，**系统必须**将所有筛选项恢复默认并立即重新查询。**If** 单次查询返回条数 > 50，**系统必须**启用分页或无限滚动；**If** ≤ 50，**系统必须**一次性渲染且不展示分页控件 |
| **AC-28** | 风控异常标记思路（6.15） | **When** 某挂单满足异常规则（单挂单价 < 该藏品最近成交价 × 50%；或同一卖家在售挂单数 ≥ 3），**系统必须**在列表卡片与详情页标记「疑似异常低价」/「疑似批量挂单」，并展示**判定数值依据**（如「挂单价 ¥5.00，最近成交价 ¥5.00，占比 100%」）。**且判定阈值必须**可配置，**不得**硬编码。**Where** 当前数据，**规则上线首日必须能复现命中的是「疑似批量挂单」规则**：臻海蓝卡 iid=2109928427009183745 的 10 条挂单分属 3 个卖家，其中 uid 2110748099560517634 占 5 条、uid 2110254061781852161 占 3 条，均 ≥3 → **命中 2 个卖家共 8 条挂单**。**「疑似异常低价」规则在当前源站真实数据下不命中，且这是数据事实而非实现缺陷**：该 iid 挂单价 500 分、成交价 400 分，阈值 = 400 × 50% = 200 分，500 > 200 → 不命中（详见 §17.5.4 裁决） |

## 十六、移动端形态的副作用（必须让总监与架构师提前知道）

> **v1.3 状态标注**：本章 8 条副作用是**基于纯移动端形态**推导的。双端化后这 8 条在桌面端的状态逐条标注见 **附录 G**。本章原表格内容保留不改（S1~S8 的「为什么在移动端变难用」在移动端依然完全成立）。
>
> **重要**：S1~S8 的表述**不因双端化而失效**——它们描述的是移动端形态的固有问题，桌面端的改善是**另辟路径**，不是在移动端解决的问题。附录 G 中的「完全消解」指的是「用户在桌面端完成该任务不再困难」，移动端路径与缓解措施**依然全部保留**。

后台锁定移动端后，v1.0 里若干「按 PC 口径成立」的设计会**变差**。以下按严重程度排序，逐条给出缓解方案。

| 编号 | 变难用的功能 | 为什么在移动端变难用 | 缓解方案 |
|---|---|---|---|
| **S1** | **数据看板（P1，v1.0 §9.3 模块 A）** | 6 张指标卡 + 3 种可视化，在 PC 上是三栏并列，390px 下只能纵向堆叠，滚动 5 屏以上；且柱状图/条形图的坐标轴标签（如「103000–105100 分」）在 358px 可用宽内放不下 | 移动端看板**只保留指标卡 + 藏品成交排行（横向条形图最适应窄屏）**；「成交价区间分布」「用户活跃分布」降级为可跳转的列表入口。**这是本轮最需要做减法的一处** |
| **S2** | **用户详情「一个页面看完」（5.2 客服画像的核心诉求）** | 原设计是单屏聚合基本信息 + 实名 + 钱包 + NFT + 订单。移动端必须切 4 个 Tab 才能看完，客服处理申诉时会反复横跳 | Tab 1「概览」内加**关键摘要行**（余额 / 持有数 / 订单数），让 80% 的申诉在概览页就能定性；Tab 2/3 只承载明细 |
| **S3** | **版权审核的版权图与藏品图比对（v1.0 §9.3 模块 D）** | 审核员要同时看版权图与藏品图做人工比对。390px 下两图并排各只能给到约 150px，比对体验明显劣于 PC；且原 6 列（名称/图/关联藏品/sort/状态/操作）压到 4 字段后，必须砍掉 `sort` 与缩略图之一 | 保留版权图缩略图（64px）、砍掉 `sort` 列下沉到详情；详情页提供「并排比对」视图，双图上下排各占 358px 全宽。**若二期要做严格比对，建议该功能明确限定在桌面视口使用** |

| **S5** | **操作日志的多维检索与前后值对照（P2）** | 检索条件有 4 个（操作人 / 对象 / 时间 / 字段），手机上要 4 次底部弹层；「前值 → 后值」在 PC 上可左右并排对照，移动端只能上下排，长字段（如 `content` 富文本）几乎不可读 | 移动端只保留 2 个高频检索维度（操作人 + 时间区间），其余下沉为「高级检索」；前后值采用**字段级 diff 摘要**（如「价格：388.00 → 499.00」），**不展示整段富文本原文对比** |
| **S6** | **批量操作** | PC 上的多选 checkbox 列在移动端卡片流里没有位置（会挤掉一个主字段）。v1.0 已把「批量审核」列为 backlog，**移动端形态下它更远了** | 维持不做。用「筛选 + 全选当前筛选结果 + 单条确认」的替代路径消化，但需要总监确认是否接受 |
| **S7** | **金额与长文本录入（调价、填驳回理由）** | 价格录入要 ×100 换算（元 → 分），手机上数字键盘输错一个 0 就是 10 倍差——这正是 5.1 画像里运营「最怕」的场景；长文本（驳回理由）在小屏输入法下占用半屏 | 价格输入框**必须在下方实时回显换算结果**（输入 499 → 立即显示「= 49900 分 / ¥499.00」），提交前再确认一次；驳回理由改为「常用理由快捷选择 + 补充说明」，不强制长文本 |
| **S8** | **一屏看完列表的预期** | 按 14.1 测算，列表可视高度约 676px ≈ 7 张卡片。16 条 NFT 要滚 2.3 屏、36 个用户要滚 5.1 屏。**「打开列表一眼看全」在移动端不成立** | 用顶部计数条 + 吸顶搜索 + 已生效筛选条件红点来补偿；36 条用户列表**必须有搜索**，否则 5 屏滚动查找不可接受 |

## 十七、双端适配（v1.3 新增）

> **本章为 v1.3 新增。起因**：项目总监决策「后台要双端能用——PC 电脑和手机都要能正常用」，推翻 v1.1 的「纯移动端」单端形态。

>
> **本章的约束优先级高于第十四章**：当两者冲突时，第十四章中「仅移动端」性质的措辞按 17.6 的复核结论修订；第十四章中「工作记忆上限」「移动端触控物理限制」性质的约束（如详情页 Tab ≤4）在双端下**继续有效**。
>
> **本章的分工边界**：视觉与实现细节由 `RESPONSIVE.md`（设计师）与 `DESIGN_SYSTEM.md` 承载。本章只定义**业务语义、可用性边界、数据一致性硬约束、可验收行为**。

### 17.1 断点表

| 断点 | 视口宽 | 形态 | 一级导航 | 内容布局 | 内容宽上限 |
|---|---|---|---|---|---|
| **移动** | `< 768px` | 移动端 | 底部 TabBar（4 项，每项 ≤2 汉字） | 单列满宽，卡片流 | 满宽（设计基准 390px，兼容 320–428px） |
| **平板** | `768 ~ 1023px` | 平板 | **底部 TabBar 保留** | 单列居中 | 640px |
| **桌面** | `≥ 1024px` | 桌面 | **侧边 Rail 200px（可折叠 56px）** | 两栏：Rail + 主内容区 | 1440px 总宽 / 1216px 内容块 |

**平板不上 Rail 的论证（v1.3 修正数字）**

设计师原论证为「iPad 竖屏 820px 扣掉 200px Rail 只剩 364px，比移动端 390px 还窄」。**结论成立，但算术不成立**：820 − 200 = **620px**，不是 364px；620px 明显宽于移动端 390px。**修正后的论证**：

| 方案 | iPad 竖屏（CSS 宽 820px）下的内容区 | 代价 |
|---|---|---|
| 平板方案（底部 TabBar + 单列居中） | **640px**（内容宽上限） | 左右各余 90px 留白 |
| 桌面方案（Rail 200px + 两栏） | **620px**（820 − 200） | 内容区**反而窄 20px**，且多占用一个导航形态 |

即：在 820px 区间引入 Rail，**内容宽度净收益为负（−20px）**，同时让同一台设备在竖屏（TabBar）与横屏（≥1024 走 Rail）之间切换导航形态，认知成本上升。**故 768~1023px 不上 Rail。**

**断点归属的唯一真源**：断点值只允许从设计令牌 `--admin-bp-md` / `--admin-bp-lg` 读取，JS 侧 `matchMedia` 必须与 CSS 媒体查询同源；**不得**在组件里写裸断点数字（写入 AC-42）。

### 17.4 已知取舍（诚实记录）

#### 17.4.1 PC 看板首屏「看起来有点空」—— 这是故意留白，不是没做完

**事实**：桌面端总宽 1440px，内容块 1216px。看板首屏内容为 6 张指标卡（3 列两行）+ 2 张图表（2 列并排），在 1216px 内只占约 2/3，右侧有富余。

**这是设计决策，不是遗漏。** 理由已在 `RESPONSIVE.md` §5 给出，本 PRD 侧的业务判断见**附录 H（Q13 裁决）**。

**必须同时落地的两个配套动作**（否则「留白」会被读成「没做完」）：

| 动作 | 内容 | 优先级 |
|---|---|---|
| **A. 容器定宽，不硬撑** | 看板主容器在 `≥1024` 限宽至 **960px**（示例取值）并居中，而不是撑满 1216px 内容块。**同样是空白，960px 居中块四周的留白读作「页面边距」；1216px 内容块内空掉 400px 读作「漏了东西」**。这是纯布局决策，**不增加任何数据、不增加任何图形** | P0 |
| **B. 数据说明行** | 看板顶部固定一行说明当前样本量与解锁条件，文案示例：「当前样本：成交记录 10 条 / 挂单 10 条 / 用户 36 个；趋势折线需成交记录 ≥30 条后自动解锁」。**这是把「为什么这里没有更多图」讲清楚，不是装饰** | P0 |

**明确拒绝的做法**（会制造未完成感）：

| 拒绝项 | 拒绝理由 |
|---|---|
| 装饰性插图 / 抽象色块 / 占位插画 | 装饰不承载信息，且视觉上在暗示「这里本该有内容」 |
| 把 10 个成交点连成折线 | 违反 §9.3 与 AC-54 的样本量门槛；屏幕变宽让**假趋势更有说服力**，是负向改变 |
| 灰底「更多功能敬请期待」占位块 | **最糟的一种**。占位块明确告诉运营「这里该有东西但还没做」，直接制造「后台没做完」的判断 |
| 虚构的对比数据 / 示例数据填充 | 违反「禁止臆造数据」铁律 |

**后续路径**：看板右栏填入**真实待办聚合**（异常挂单 10 条、关联异常版权 3 条、未实名用户 35 个——均为实测值），这是「补真实数据维度」的正确解法。**但这是新增功能，列入 Backlog（P1），不进 MVP 第一期**；MVP 阶段只做 A + B。

### 17.5 数据一致性保证机制（硬约束）

> 这是本轮双端化的**核心风险点**。字段口径一旦两端漂移，在审核 / 审计场景是事故（同一件事在手机和 PC 上显示不同数字，运营会先怀疑系统而不是怀疑屏幕）。

#### 17.5.1 字段映射：PC 列必须是移动端 L1 ∪ L2 的子集

**唯一真源**：每个字段只在**一个**位置定义（详情页 DL 定义）。移动端 L1 槽位、L2 展开项、桌面表格列，三者都是**对该定义的引用**，**不得各自维护一份**。实现上抽到统一的字段定义模块（示例，非指定：字段定义文件），移动端投影出 L1/L2，桌面端投影出列。

**PC 表格列映射表**（列顺序固定；「来源」列标注该列在移动端的位置）

| 列表 | 桌面列（顺序固定） | 列数 | 移动端来源 |
|---|---|:--:|---|
| 藏品列表 | 藏品名 / 编号 / 状态 / 售价 / 库存 / 已售 / 作者 / 创建时间 | 8 | 名称+编号 = L1；售价 = L1 槽位 3；状态 = L1 标签；库存 / 已售 / 作者 / 创建时间 = L2 |
| 挂单监控 | 藏品+NFT 编号 / 挂单 ID / 挂单价 / 最近成交价 / 价差比 / 状态 / 挂单时间 | 7 | 名称+ID = L1；挂单价 = L1 槽位 3；状态 = L1 标签；最近成交价 / 价差比 / 挂单时间 = L2 |

**三条不可违反的规则**：

1. **无「只有 PC 能看到」的字段。** 桌面表格的每一列，在移动端 L1 或 L2 展开区**必须可达**（不等于「必须在首屏」）。
2. **无「只有移动端能看到」的字段。** 反向同样成立——移动端 L2 的字段在桌面详情页 DL 中必须可见。
3. **上表列清单不得单方面扩张。** 若要加列，必须先在移动端 L2 建立同名字段可达路径，再在桌面引用。**禁止**在桌面表格里直接加一个移动端不存在的列。

#### 17.5.2 派生列的数据来源必须声明（v1.3 新增，来自建表脚本核对）

上表中有 4 个列**不是单一表的原生字段**，必须由 JOIN / 派生计算得到。实现前必须明确来源，**否则会出现同一列在两端算法不同**：

| 列 | 列表 | 来源 | 口径要求 | 风险 |
|---|---|---|---|---|
| **最近成交价** | 挂单监控 | `nft_sell_orders.iid` → `nft_trade_logs.iid` 取 `sold_price` 最大且 `sold_time` 最新的一条 | 挂单无对应成交记录时显示「无成交记录」而非 0；**不得**用挂单自身 `price` 顶替 | 高：10 条挂单价均为 500 分，若错顶替则「价差比」恒为 0，异常低价预警（AC-28）在桌面端失效 |
| **价差比** | 挂单监控 | `(最近成交价 − 挂单价) ÷ 最近成交价` | 与 AC-28 的「占比」口径**必须互为补数**（价差比 = 1 − 占比）；臻海蓝卡实测占比 125% ⇒ 价差比 −25%（两者合计 100%） | 高：口径不统一会让同一数值在桌面端与移动端对不上，且负值不得被截断为 0 |
| **买家 / 卖家** | 成交记录 | `nft_trade_logs` **无买家/卖家字段**，须经 `nft_id` → `nfts.uid`（持有人）/ `nft_sell_orders.buyer_uid` 反查 | 反查不到时显示「—」并说明原因，**不得**臆造 | 中：v1.2 §14.3 已写「买卖双方（脱敏）」，桌面端必须复用同一反查与脱敏逻辑，不另写一套 |
| **审核状态 / 审核人 / 审核时间** | 版权队列 | `item_copyrights` **无审核字段**（仅有 id/name/image/image_url/sort/created_at/updated_at），须来自新建的审核记录表 | 审核记录表由架构师设计（v1.0 §6.4 故事 8 已要求「提交后生成一条审核记录」） | 高：若桌面端直接读 `item_copyrights` 的 `updated_at` 冒充审核时间，审核追溯链断裂 |
| **录入时间 / 录入人** | 实名台账 | `users` 无录入字段（`created_at` 是注册时间），须来自操作审计表（AC-23） | 录入时间 = 对应写操作的审计时间，**不得**用 `users.updated_at` 冒充 | 中：二者语义不同，冒充会让「何时录入实名」失真 |
| **库存 / 已售** | 藏品列表 | `items.issue_quantity`（发行总量）/ `items.buy_quantity`（已购）/ `items.nft_quantity`（已铸造）/ `items.trade_quantity`（成交数量） | **必须逐列锁定唯一字段**，不得由前端自行推导。「已售」取 `trade_quantity`，「库存」取 `issue_quantity`；二者不得与 `sell_quantity`（在售数量）混用 | 中：五个数量字段语义相近，取错列会让「已售」与「在售」互相矛盾 |

> **本表的用途**：这是**交给架构师的前置澄清清单**，不是技术方案。PRD 只锁定「这一列显示什么语义、数值必须与移动端一致」，具体 JOIN 与字段选型由架构师决定，但**必须满足上表的语义约束**。

#### 17.5.5 「AC-28 首日必须复现命中」与派生列口径的裁决（v1.4 新增，来自源站实抓复核）

**背景**：架构师在 Phase 1 提出 OPEN-06 ——「AC-28 当前无法复现」。经本轮对源站 `api.shengtai.cyou` 实抓复核，查出的根因**不是实现缺陷，而是两重数据事实**，且顺带发现 PRD 自身的一处口径错误。

##### 发现 1：本地种子丢失了「同 iid 挂单-成交配对」（已修复）

旧种子把挂单放在臻海蓝卡、成交放在韩湘子，两者分属不同藏品：

| 表 | 旧种子 iid | 数量 |
|---|---|---|
| `nft_sell_orders` | 2109928427009183745（臻海蓝卡） | 10 条 price=500 |
| `nft_trade_logs` | 2111310949005721602（韩湘子） | 10 条 soldPrice=103000~105100 |

后果：按 `iid` 关联反查，臻海蓝卡成交记录 = **0 条**，10 条挂单的「最近成交价」全为「无成交记录」，异常低价预警首日一条都命中不了。

源站实抓证实**两个 iid 都同时有挂单和成交**（快照已入库 `.cache/source-probe/sec-{sell,sold}-zhenhai.json`）：

| iid | 挂单 | 成交 |
|---|---|---|
| 2109928427009183745（臻海蓝卡） | 10 条 price=500 | 10 条 soldPrice=400 |
| 2111310949005721602（韩湘子） | 7~8 条 price=78800~150000 | 10 条 soldPrice=100000~101800 |

**已执行**：备份三表至 `.cache/db-backup/market-20261020-115741.sql`，按源站 2026-10-20 实抓快照重建 `nfts` / `nft_sell_orders` / `nft_trade_logs`，本地接口输出与源站快照**逐字段相等**（挂单 10 条 × 6 字段、成交 10 条 × 4 字段）。种子文件 `database/seed_market_data.sql` 已同步，150 项字段级校验通过，E2E 38/38、58 页巡检 58/58 通过。

**遗留边界（诚实记录，不臆造）**：成交记录的 10 个 `nft_id` 在 `nfts` 表无对应行 —— 源站 `sold` 接口只返回 5 字段（`nftId`/`token`/`soldPrice`/`soldTime`/`chainId`），不含持有人 `uid`，而 `nft/info` 需鉴权才可取。按「禁止臆造数据」原则不补造 `uid`；后台「买家/卖家」列反查不到时显示「—」并说明原因（17.5.2 已预设该行为）。

##### 发现 2：「异常低价」规则在源站真实数据下不命中 —— 这是数据事实，不是实现缺陷

修复配对后用真实数值验算：

| 规则 | 判定式 | 代入臻海蓝卡 | 结果 |
|---|---|---|---|
| 规则 A 异常低价 | 挂单价 < 最近成交价 × 50% | 阈值 = 400 × 50% = **200 分**；挂单价 **500 分** | 500 > 200 → **不命中** |
| 规则 B 批量挂单 | 同一卖家在售挂单数 ≥ 3 | uid 2110748099560517634 **5 条**、uid 2110254061781852161 **3 条** | **命中 2 个卖家共 8 条** |

**裁决**：
1. AC-28 的「上线首日必须能复现命中」**改由规则 B 承担并已实证命中**；规则 A 保留实现、阈值可配置，但在当前数据下不命中。
2. **不为了迁就验收标准去造低价挂单数据**。规则 A 的价值在于阈值可配 —— 当运营把阈值从 50% 调到 150% 时，500 > 600 不成立即会命中；这已由「阈值可配置」这一硬约束覆盖，无需改数据。
3. 派生列「价差比」在此数据下为 **−25%**（(400−500)÷400），与规则 A 的「占比」口径 125% 互为补数（合计 100%），两列口径自洽（AC-48 ②）。

##### 发现 3：PRD 原文的 0.48% 示例是跨藏品错配，必须废止

AC-28 原文与 §9.3 曾写「挂单价 ¥5.00，最近成交价 ¥1051.00，占比 0.48%」，并据此论证「0.48% 仍明确命中」。该示例的算式是：

```
500 ÷ 105100 = 0.4757% ≈ 0.48%
```

其中 500 是**臻海蓝卡的挂单价**，105100 是**韩湘子的成交价** —— **两个不同藏品的数字相除**，不构成任何真实藏品的价差。同 iid 配对后，臻海蓝卡的真实占比是 **125%**。

**该示例已从 AC-28 与相关章节废止**，并同步更正 Q9 运营文案（原写「1/20」，实为 0.48% 且本身不成立，现改为按实际阈值动态表述）。这与 `docs/admin/PRICE_UNIT_AUDIT.md` 中「文档被占位符污染」是同一类错误的另一个实例：**PRD 里的示例数字同样需要证据链，不能凭算感写**。

### 17.6 设计师 9 条处置结论的业务侧复核

> 逐条复核设计师对 PM 移动端硬约束的处置。**结论列**：认同 / 认同但需补充前置条件 / **不认同**。

#### 第 1 条：详情页 Tab ≤4 且 ≤2 汉字 → 详情页不变，一级导航放宽 ≤6 / 4 汉字

**结论：认同。**

工作记忆上限与屏宽无关，放宽会让「一眼看完分层」失效——PC 上同样找不到第 5 个 Tab。**但补充一条**：桌面 Rail 的 ≤6 项是**上限**不是目标，Rail 项数应为**角色相关**（`reviewer` 不渲染「用户」→ 腾出位置给「版权」）。移动端 TabBar 4 项在**所有角色下恒定**（工作台 / 藏品 / 市场 / 用户），角色差异通过**页面内模块**体现，不通过一级导航项数体现。写入 AC-43。

#### 第 2 条：首屏 3~4 字段 → 桌面放宽 4~8 列，且 PC 列必须是移动端 L1+L2 的子集

**结论：认同，并已升格为硬约束（写入 AC-45 / AC-46 / AC-47）+ 补齐派生列来源（17.5.2）。**

补充：8 列上限的依据成立（1216px ÷ 平均 150px ≈ 8 列），超过 8 列需要横向滚动，会让「一屏扫完一行所有字段」失效——而这正是 PC 表格的核心价值。**但 8 列是桌面专属密度，移动端 L1 仍为 ≤4 主字段**（AC-29 不变）。

#### 第 3 条：操作按钮不放行尾 → 桌面放开，行尾 ≤2 文字 + 1「更多」，高危操作仍不放行尾

**结论：认同。**

移动端禁行尾的理由是「按钮被挤到 <80px，误触率高」——该理由在指针环境不成立。**但高危操作（强制下架 / 冻结 / 驳回）不放行尾这一条必须坚持**：PC 误触概率虽低，**误冻结一个用户的后果与移动端完全相同**，键盘鼠标不会让后果变轻。

#### 第 4 条：六个列表不分页（阈值 50）→ 桌面阈值降到 25

**结论：不认同。修正为：阈值跨端统一为 40，桌面在 >40 时才启用页码。**

**详细论证见 17.6.1（总监点名要求回答的问题）。**

#### 第 5 条：成交记录横向滚动表 → 桌面撤销，恢复 6 列正常表格

**结论：认同结论，但需修正表述范围。**

不是「PC 撤销横向滚动表」，而是「**全端取消横向滚动表**」——`RESPONSIVE.md` §2.2 里「`<768` 成交记录为横向滚动表」与已验收的 **AC-29** 直接冲突，v1.1 §14.3 已经把成交记录改成 4 主字段卡片流。**本 PRD 裁决以 AC-29 为准，设计师文档 §2.2 需同步修订。**（见 17.2.2）

#### 第 6 条：看板 PC 恢复 tooltip、图表 2 列并排、指标 3~4 列；折线图两端同锁（数据点 ≥30）

**结论：完全认同，且认为这是设计师 9 条里最重要的一条。**

理由不只是「屏幕变宽不增加数据点」，而是**屏幕变宽让假趋势更有说服力**——一个 10 点的折线画在 260px 高的卡片里、配 hover tooltip 读数，观者会做因果推断，这是用更强的视觉说服力包装更弱的数据。**「看板的信息量上限由数据决定，不由断点决定」这一句应写进 PRD 正文作为原则**（已写入 17.4.1 与 AC-54）。

**补充一条门槛细则**：`users` 36 条虽满足「数据点 ≥30」的字面门槛，但「用户活跃分布」的分组数远小于 30，**样本量门槛按「实际绘制的数据点数」判定，不按表行数判定**。即：折线图的数据点数 = 该图实际绘制的点数，≥30 才解锁。

#### 第 7 条：筛选收进右侧抽屉 → 桌面改顶部横排条（搜索 320px + ≤4 chip 直显 + 360px 下拉）

**结论：认同，并补充一条 v1.2 对齐说明。**

v1.2 的 AC-33 规定**移动端**筛选为**底部弹层**（`van-popup position="bottom"`）；`RESPONSIVE.md` §4.9 与 §2.3 写作「移动端右侧抽屉」。**二者不一致，本 PRD 以 AC-33 为准（底部弹层）**，理由：移动端搜索栏常驻吸顶、筛选收起为胶囊按钮，底部弹层与 TabBar 在同侧拇指区，且「重置/确定」固定在弹层底部更符合移动端惯例。**设计师文档 §4.9 / §2.3 需同步修订为「底部弹层」。**

「≤4 chip 直显」的依据成立（4 × 100px + 搜索 320px + 间距 ≈ 760px，在 1216px 内余量充足）。**但需补一条**：桌面筛选字段 ≤6 且均为枚举时用下拉；含日期区间 / 多选 / 需输入时仍用抽屉（宽 360px 固定）——**不是所有筛选都能塞进下拉**。筛选 chip 生效后显示已选数量角标，**两端筛选语义完全一致**。

#### 第 8 条：批量操作 → 双端都不做（理由从「PC 放不下」改为「权限矩阵 + 部分失败语义」）

**结论：认同，并补第三条理由。**

- **理由一（保留 Q12 原裁决）**：真实数据量否定需求本身——`items` 5 / `nft_sell_orders` 10 / `nft_trade_logs` 10 / `users` 36，逐个点击的操作成本**低于**筛选 → 全选 → 批量确认的交互成本。
- **理由二（设计师新增，成立）**：权限模型 + 审计粒度 + **部分失败语义**（三条里两条成功怎么办）三条同时做才完整，MVP 阶段做一半比不做更危险。AC-23 要求批量写操作**按对象逐条写日志**，未做部分失败语义时无法满足 AC-23。
- **理由三（本 PRD 补充，成立且与端无关）**：**语义歧义**。桌面端「全选」的天然语义是「全选当前页」，而业务想要的是「全选当前筛选结果」——两者在 PC 上极易混淆。批量操作若上线而语义未做对，误操作范围会被静默放大，且**误操作对象可能远超当前视野**。这条风险在 PC 上比移动端更高。

**替代路径**：双端统一为「筛选 + 排序 + 搜索 → 逐条处理」。**不引入「全选」控件**——没有批量操作时，全选控件是纯负担。数据量增长到 `users > 500` 时再评估（与 Q12 裁决口径一致）。

#### 第 9 条：导出 ≥768 可见 → 保持，≥1024 增加「导出全部 + 字段选择」

**结论：认同，与 Q11 裁决一致。**

**补充一条约束**：桌面「选择导出字段」的可选范围**必须等于桌面表格可见列**（≤8 列，见 17.5.1），且这 8 列都是移动端 L1 ∪ L2 的子集——**导出的 CSV 因此也不会出现「只有 PC 能看到」的字段**，一致性机制延伸到导出通道。写入 AC-53。

#### 17.6.1 分页阈值 25 vs 不分页：PM 的判断（总监点名要求回答）

**问题**：users 36 条，桌面阈值 25 → 2 页（25 + 11）。上轮结论是「六个列表全不分页」。PC 上「不分页」是否反而更好用？

**PM 的判断：在 PC 上，「不分页」对当前 36 条数据确实更好用。阈值应修正为跨端统一 40，而不是 25。**

**第一步：把「一屏多少行」算清楚（这是阈值争议的真正分歧点）**

设计文档说「PC 一屏约 20 行」，但未给推导。按桌面端实测的表格行高口径推：

| 项 | 取值 | 说明 |
|---|---|---|
| 桌面视口高 | 900px | **示例基准**（常见桌面分辨率，非实测设备） |
| 减：顶栏 | 48px | 设计取值 |
| 减：筛选条 | 48px | 设计取值 |
| 减：表头 | 40px | 设计取值 |
| **= 内容可视高** | **764px** | |
| 表格行高（常规档） | 44px | 设计取值（与 14.1 的 88px 卡片高同源，密集档） |
| **= 一屏行数** | **17 行** | 764 ÷ 44 ≈ 17.4 |
| 表格行高（紧凑档） | 36px | 设计取值 |
| **= 一屏行数** | **21 行** | 764 ÷ 36 ≈ 21.2 |

**结论：PC 一屏是 17~21 行，不是固定 20 行。**

**第二步：三条路径的实际体验对比（users 36 条）**

| 方案 | 页数 | 运营实际动作 | 评价 |
|---|---|---|---|
| **A. 阈值 25（设计师方案）** | 2 页（25 + 11） | 滚到底 → 点「下一页」→ 重新从表头扫 11 行 → 若要找第 30 条需滚回再翻 | **末页只有 11 行（≈半屏）**，页面底部一片空白，运营会怀疑「是不是还有数据没加载出来」——**这与 §9.2「区分真的没有数据和功能没做完」是同一类错误** |
| **B. 阈值 40（本 PRD 修正方案）** | 1 页 | 滚 1.7~2.1 屏到底 | 桌面端有原生滚动条、浏览器 Ctrl+F 查找、可点列头排序，**定位成本远低于移动端**；36 条一次全部呈现，无需「还有别的页吗」的心智负担 |
| **C. 阈值 50（v1.2 原结论，仅移动端）** | 1 页 | 同 B | 与 B 在当前数据下**行为完全相同**（36 ≤ 40） |

**第三步：为什么阈值应是 40 而不是 25**

设计师的推导是「PC 一屏约 20 行，25 条 = 1.25 屏，固定 50 是 2.5 屏」。**这个推导的方法论是对的**（阈值应随一屏行数缩放），**但落点错了**：

- 1.25 屏就分页是**过度分页**。分页的收益是「降低单次查找的滚动成本」，1.25 屏的滚动成本本来就极低（一次滚轮到底），分页反而**增加了**动作（点击 + 重新扫视表头 + 找回位置）。
- 阈值真正的边界是「**滚动到第几行时我开始记不住位置**」。按一屏 17~21 行算，**2 屏（34~42 条）是记忆边界**，取 **40** 为保守值。超过 2 屏才分页。
- 移动端取 50 是因为移动端**没有**原生滚动条、没有 Ctrl+F、滚动位置极难找回，所以记忆边界更宽（7 屏）。**PC 端应更早分页，但不是早到 1.25 屏。**

**第四步：为什么必须「跨端统一」而不是「各端一个阈值」**

若桌面 25、移动 50，则 `users` 36 条在 PC 上分 2 页、在手机上 1 页全出。**运营会先怀疑系统数据不一致，而不是怀疑屏幕。** 这是 §17.5「口径漂移在审核场景是事故」的同类问题，只是发生在「分页与否」而不是「字段」上。

**统一为 40 后**：36 ≤ 40 → **六个列表在双端下全部不分页**（items 5 / nfts 16 / 挂单 10 / 委托 10 / 成交 10 / users 36，全部 ≤40）。**当前真实数据下双端行为完全一致，阈值差异只在未来数据增长时才显现。**

**第五步：给总监的退路（如果坚持 25）**

若总监仍要 25，PM 接受，但必须同时满足两条护栏，否则末页 11 行的空白会被读成数据缺失：

1. 页码控件**常驻可见**（不随列表滚动消失），并**始终显示「共 36 条 / 第 2 页 · 11 条」**；
2. 末页行数 < 一屏行数的一半时，列表底部**必须**显示「已显示全部 36 条」的终止态说明（复用移动端「已全部加载 N 条」的语义，AC-51）。

**第六步：分页真正该被触发的时点**

阈值只是兜底。**更有效的是给「数量敏感列表」设预警线**：`users` 是唯一一个会增长的列表（当前 36）。建议在 `users > 100` 时由运营侧提出分页需求评审（此时 40 阈值自然触发分页），**而不是提前把阈值压到 25 让每个列表都背上分页控件**。

**PM 结论一句话**：**PC 上「不分页」更好用；阈值应跨端统一为 40 而非 25。当前 36 条数据下，40 与 50 的实际行为一致——**「六个列表全不分页」这个 v1.2 结论**在双端下依然成立**，不需要为 PC 破例。**

## 十八、双端验收标准（AC-42 ~ AC-58）

> 接在 AC-41 后，编号连续。EARS 格式沿用第十五章约定：`While / When / If / Where` + `系统` + `必须 / 应该` + 行为。
> **本章 17 条**，与第十四 / 十五 / 十八章合计 **58 条**验收标准。

| 编号 | 验收点 | EARS 验收标准 |
|---|---|---|
| **AC-42** | 三断点布局与导航形态 | **Where** 视口宽度 < 768px，**系统必须**渲染底部 TabBar 主导航（4 项，每项 ≤2 汉字）且**必须不**渲染侧边 Rail；**Where** 视口宽度在 768~1023px，**系统必须**渲染底部 TabBar 且**必须不**渲染 Rail，内容区单列居中、宽上限 640px；**Where** 视口宽度 ≥1024px，**系统必须**渲染侧边 Rail（展开 200px / 折叠 56px）且**必须不**渲染底部 TabBar，主内容区呈两栏。**所有断点判定必须**只读取设计令牌 `--admin-bp-md` / `--admin-bp-lg`（或与 CSS 媒体查询同源的 JS 常量），**必须不得**在组件中写裸断点数字。**且**断点归属必须为：768px 归入平板区间、1023px 归入平板区间、1024px 归入桌面区间 |
| **AC-43** | 导航形态切换的实现方式与项数约束 | **When** 视口跨越断点，**系统必须**通过**组件级条件渲染**切换导航形态，**必须不得**仅用 CSS `display:none` 隐藏导航（隐藏的组件仍会加载图标与占位，导致折叠态 Rail 项占位与桌面图标重叠）。**Where** 桌面 Rail，**系统必须**将 Rail 项数控制在 ≤6 且每项文案 ≤4 汉字，**且必须**按当前登录角色裁剪 Rail 项（`reviewer` 不得渲染「用户」类入口）。**Where** 移动端 TabBar，**系统必须**在所有角色下恒定渲染 4 项 |
| **AC-44** | 平板区间不得上 Rail | **Where** 视口宽度在 768~1023px，**系统必须**保持单列布局且**必须不**渲染任何侧边导航条；**系统必须不得**因加载 Rail 组件而在内容区左侧保留空白占位。**说明**：该区间内引入 200px Rail 会使 iPad 竖屏（CSS 宽 820px）的内容区从 640px **缩至** 620px，净收益为负（v1.3 §17.1 修正论证） |
| **AC-45** | 桌面列 ⊆ 移动端可达字段（正向子集约束） | **Where** 视口宽度 ≥1024px，**系统必须**以表格渲染列表，**且**表格中出现的**每一个**列，**必须**在移动端对应列表的 **L1 主字段或 L2 展开项**中存在同名字段定义。**If** 某列在移动端 L1 ∪ L2 中无对应字段，**系统必须**在构建期报错并**禁止**该列上线。**系统必须不得**出现「只有 PC 能看到」的字段 |
| **AC-46** | 移动端字段在桌面端亦可达（反向约束） | **Where** 视口宽度 <768px，**系统必须**在 L2 展开区暴露移动端列表的全部 L2 字段；**Where** 视口宽度 ≥1024px，**系统必须**在同一对象的详情页 DL 定义区展示与移动端 L2 同名的全部字段。**两端字段集合必须**互为可达，**必须不得**出现单端独有字段 |
| **AC-47** | 字段定义单一真源 | **系统必须**将列表字段定义维护在**唯一一处**（统一字段定义模块，示例，非指定），移动端 L1 槽位、移动端 L2 展开项、桌面表格列**必须**均从该定义投影生成；**系统必须不得**在列表组件、表格组件、详情组件中各自维护一份字段清单。**If** 同一字段在两处出现不同格式化逻辑（如金额换算、时间格式化），**系统必须**判定验收不通过 |
| **AC-48** | 派生列口径与来源声明 | **Where** 桌面端渲染「最近成交价 / 价差比 / 买家 / 卖家 / 审核状态 / 审核人 / 审核时间 / 录入时间 / 录入人 / 库存 / 已售」列，**系统必须**按 v1.3 §17.5.2 声明的来源与口径计算。**Specifically**：①「最近成交价」取同 `iid` 的 `nft_trade_logs` 中 `sold_time` 最新一条的 `sold_price`，无对应成交记录时**必须**显示「无成交记录」，**必须不得**以挂单自身 `price` 顶替；②「价差比」= (最近成交价 − 挂单价) ÷ 最近成交价，**必须**与 AC-28 的「占比」口径互为补数；③「买家 / 卖家」**必须**复用移动端同一套反查与脱敏逻辑；④「审核状态 / 审核人 / 审核时间」**必须**取自审核记录表，**必须不得**以 `item_copyrights.updated_at` 冒充审核时间；⑤「录入时间 / 录入人」**必须**取自操作审计记录，**必须不得**以 `users.updated_at` 冒充；⑥「已售」取 `items.trade_quantity`、「库存」取 `items.issue_quantity`，**必须不得**与 `sell_quantity` 混用。**If** 任一列在移动端与桌面端显示不同数值，**系统必须**判定验收不通过 |
| **AC-49** | 断点切换保留筛选条件 | **When** 管理员已设置任一筛选条件（搜索词 / 状态 / 实名状态 / 异常标记等）后视口跨越断点，**系统必须**保留全部筛选条件与已生效筛选 chip，**系统必须不得**重置为默认值。**两端筛选语义必须**完全一致（同一条件在移动端与桌面端筛出相同结果集） |
| **AC-50** | 断点切换保留滚动位置与展开状态 | **When** 视口跨越断点且管理员当前处于列表页，**系统必须**保留：① 列表滚动位置（按列表标识 + 筛选条件记存）；② 已展开的 Accordion / L2 展开项的展开状态；③ 详情页当前选中的 Tab；④ 已填但未提交的表单草稿。**If** 任一项在切换后丢失，**系统必须**判定验收不通过 |
| **AC-51** | 分页阈值跨端统一 | **If** 列表查询结果 ≤40 条，**系统必须**在全部三个断点一次性全量渲染并显示顶部计数条，**必须不得**展示任何分页控件；**If** >40 条，**系统必须**在移动端（<768px）启用加载更多（游标式，每页 20），在桌面端（≥1024px）启用页码（offset 式，每页 25）并显示「共 N 条 / 第 X 页」。**两端必须**返回同一 `total` 口径；**Where** 移动端已加载全部，**系统必须**显示「已全部加载 N 条」终止态，**该 N 必须**等于桌面端 `total` |
| **AC-52** | 分页尾部与总数的可见性 | **Where** 列表启用分页，**系统必须**常驻显示总条数与当前页区间（示例：「共 36 条 / 第 2 页 · 11 条」），**必须不得**让分页控件随列表滚动消失。**If** 末页行数 < 一屏可见行数的一半，**系统必须**在列表底部显示「已显示全部 N 条」的终止态说明，**必须不得**以空白区域暗示数据缺失 |
| **AC-53** | 导出入口的断点可见性与字段范围 | **Where** 视口宽度 <768px，**系统必须不**渲染任何导出入口（Q11 裁决）；**Where** 768~1023px，**系统必须**渲染「导出当前筛选结果」入口；**Where** ≥1024px，**系统必须**在同一导出按钮的下拉中额外提供「导出全部结果」与「选择导出字段」。**「导出全部结果」的导出范围必须**为全部筛选结果而非当前页；**「选择导出字段」的可选字段集必须**等于桌面表格可见列（≤8 列），**必须不得**包含移动端 L1 ∪ L2 之外的字段；**导出动作必须**记入操作日志（含导出人、时间、数据区间、行数、字段集） |
| **AC-54** | 折线图样本量门槛两端同锁 | **When** 渲染任何时间序列折线图，**系统必须**先判定该图**实际绘制的数据点数** ≥30；**If** <30，**系统必须**降级为指标卡 + 分布可视化（横向条形 / 柱状 / 列表），**且**该降级规则**必须**在移动端与桌面端**完全一致**（同一判定逻辑、同一数据源，**必须不得**存在端侧差异）。**Where** 成交记录当前实测 10 条，**系统必须**在两端均不渲染成交额折线图。**系统必须不得**以装饰图形、占位块或 10 点连线替代 |
| **AC-55** | PC 看板留白的处置 | **Where** 视口宽度 ≥1024px 且页面为数据看板，**系统必须**将看板主容器限宽至 960px（示例取值）并居中，**必须不得**硬撑满 1216px 内容块；**且必须**在看板顶部渲染一行数据说明，载明当前样本量与折线解锁条件（示例：「当前样本：成交记录 10 条 / 挂单 10 条 / 用户 36 个；趋势折线需成交记录 ≥30 条后自动解锁」）。**系统必须不得**在该页面渲染装饰性插图、抽象色块、占位插画、「更多功能敬请期待」占位块或任何虚构数据 |
| **AC-56** | 高危操作在两端强度一致 | **When** 管理员在任一断点触发高危操作（藏品上下架 / 藏品调价 / 挂单强制下架 / 用户冻结解冻 / 版权驳回），**系统必须**执行完整三步确认：① 二次确认层（列明操作对象 + 将发生的变更 + 变更后值）② 原因必填（≥5 字符，AC-17）③ 管理员密码服务端校验（AC-18）。**Where** 视口宽度 ≥1024px，**系统必须**将高危操作入口置于行尾「更多」菜单内，**必须不得**以行尾独立按钮形式呈现。**系统必须不得**因指针环境而减少任何一步确认 |
| **AC-57** | 成交记录全端无横向滚动 | **Where** 视口宽度 <1024px，**系统必须**以卡片流渲染成交记录（4 主字段：藏品名 / 成交价 / 买卖双方（脱敏）/ 成交时间），**必须不得**渲染横向滚动表格；**Where** 视口宽度 ≥1024px，**系统必须**以 6 列表格渲染（成交 ID / 藏品名 / 买家 / 卖家 / 成交价 / 成交时间），**必须不得**出现横向滚动条。**系统必须不得**在任一断点保留冻结首列机制 |
| **AC-58** | 移动端零回归 | **Where** 视口宽度 <768px，**系统必须**保持与 v1.2 一致的渲染结果（回归基线 = v1.2 验收截图）；**所有**新增桌面端令牌与媒体查询**必须**仅在 ≥768px 或 ≥1024px 生效，**必须不得**影响 <768px 的任何布局、字号、间距与组件形态。**If** 任一 <768px 页面出现渲染差异，**系统必须**判定验收不通过 |

### 附录 F：Q11 / Q12 裁决依据

**Q11 —— 移动端不提供导出**

采纳 PM 建议。三条依据：
1. 「导出做外部分析」是 `viewer` 角色的核心诉求（PRD 5.3），但手机下载完无法分析，
   提供入口等于**假交付**——比不提供更糟，因为它制造了"功能已支持"的错觉。
2. PM 提出的备选「生成文件后回传下载链接」，所需的回传通道当前不存在。
   按**「禁止臆造数据」**铁律，不得为不存在的通道设计功能。
3. 桌面视口 ≥768px 保留入口，回应了真实诉求，成本极低。

**Q12 —— 批量操作移出 MVP**

不采纳替代路径，直接移出 MVP。理由是**真实数据量否定了需求本身**：
`items` 5 条、`nft_sell_orders` 10 条、`nft_trade_logs` 10 条、`users` 36 条。
在这个量级下，运营逐个点击的操作成本**低于**筛选→全选→批量确认的交互成本，
批量操作是为不存在的问题找答案。数据量增长到 `users > 500` 时再评估。

> **v1.3 补充**：双端化后 Q12 裁决**维持不变**（双端都不做批量操作）。理由由「PC 放不下」升级为三条同时成立的理由（数据量 / 权限矩阵与部分失败语义 / 全选语义歧义），详见 17.6 第 8 条。**唯一变化**：桌面端替代路径中**不引入「全选」控件**——没有批量操作时，全选是纯负担。

**汇总**：**完全消解 4 条**（S2 / S3 / S5 / S8）、**部分消解 2 条**（S1 / S7）、**不消解或放弃 2 条**（S4 本就成立 / S6 双端放弃）。

> **一句话原则（v1.3）**：**双端化不是把移动端的问题在 PC 上重做一遍，而是让同一个任务在 PC 上有一条更宽的路。移动端的每一条限制与缓解措施都原样保留——「PC 能做」不是「手机可以不守规矩」的理由。**

### 附录 H：Q13 裁决 —— PC 看板留白（v1.3 新增）

| 编号 | 问题 | 状态 |
|---|---|---|
| **Q13** | PC 端看板首屏 1440px 宽但内容只占中间一部分，运营会不会觉得「这后台没做完」？如果会，有不违反「数据决定信息量」的解法吗？ | **已裁决（2026-10-21，PM 提出、总监确认原则）** |

#### H.1 业务侧判断

**结论：会有这个感知，但感知来源不是「空」，是「空得没有解释」。这两者的解法完全不同。**

先说判断本身：**会。** 理由是运营的第一印象形成于前 3 秒，而前 3 秒的认知路径是——

1. 看到 1440px 的宽屏后台（预期：这是一个信息密度高的专业系统）；
2. 看到中间一块内容（预期：这块内容应该铺开或至少填满一屏）；
3. 看到右侧有空白；
4. **推断：「右边那部分功能还没做」。**

**关键在于第 4 步的推断方向。** 人对空白的默认解释是「缺失」，不是「克制」。要让运营不产生这个推断，必须让他**在看到空白的同一秒就拿到「为什么空」的信息**——而不是让他自己猜。

**但这里要区分两种空白，它们性质完全不同：**

| 类型 | 形态 | 运营的解读 | 是否可接受 |
|---|---|---|---|
| **容器内空白** | 1216px 内容块内只有 720px 有内容，右侧 400px 空 | 「这功能没做完」 | **不可接受**——它伪装成「本来该有内容」 |
| **页面外留白** | 960px 居中内容块 + 两侧对称留白 | 「这是个窄版布局，正常」 | **可接受**——留白读作「页面边距」 |

**这是本裁决的核心，也是最省成本的解法**：同样是空白，**把它从「内容块内部」挪到「页面外部」，运营的解读就从「没做完」变成「正常排版」。** 而这一步**不增加一个字节的数据、不增加一个图形**，纯布局决策。

#### H.2 采纳设计师的主张

| 主张 | PM 判断 |
|---|---|
| PC 端不设专属三栏版，与移动端共用同一套降级可视化 | **采纳**。设专属版 = 两套信息定义 = 必然漂移，违反 17.5 的单一真源原则 |
| 不加折线，直到数据量到位 | **采纳**。屏幕变宽让假趋势**更有说服力**，是负向改变（17.6 第 6 条） |
| 「若要求填满，正确答案是补真实数据维度，不是加装饰图形」 | **采纳**，并作为 Q13 的原则写入 17.4.1 与 AC-55 |
| 折线门槛两端同锁，不做端侧差异 | **采纳**（AC-54） |

#### H.3 四条解法（按优先级，全部不违反「数据决定信息量」）

| 序 | 解法 | 内容 | 是否新增数据/图形 | 优先级 |
|---|---|---|---|---|
| **1** | **容器定宽，不硬撑** | 看板主容器在 ≥1024 限宽 **960px** 居中，四周留白成为页面边距 | **否**（纯布局） | **P0，必做** |
| **2** | **数据说明行** | 看板顶部固定一行：「当前样本：成交记录 10 条 / 挂单 10 条 / 用户 36 个；趋势折线需成交记录 ≥30 条后自动解锁」 | **否**（全是实测值 + 真实门槛） | **P0，必做** |
| **3** | **真实待办聚合** | 看板右栏填入**实测**待办计数：异常挂单 10 条、关联异常版权 3 条、未实名用户 35 个。**这是补真实数据维度**，正是设计师说的正确解法 | 是（但全部是已有实测数据的聚合，非新维度） | **P1，进 Backlog，不进 MVP 第一期** |
| **4** | **指标卡补齐为两行满格** | 6 张指标卡在桌面 3 列 × 2 行，**本身已铺满 1216px 内的 2/3 宽**；配合解法 1 的 960px 容器，6 张卡在 960px 内占 4 列 × 2 行（≥1280）或 3 列 × 2 行，几乎满格 | 否 | P0（随解法 1 一起落地） |

#### H.4 明确拒绝的两类做法

| 拒绝项 | 拒绝理由 |
|---|---|
| 装饰性插图 / 抽象色块 / 占位插画 / 「更多功能敬请期待」灰底占位块 | 装饰不承载信息。**占位块尤其危险**——它明确告诉运营「这里本该有东西但还没做」，**比空白更强化「没做完」的判断**。这与 §9.2「区分真的没有数据和功能没做完」是同一条原则：占位块就是用视觉撒谎 |
| 把 10 个成交点连成折线 / 用虚构示例数据填满图表 | 前者违反 AC-54 样本量门槛（且屏幕变宽让假趋势更有说服力）；后者违反「禁止臆造数据」铁律 |

#### H.5 验收与后续

- **验收**：AC-55（容器限宽 960px 居中 + 数据说明行 + 明令禁止装饰图形与 占位块）。
- **后续解锁条件**：成交记录 ≥30 条 → 两端同时解锁折线图（AC-54）；`users > 100` → 触发分页需求评审（17.6.1 第六步）。

#### H.6 总监补充条款：解法 2 的说明行不得依赖「人工解释」

PM 在 H.5 建议「首次演示时主动说明一句」。这条**采纳为运营动作，但不作为解法的一部分**——
因为它依赖「每次有新运营人员第一次打开时都有人在场解释」，这在系统长期使用中不成立。
一旦运营换人、或某天没人解释，留白就重新变成「没做完」。

因此追加两条硬约束：

| # | 补充条款 | 理由 |
|---|---|---|
| **B1** | **数据说明行必须常驻可见，不得折叠、不得置于悬浮提示、不得仅在首次访问时弹出** | 说明行是**自解释**的唯一载体。它一旦被折叠，它的价值归零——而折叠恰是 PC 端节省垂直空间的常规做法。**这是最容易在实现中被优化掉的细节，必须写进验收** |
| **B2** | **说明行的文案必须由接口返回的实时样本量生成，不得硬编码「10 条 / 36 个」** | 样本量会变（成交记录每天增加）。硬编码的说明行在数据增长后会变成**新的谎言**——比没有说明行更糟。同理，折线解锁条件文案须随实际阈值生成 |

> B2 的必要性：AC-55 现写法中示例文案含「成交记录 10 条 / 挂单 10 条 / 用户 36 个」，
> 若实现方照抄成常量，数据增长后说明行会与事实不符。**验收时须确认文案来自接口而非硬编码。**

#### H.7 关于「演示时口头解释」这条建议的定位

PM 的这条建议**仍然有效，但降级为辅助**：

- **它不是解法**——解法是 B1 + B2 的常驻说明行，任何人任何时候打开都能自解释。
- **它是有益的补充**——首次演示时主动说明，能加速运营建立「样本量决定图表密度」的心智模型，
  减少他们后续问「为什么没有折线图」的次数。**但即便没人解释，界面也不应产生误导。**

这条区分很重要：**依赖人的善意解释 = 系统缺陷；依赖人但有系统兜底 = 体验优化。**
