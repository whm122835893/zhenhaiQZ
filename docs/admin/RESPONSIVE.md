# 臻海艺术 · 运营后台 双端差异说明（RESPONSIVE）

> 设计师：颜好看 ｜ 决策日期：2026-10-21 ｜ 变更性质：产品形态变更（非增量优化）
> 上游：`DESIGN_SYSTEM.md`（组件规范）、`PAGE_PROMPTS.md`（页面提示词）、`admin-tokens.css`（令牌）
> 触发源：总监决策「后台要双端能用——PC 电脑和手机都要能正常用，不是只能手机用」

## 0. 变更摘要

| | 旧 | 新 |
|---|---|---|
| 形态 | 单端（移动端 390px）+ PC 上套 430px 设备框居中 | 双端（移动端 390 / 平板 640 / 桌面 1440 两栏） |
| 断点 | 1 个（768px） | 3 个（768 / 1024 / 1280） |
| 桌面导航 | 无（PC 上看到的还是底部 TabBar） | 侧边 Rail 200px（可折叠 56px） |
| 桌面列表 | 与移动端同构（卡片 + L2 展开） | 表格 / 行式列表，列数 4~8 |
| 桌面筛选 | 右侧抽屉（已作废，见 v1.3 修订） | 顶部横排筛选条 + 更多筛选下拉；移动端为底部弹层 |
| 桌面导出 | ≥768px 显示 | 保持，≥1024 增加「导出全部 + 字段选择」 |

**本次变更不推翻任何已验收成果**：Token 复用机制（`@import` 单一真源、零 hex 复制）、列表卡片三槽位（L1 三字段）、审计时间线纵向 diff、317+ 个 `--admin-*` 令牌的 A1/A2/B/C 分层组织方式，全部保留。移动端（<768px）的渲染结果与改造前**逐像素一致**——**唯一例外是成交记录与筛选形态两处，按 PRD v1.3 裁决同步（见 §2.2 / §4.9），这两处属于修正跨文档冲突，不是新增端侧差异**。

## 1. 断点表

| 断点 | 视口宽 | 形态 | 一级导航 | 内容布局 | 内容区宽上限 |
|---|---|---|---|---|---|
| **xs / sm** | < 768px | 移动端 | 底部 TabBar（4 项，≤2 汉字） | 单列满宽，卡片流 | 满宽（设计基准 390px） |
| **md** | 768 ~ 1023px | 平板 | 底部 TabBar（保留） | 单列居中，间距放宽 | 640px |
| **lg** | 1024 ~ 1279px | 桌面 | 侧边 Rail 200px | 两栏：Rail + 主内容区 | 1440px 总宽 / 1216px 内容块 |
| **xl** | ≥ 1280px | 桌面宽屏 | 侧边 Rail 200px | 两栏，结构不变 | 同上（内容块不继续拉伸） |

**三条不可动摇的约束**

1. 根字号永远锁 `16px`，不随视口缩放。C 端 `html { font-size: calc(100vw / 23.4375) }` 是移动端专属产物，后台不继承。
2. `html, body, #app { height: auto }` 覆盖必须保留——C 端 `tokens.css` 里有 `height:100%`，不覆盖则长列表无法滚动。
3. `#app` 在 ≥1024px 不再有 `max-width: 430px`、无 `box-shadow` 裁切圆角。桌面端不做「手机画中画」。

**为什么 `1440px` 而不是 `1920px`**：桌面主内容块上限 1216px，14px 密集位正文一行约 80 字符，接近可读上限 75 字符。1920 视口下继续拉伸只会让行长失控，1440 是「够宽 + 不失控」的平衡点。

**成交记录：全端取消横向滚动表（v1.3 修订，对齐 AC-29 / AC-57）。**

原 v1.2 结论「成交记录是全后台唯一允许横向滚动表的页面，移动端保留冻结首列 + 渐隐提示，桌面端撤销」**整条作废**，改为**全端统一**：

- **<1024（移动端 + 平板）：卡片流**，与模块一卡片流同构，L1 四主字段（藏品名 / 成交价 / 买卖双方脱敏 / 成交时间），其余字段进 L2 展开区。
- **≥1024：6 列表格**，无横向滚动条。
- **全端不保留冻结首列机制**（AC-57 明确禁止任一断点保留冻结首列）。
- **取消理由（不是「PC 上能平铺」）**：横向滚动表在移动端本身就是反模式——内容在视口外不可发现，渐隐提示只能告知「右边还有」，不能告知「右边还有什么、值不值得滑」。AC-29 已写死「≤428px 必须卡片流、不得渲染横向滚动表格」，AC-34 进一步要求首屏无横向滚动条。原先把它写成「移动端特例 + PC 撤销」是**结论错误**，不是端侧差异。
- **横向比价的替代**：「成交价单列排序列表」——卡片流下按成交价降序即等价于横向比价，且不需要滑动。

## 4. 移动端硬约束在 PC 端的逐条处置

PM 基于「纯移动端」做的一批硬约束，双端下不是全部放开，是分层处置。**「必须遵守」= 双端都遵守的红线；「可放宽」= 有明确依据与上限的放宽；「必须遵守」在 PC 端不变。**

### 4.1 Tab ≤ 4 个且每 Tab ≤2 汉字 → **可放宽到 6 项 / 4 汉字**

- **详情页 Tab**（概览/内容/交易/审计）：**保持 ≤4 不变**。这是工作记忆上限，与屏幕宽度无关——放宽会让「一眼看完分层」失效，PC 上同样找不到第 5 个 tab。
- **一级导航**（TabBar 4 项 → Rail 项）：
  - **移动端 TabBar：≤4 项、每项 ≤2 汉字，不变**（390px 一行 4 个 50px 项，中文 2 字是物理上限）。
  - **桌面 Rail：≤6 项、每项 ≤4 汉字**。依据：
    - Rail 竖排，垂直空间是 44px × 6 = 264px，768px 视口高下**不需要滚动**，比横向 4 项更省垂直空间——这是桌面导航的真实优势，必须用起来。
    - 上限取 6 而非 8：6 项之上运营需要开始「回忆位置」而不是「扫视位置」，导航从「扫视」退化为「搜索」，而搜索是 P1 成本。
    - 文字 4 汉字依据：Rail 项宽 200px − 左缩进 12px − 图标 20px − 图标文字间距 12px = 156px 可用；4 汉字 14px = 56px，余量充足。5 汉字（70px）也放得下，但 5 汉字在导航位是「句子」不是「标签」，读起来慢，**4 汉字是标签的语法上限**。
  - **注意**：Rail 项数不是「越多越好」的平移。移动端 4 项 = 工作台 / 藏品 / 市场 / 用户；桌面可多出的 2 项是**二级入口上浮**（版权审核、审计日志），且必须**按角色裁剪**（reviewer 不渲染「用户」→ 自动腾出位置给「版权」）。总项数是**角色相关的**，不是全局 6。

### 4.2 列表首屏只露 3~4 字段 → **PC 放宽到 4~8 列，按列表定**

移动端 L1 三槽位（主标识 / 编号 / 一个业务关键值 + 状态标签）**完全保留在移动端**。PC 端改为表格，列清单如下（每列都必须在移动端可达——见 §6 数据一致性）：

| 列表 | PC 列（顺序固定） | 列数 | 移动端对应位置 |
|---|---|:--:|---|
| 藏品列表 | 藏品名 / 编号 / 状态 / 售价 / 库存 / 已售 / 作者 / 创建时间 | 8 | 名称+编号=L1，售价=L1 槽位 3，状态=L1 标签，其余 4 项 = L2 |
| 版权队列 | 版权名 / 版权 ID / 缩略图 / 关联藏品 / 审核状态 / 审核人 / 审核时间 | 7 | 名称+ID=L1，关联诊断=L1 槽位 3，状态=L1 标签，缩略图+sort+审核人+时间=L2 |
| 挂单监控 | 藏品+NFT 编号 / 挂单 ID / 挂单价 / 最近成交价 / 价差比 / 状态 / 挂单时间 | 7 | 名称+ID=L1，挂单价=L1 槽位 3，状态=L1 标签，其余=L2 |
| 成交记录 | 成交 ID / 藏品名 / 买家 / 卖家 / 成交价 / 成交时间 | 6 | 全部在 L2 展开区 |
| 用户列表 | 用户 ID / 手机号 / 实名状态 / 冻结状态 / 钱包余额 / 持有 NFT / 注册时间 | 7 | 手机号+ID=L1，余额=L1 槽位 3，状态=L1 标签，其余=L2 |
| 实名台账 | 用户 ID / 手机号 / 实名状态 / 证件号（掩码）/ 录入时间 / 录入人 | 6 | 手机号+ID=L1，状态=L1 槽位 3，其余=L2 |

**上限 8 列的依据**：8 列 ≈ 1216px 内容宽 / 平均 150px。**桌面表格同样不允许出现横向滚动条**（与成交记录全端取消横向滚动表的口径一致）——横向滚动会让「一屏扫完一行的所有字段」失效，那正是 PC 表格的核心价值。**超过 8 列的字段一律下沉到详情页，不加列。**

### 4.3 操作按钮不放行尾，改 ActionSheet → **PC 放开到行尾，≤2 文字 + 1 更多**

- **移动端完全不变**：卡内「更多」→ ActionSheet（52px 行高，触摸目标），左滑露单主操作。
- **PC 放开行尾操作列**，依据：
  - 移动端禁行尾的原始理由是「按钮被挤到 <80px，误触率高」——这个理由在 PC 不成立（鼠标是精确指针，160px 操作列可容纳两个 16px 图标 + 文字）。
  - **上限 2 个文字按钮 + 1 个「更多」图标**。为什么不是 3 个文字按钮：① 一行 3 个动词按钮会争夺「主操作」的注意力，运营扫行时无法判断该点哪个；② 2 个 + 「更多」是「两个已知高频 + 一个兜底」的最优分布，第三个及以后的操作在 ActionSheet 里仍可 2 次点击到达，成本可接受。
  - 尺寸：文字按钮 32px 高（`--admin-pc-row-action-hit`），低于 44px 触摸目标——**PC 是指针环境，44px 只对触摸端是硬约束**。图标仍 16px 档。
  - **高危操作（强制下架 / 冻结 / 驳回）在 PC 端仍不放行尾**——只放「更多」里，且必须走二级高危确认 Dialog（必填理由 + 手输确认词）。PC 端误触成本（误冻结一个用户）不比移动端低，键盘鼠标的误触概率虽低但**后果相同**。这是「PC 也不放松」的一条。

### 4.4 六列表单全部不分页（阈值 50）→ **双端统一阈值 40，PC 用页码、移动端仍「加载更多」**

- **表单不分页在两端都不变**：藏品编辑、实名录入、版权裁决都是「单条记录的表单」，一页一次提交一个对象，本来就没有分页概念。这条约束与断点无关。
- **真正需要分页的是列表页**。原 v1.2 裁决「阈值 50」与设计师 v1.2 的「PC 阈值 25」**均已作废**，改为**跨端统一 40**（PRD v1.3 §17.5.3，AC-27/AC-48）：
  - **列表结果 ≤40 条**：不分页，一次渲染完（移动端直接出「已全部加载 N 条」终止态，PC 端不渲染分页控件）。
  - **列表结果 >40 条**：PC 端启用页码（每页 40 条 + 「共 N 条 / 第 X 页」）；移动端继续「加载更多」。
  - **PC 一屏是 17~21 行，不是 20 行**：内容可视高 764px（1440 − 顶栏 48 − 筛选条 48 − 表头 40），常规行高 44px → 17 行，紧凑行高 36px → 21 行。**记忆边界是 2 屏 = 34~42 条，取 40 为保守值**。
  - **设计侧对「统一 40」的确认（见 §4.4 附注）**：960px 居中的看板容器与「末页不满半屏」的观感都支持 40，25 在视觉上更整齐的代价是「空白页诱导「数据没加载完」的误判」，不值。
  - **数据一致性**：分页只改前端请求参数（`page`/`pageSize`），后端返回结构不变；移动端继续用「加载更多」（游标式），PC 用页码（offset 式）。同一列表在两端看到的是**同一份数据的不同切片方式**，总数口径一致（页码模式由后端返回 `total`）。
  - **尾页孤儿规则**：若分页后末页 < 半屏且总条数 >40，在末页上方给一行说明「已显示全部 N 条」，避免空白被误读为加载失败。

#### 设计侧对「跨端统一 40」的确认意见

PM 主张的 40 我确认采纳，理由三条：

1. **60% 内容宽（960px 居中容器）与阈值无关**——960px 是看板页 AC-55 的容器限宽，列表页用的是 1216px 内容块。两者不是同一个容器，不构成「窄容器要小阈值」的约束。
2. **「末页不满半屏」是真实的误判源**。users 36 条按 25 分页 → 2 页（25 + 11），末页 11 行 ≈ 半屏空白。这个观感与 PRD §9.2「区分真没数据和功能没做完」是同一类错误：空白被读成「还有」。40 让 36 条在两端都是 1 页全出，把这个歧义彻底删掉。
3. **跨端统一比「各端最优」更重要**。若桌面 25 / 移动 50，运营会先怀疑数据不一致，而不是怀疑屏幕——这与 §6.1「口径漂移在审核场景是事故」同源，只是漂移发生在「分页与否」而不是「字段」上。

**如果坚持 25，代价是**：① 36 条用户列表在 PC 上永远以「末页 11 行」呈现，每一页都要处理这个歧义；② 需要额外写一条「已显示全部」的说明行去补视觉空缺——**这不是消除空白，而是用文案掩盖一个本可以不存在的空白**；③ 双端阈值不同带来的口径疑问。**收益仅是「每页行数整齐」，而整齐本身不解决任何任务。** 我不建议。

### 4.5 导出：仅 ≥768px 显示 → **保持，≥1024 增加能力而非增加入口**

- **≥768 显示导出入口：保持**（Q11 裁决不动）。
- **≥1024 增加两项**（都在同一个导出按钮的下拉里，不新增页面级按钮）：
  - 「导出全部结果」（不只是当前筛选页）
  - 「选择导出字段」（勾选要导出的列，勾选范围与 PC 表格可见列一致，≤8 列）
- **移动端仍无导出**。移动端下载文件后无法直接分析（PRD S4），这个诉求在移动端实质落空——双端化不改变这个事实，不为了「双端看起来一致」而在手机上放一个用不了的按钮。

### 4.6 成交记录：唯一允许横向滚动表 → **全端取消横向滚动表，改卡片流**（v1.3 修订）

见 §2.2。**原「移动端保留横向滚动 + 冻结首列 + 渐隐提示、桌面端撤销」的结论整条作废**：

- **<1024（移动端 + 平板）：卡片流**，L1 四主字段（藏品名 / 成交价 / 买卖双方脱敏 / 成交时间），其余进 L2 展开区。
- **≥1024：6 列表格**，数值列等宽右对齐。
- **全端无横向滚动条、全端不保留冻结首列机制**（AC-57）。
- 这不是「PC 撤销移动端特例」，而是**该特例本身被取消**。原论证「1216px 足以平铺 6 列」只是桌面端的补充理由，**取消的真正理由是横向滚动在窄视口不可发现**（见 §2.2）。

### 4.7 看板：指标卡 + 横向条形、禁 tooltip → **PC 端给折线 + tooltip，但**数据点门槛不变**

这是本轮**最需要妥协的功能**，详见 §5。

- **PC 端（≥1024）允许的**：
  - 折线图（时间序列），带 hover tooltip
  - 指标卡 3 列（≥1280 为 4 列）
  - 图表容器高 260px（≥1280 为 320px）
  - 同一屏可并排 2 张图（各自最小宽 320px）
- **PC 端仍然禁止的**：
  - **PRD §9.3 的样本量门槛不因断点改变**。当前真实数据：用户 36、订单 2、成交 10。「10 个数据点画折线是荒谬的」这个结论**在 PC 端依然成立**——因为荒谬的原因不是屏幕窄，是**样本量不足导致折线的趋势暗示是假的**。10 个点连成线，读者会以为看到了趋势，实际那是噪声。屏幕变宽不增加数据点，屏幕变宽只让「假趋势」画得更漂亮，更有害。
  - 因此：成交额折线**仅在成交记录数 ≥30 时启用**；10 条成交数据下仍用指标卡 + 分布列表。
- **PC 端给什么（替代折线）**：
  - **指标卡 3~4 列**（6 张卡两行放下，一屏看完）
  - **横向条形图 + 数值直标**（`藏品成交排行`，条形右侧直接标数值 + 占比）
  - **直方图/柱状**（`成交价区间分布`，区间标签在轴上，PC 端不再放不下）
  - **区间分布表**（`用户活跃分布` 降级为列表，PC 端给表格形态而非跳转）
  - 图表区 2 列并排，不做 3 列（3 列在 1216px 下每列 400px，坐标轴标签仍会挤）

### 4.8 「10 个数据点画折线是荒谬的」在 PC 端是否成立 → **成立，且理由更强**

- 该结论的依据是**样本量 → 趋势暗示的真实性**，与视口宽度无关。
- 屏幕变宽唯一改变的是「假趋势看起来更专业」——这是**负向改变**。一个 10 点的折线画在 260px 高的卡片里，配上 hover tooltip 读数，观者会做因果推断。这是用更强的视觉说服力包装更弱的数据。
- **PC 端的硬门槛**（写入实现规范）：折线图的数据点 ≥30 才允许；不足时用条形 / 指标卡 / 分布列表。成交记录当前 10 条 → 不画折线。用户 36 条 → 满足点数门槛，但**用户活跃分布的"活跃"定义若只看 36 人中的一部分，样本仍不足**，需按实际分组数再核。

### 4.9 移动端筛选为右侧抽屉 → **修正为底部弹层**（v1.3，对齐 AC-33）

**原结论「移动端筛选 = 右侧抽屉，宽 `calc(100% - 56px)`」作废。** AC-33 已定移动端筛选为**底部弹层**（`van-popup position="bottom"`），底部固定「重置 / 确定」。

- **移动端（<768）：底部弹层**
  - 从屏幕底部升起，上圆角 `--admin-radius-sheet`（14px），宽 100%，最大高 70vh（字段多时内部滚动）
  - 底部固定操作栏高 `--admin-footer-h`（56px）：左「重置」次按钮 + 右「确定」主按钮，两按钮等宽，热区 ≥44px
  - 字段间距 `--admin-filter-field-gap`（20px）；字段 >6 个时分组折叠（组标题 `--admin-filter-group-title-fs`）
  - **迁移理由**：① **拇指可达区在屏幕下半部**——底部弹层的「重置/确定」与 TabBar 同侧，单手可完成「打开 → 调条件 → 确认」全程；右侧抽屉要伸右手，且右侧边缘滑动是系统返回手势的冲突区。② `calc(100% - 56px)` 在 390px 视口下只有 334px 宽，且右侧 56px 露出的主页面在移动端不是「暗示可 dismiss」，而是**误触区**（点到了就是关闭，条件全丢）。③ 「重置/确定」固定在弹层底部是移动端惯例，位置与拇指弧线重合。
- **平板（768~1023）：仍是底部弹层**（PRD v1.3 §17.2.1 表），弹层宽度跟随内容区并居中，不改侧面板。
- **桌面（≥1024）**：**顶部横排筛选条**（高 48px）：搜索框定宽 320px + 筛选 chip 横排（≤4 个直接可见）+ 「更多筛选」下拉面板（360px，含剩余字段）+ 「重置」
  - **筛选 chip ≤4 个直接可见的依据**：4 个 chip × 平均 100px + 搜索 320px + 间距 = 约 760px，在 1216px 内容宽内留有充足余量；第 5 个起进下拉。
  - **桌面侧面板（360px 固定）的保留条件**：字段数 >6，或含日期区间 / 多选 / 需要输入时，仍用 360px 侧面板（不做成下拉），因为下拉面板内表单多时不好操作。**这是「字段复杂度触发的形态选择」，不是端侧特例**——判据是字段构成，与视口无关。
  - **下拉 vs 侧面板的选择规则**：筛选字段 ≤6 且都是枚举 → 下拉；含日期区间 / 多选 / 需要输入 → 侧面板 360px。
  - 筛选条件生效后，chip 上显示已选数量角标（沿用移动端语义），**两端筛选语义完全一致**，见 §6。

### 4.10 批量操作移出 MVP（Q12）→ **保持不放开，双端都不做**

- **桌面端也不做**。理由：
  - 复核 PM 的原论证「PC 上的多选 checkbox 列在移动端卡片流里没有位置」——这个论证在 PC 端不成立，checkbox 在 PC 表格里完全可行。
  - 但 Q12 的裁决理由不止这一条：**批量操作的权限模型、审计粒度、部分失败语义（三条里两条成功怎么办）在 MVP 阶段做不完整，比不做更危险**。后台 5 个写角色 × 批量操作 = 权限矩阵爆炸。
  - **替代路径两端统一**：「筛选 → 全选当前筛选结果 → 单条确认」。这个路径在移动端和 PC 端都成立（PC 端全选是筛选结果的全选，不是当前页的全选——**这是 PC 端特有的语义，必须在 UI 上写明**，避免运营误以为只选了当前页 40 条）。
  - 批量操作进 backlog，标记为「PC 优先」——它是双端化之后**最应该优先补**的 PC 端能力。

## 5. 最需要妥协的功能：数据看板（工作台）

**结论：看板是双端下最需要妥协的功能，妥协发生在「看板是否值得做成两套」这个问题上。**

**为什么是它**

其余 14 个页面的双端差异都是**同一份信息的不同排布**（卡片 ↔ 表格、底部弹层 ↔ 筛选条、Sheet ↔ Dialog），信息本身、字段本身、状态矩阵本身完全一致，改造是「布局重排」。

看板不是。它的本质矛盾来自 PRD §9.3 与 PRD 附录 S1 的两条相反要求：

- S1 要求：**做减法**。390px 下三栏并列不可行，只能保留指标卡 + 藏品成交排行，柱状/条形降级为跳转列表，滚动 5 屏以上。
- §9.3 要求：**不画折线**。样本量不足（用户 36 / 订单 2 / 成交 10），折线会给出假的趋势暗示。

双端化让这个矛盾第一次显形：PC 端有 1216px 宽、有精确指针、有 tooltip——**技术条件全部满足，唯一还缺的是数据**。于是会有人问「PC 端能不能把砍掉的三种可视化加回来」。

**明确的妥协裁决**

1. **看板不做「PC 专属三栏版」**。PC 端保留与移动端**同一套降级后的可视化集合**（指标卡 + 横向条形 + 柱状），只是排布从「纵向堆叠 2 列」变成「指标 3~4 列 + 图表 2 列并排」。
2. **不加折线，直到数据量到位**。这是硬门槛，不是「PC 端可以例外」。理由已在 §4.8：屏幕变宽让假趋势更有说服力，而不是更少。
3. **移动端不追平 PC 端**。移动端的减法不是因为屏幕小才做减法，是因为**数据就是这么多**；PC 端数据同样这么少，所以 PC 端也不需要更多图。移动端是纵向，PC 端是并排——**信息量相同，密度不同**。
4. **看板的信息量上限由数据决定，不由断点决定**。哪一天成交记录到 30 条以上、用户活跃有连续 30 天以上，两端**同时**解锁折线图（同一个开关，不做端侧差异），因为图表能不能画是数据问题。

**代价（诚实记录）**：双端化后看板的第一屏在 PC 上「看起来有点空」——6 张指标卡 + 2 张图，1440px 宽屏下右侧有富余。这是**故意留白**（`VISUAL_DENSITY` 在看板页下调一档），不是没做完。如果后续 PM 要求「PC 端首屏填满」，正确答案是**补真实数据维度**（按渠道/按时间/按状态的分布），而不是加装饰图形或把 10 个点连成折线。

**第二难：版权审核的图文比对（S3）**——PC 端技术上完全消解（两图并排各 1216/2 宽，缩略图可给到 200px 级），但 S3 的原始方案已经把它定成「双图上下排各占全宽」，那是移动端形态。PC 端**改为左右并排**（版权图 / 藏品图 1:1），这是 PC 端自动消解的一项，不需要额外设计成本。

## 6. 已知取舍

### 6.1 数据一致性：PC 显示 8 列，移动端只有 4 个字段

**保证机制（三条，同时成立）**

1. **同源渲染**：PC 表格与移动端卡片渲染**同一份接口返回的同一批记录**。PC 端不是「另一个接口、另一个字段集」，移动端也不是「PC 字段的裁剪版」——**两端都从全量字段渲染，只是一条走卡片三槽位投影，一条走表格列投影**。
2. **字段定义单一真源**：每个字段在**一个**位置定义（详情页 DL），列表的 L1 槽位与 PC 列都是**对该定义的引用**，不是各自维护一份。这条已由「列表卡片三槽位」的既有决策确立，桌面端沿用同一原则。
3. **不引入「PC 专属字段」**：PC 表格的 8 列，全部是移动端 L1+L2 合并后的**子集**。不允许出现「只有 PC 能看到」的字段——否则两端口径必然漂移，而漂移在审核/审计场景是事故。同理，**导出的 CSV 字段集 = 桌面表格可见列**（AC-53），不因导出通道而多出任何一端看不到的字段。

**剩余的不可消除差异（诚实记录）**

- **首屏可见字段数不同**（移动 4 / PC 8）。这是屏幕物理差异，不可消除。**后果**：运营在移动端说「这条记录没有创建时间」，PC 端能看到创建时间。**缓解**：移动端 L2 展开区保留全部 L2 字段（≤8 项），创建时间在移动端是「展开 8 项」里的一项——**可达，只是不在首屏**。所有 PC 列在移动端都必须可达，这是硬约束。
- **排序不同**：PC 表格可点列头排序，移动端只能按预设顺序（新建优先 / 状态筛选）。**后果**：运营在 PC 排出的顺序在移动端看不到。**缓解**：不承诺跨端顺序一致，在需要固定顺序的场景（如审核队列按提交时间）两端都用同一默认序，PC 端额外提供排序。
- **分页方式不同**（页码 vs 加载更多），但**阈值统一 40**（见 §4.4）。**后果**：PC 上「第 3 页」在移动端没有对应概念。**缓解**：总数口径一致（同一 `total`），移动端「已全部加载 N 条」终止态与 PC 的 `total` 对齐；两端阈值相同，不存在「同一批数据在两个端上页数不同」的认知分裂。

### 6.2 字号分档：PC 密集位 14px vs 阅读位 16px

**取舍点**：桌面端 16px 中文正文一行 60~70 字符，已在可读上限；缩到 14px 反而把行长推到 80+ 字符，可读性下降且中文小字笔画粘连。
**处置**：**阅读位保持 16px 不变**，仅在**密集数据位**（表格单元、列表行内副文本、筛选 chip、Rail 项）用 14px。这是本轮唯一一处对 C 端字号体系的显式偏离，已在 `admin-tokens.css` §16.1 登记为 `--admin-fs-dense`，仅 ≥1024 生效。
**遗留风险**：14px 中文在 4.5:1 对比度要求下，若深色主题的 `--admin-fg-2` 亮度不足，密集位会读不清——深色主题上线时需单独复核密集位对比度（`--admin-fg` 与 `--admin-fg-2` 在 dark 下的比值）。

### 6.3 触屏笔记本 / 平板横屏

768~1023 平板区间用底部 TabBar 而非 Rail。这个区间**包含 iPad 横屏（1180×820 → 实际 CSS 宽 1180 落在 lg 区间）**——所以 iPad 横屏会拿到侧边 Rail，竖屏（820 CSS 宽）拿底部 TabBar。**同一台设备旋转屏幕会切换导航形态**，这是断点方案的固有代价。

**为什么 768~1023 不上 Rail（v1.3 修正论证）**

原论证写的是「iPad 竖屏 820px 扣掉 200px Rail 只剩 364px —— 比移动端 390px 还窄」。**这个算术是错的**：820 − 200 = **620px**，不是 364px。620px 明显宽于移动端 390px，「比移动端还窄」不成立。

**结论不变，但理由换为「净收益为负 + 旋转换形态」两条**：

| 方案 | iPad 竖屏（CSS 宽 820px）下的内容区 | 代价 |
|---|---|---|
| 平板方案（单列居中 640px + 底部 TabBar） | **640px** | — |
| 桌面方案（Rail 200px + 两栏） | **620px**（820 − 200） | 内容区**净缩 20px（净收益 −20px，为负）**；且引入第二个导航形态 |

1. **净收益 −20px**：引入 Rail 后内容区从 640px **缩到** 620px。导航省下的垂直空间（264px）在单列布局里本来就用不上——单列内容不需要「把垂直空间还给内容」这个收益，因为内容本来就是纵向流式。**用 20px 的宽度损失换一个在本区间无收益的收益（垂直空间），是净负。**
2. **旋转换形态的认知成本**：iPad 竖屏拿 TabBar、横屏（1180px）立刻换 Rail。同一台设备同一秒内导航形态从底部变左侧，而 Rail 只占宽度的 13.9%（1440px 区间）却吃掉 820px 区间的 24%。**导航形态应当由「是否真的需要侧栏」决定，而不是由「够不够宽」决定。**
3. 若强行要在该区间上 Rail，Rail 折叠态 56px 只能把内容区抬回 764px——**但 764px < 1024，走不到 lg 区间的布局规则**，等于自己造了第三套断点，不做。

**缓解**：≥1024 时 Rail 折叠态 56px 可用；`--admin-rail-w-collapsed` 提供紧凑解法。接受旋转跳变。

### 6.4 桌面端 hover 态在触屏上不成立

`--admin-pc-hover-enabled: 1` 仅 ≥1024 生效。**平板区间（768~1023）有鼠标也可能是触屏**，因此 hover 反馈在 md 区间不启用（沿用移动端的按压态反馈）。**代价**：md 区间的桌面鼠标用户少一层「可点性提示**。

### 6.5 移动端不受影响（已验证的取舍边界）

<768px 的渲染结果与本次改造前**逐像素一致**。所有新增令牌在 <768px 不生效，所有媒体查询只向上生效。**这是「不推翻已验收成果」的技术保证**：移动端可独立回归，回归基线 = 改造前截图。

## 7. 实现要点（给前端 Agent）

1. **断点值只从 `--admin-bp-md/lg/xl` 取**，不写裸数字；JS 侧用 `matchMedia` 监听同一组值（若框架不读 CSS 变量，则在 JS 侧硬编码 768/1024/1280 并注释与令牌同源）。
2. **两栏容器**：`<div class="admin-shell" :data-rail="railCollapsed ? 'collapsed' : 'expanded'">`，Rail 与主内容区为它的两个子元素。Rail 折叠状态存 `localStorage`（键名建议 `admin.rail.collapsed`）。
3. **移动端 `<768px` 必须不渲染 Rail 组件**（不是 CSS 隐藏——隐藏的 Rail 仍会加载图标与占位）。`≥1024px` 必须不渲染 TabBar（同理）。`admin-tokens.css` 里的 `.admin-tabbar { display:none }` 是**兜底**，不是主要手段。
4. **列表页组件分两套实现**：`ListCard`（移动/平板）与 `DataTable`（桌面）。两者消费**同一份字段定义**，不各自维护列/槽位映射。建议把字段定义抽到 `listFieldDefs.js`，移动端投影出 L1/L2，桌面端投影出列。
5. **表格列宽**用 `--admin-pc-col-*` 变量，不写死 px；用 `grid-template-columns` 或 `<colgroup>`，最后列 `minmax(var(--admin-pc-col-min), 1fr)` 吃掉余量。
6. **字号**：桌面密集位用 `var(--admin-fs-dense)`，阅读位用 `var(--admin-fs-body)`。**不要全局改 `--admin-fs-body`**——它是移动端的基准。
7. **hover**：`@media (hover: hover) and (pointer: fine)` 内启用 hover 态，md 区间不启用。
8. **导出**：`≥768` 显示入口（保持 Q11）；`≥1024` 额外给「导出全部 / 选择字段」。
9. **无 emoji**：所有图标 `lucide-vue-next@1.0.0`（精确版本），尺寸 16/20/24，`stroke-width: 1.75`。
10. **零硬编码色值**：桌面新增令牌全部走 `--admin-*`，深色主题由 `[data-admin-theme="dark"]` 下的 §17 覆盖，不需要在组件里写主题判断。
11. **禁止横向滚动**：任何断点下不渲染 `overflow-x: auto` 的表格容器，不实现冻结首列（`position: sticky` 首列）。成交记录 <1024 走卡片流（§2.2）。
12. **移动端筛选用底部弹层**，不用右侧抽屉；平板同样底部弹层。桌面 ≥1024 用顶部横排条 + 下拉/360px 侧面板（§4.9）。
13. **分页阈值 40 全端统一**，常量单点定义（建议 `--admin-page-size: 40`），PC 页码与移动端「加载更多」共用同一个阈值令牌，不各写一个数字。

## 8. 双端一致性自检清单（实现时逐条对照）

> 这份清单是**可执行**的，不是原则性文字。每条都能在代码里指出「查什么」。设计侧在 review 时按此逐条核对；任一条不通过即视为双端一致性验收不通过。
> 清单共 **18 条**，分四组：A 字段一致性（5）、B 操作语义一致性（5）、C 状态与文案一致性（4）、D 布局形态与禁用项（4）。

### A组 · 字段一致性（对齐 AC-45 / AC-46 / AC-47）

- [ ] **A1** 桌面表格的**每一列**，都能在对应列表的移动端 L1 主字段或 L2 展开项中找到**同名字段定义**（查：`listFieldDefs.js` 中该列的 `key` 是否存在于该列表的移动端投影集合内）。
- [ ] **A2** 移动端 L2 展开项**全集**在桌面端详情页 DL 中同名可见（AC-46 反向约束，查：移动端投影数组逐项在桌面 DL 定义中存在）。
- [ ] **A3** **不存在单端独有字段**（查：全量grep 字段定义来源，只有 `listFieldDefs.js` 一处；组件内不得出现字面量字段名数组）。
- [ ] **A4** 同一字段在两端的**格式化逻辑完全一致**（金额千分位+单位后置、时间格式、编号等宽+`tabular-nums`、脱敏规则），查：格式化函数只有一份，两端调用同一函数而非各写一遍。
- [ ] **A5** **导出的 CSV 字段集 = 桌面表格可见列**（≤8 列），不含移动端 L1∪L2 之外的字段（AC-53，查：导出字段选项的数据源与 `DataTable` 列定义同源，不是另一份列表）。

### B 组 · 操作语义一致性

- [ ] **B1** 每个列表的**「主操作」在两端语义一致**：同一记录、同一动作，断点切换不改变含义（如「冻结」在两端都是冻结，不因 PC 有行尾就变成别的动作）。
- [ ] **B2** **高危操作两端走同一套二次确认流程**（必填理由 + 手输确认词 + 审计留痕），且**两端都不在行尾**——PC 放开行尾是针对低危操作（查看详情/复制 ID），高危（强制下架 / 冻结 / 驳回 / 查看完整证件号）只进「更多」。
- [ ] **B3** 可点操作**总数**在两端一致（移动端左滑 1 + 卡内「更多」N；PC 行尾 ≤2 + 「更多」M，N = M + 1），不存在「移动端有这个操作、PC 上没有」。
- [ ] **B4** **筛选语义两端一致**：同一筛选条件在两端产生同一结果集；chip 已选数量角标两端同一算法；「重置」在两端都恢复全部默认值并立即重新查询。
- [ ] **B5** **分页阈值两端统一 40**（常量单点），PC 页码与移动端「加载更多」不各写一个数字；两端 `total` 口径一致。

### C 组 · 状态与文案一致性

- [ ] **C1** **空态文案逐字一致**（同一状态的标题/说明/行动按钮），两端不因排版改写文案；空态必须写清「为什么空 + 依赖表名 + 行数」，不得用「暂无数据」四字了事。
- [ ] **C2** **状态标签两端一致**：同一状态同一文案同一颜色档（状态色是双重编码，文案必须存在，不靠颜色单独传达）。
- [ ] **C3** **断点切换后的状态保持**：切换断点后，滚动位置、已加载条数、已选筛选、已展开的 L2、行尾「更多」里已勾选项**保持不变**；分页位置在「页码 ↔ 加载更多」互换时按同一 `total` 对齐（PC 第 2 页 40 条对应移动端已加载 80 条）。
- [ ] **C4** **同一操作的反馈位置一致**：toast / 内联提示的位置随「同一屏」而不是随断点跳变（例如错误提示都在操作发生的邻近位置，不出现移动端在顶部、PC 在行尾）。

### D 组 · 布局形态与禁用项

- [ ] **D1** **全端无横向滚动表格**，**全端无冻结首列**（查：代码里不存在 `overflow-x: auto` 的表格容器与 sticky 首列）。
- [ ] **D2** **移动端与平板筛选均为底部弹层**，含底部固定「重置 / 确定」；<1024 不出现右侧抽屉。
- [ ] **D3** **768~1023 不渲染 Rail**（AC-44），且不因加载 Rail 组件在内容区左侧留空白占位。
- [ ] **D4** 桌面图表门槛不因断点放松（数据点 ≥30 才画折线），且看板容器限宽 960px 居中（AC-55）——**断点不改变数据门槛，只改变排布**。

### 自查执行方式（建议）

在 `listFieldDefs.js` 旁加一个开发期断言：构建时遍历每张表格的列定义，若某列 key 不在该列表的移动端投影集合内，直接**构建失败**（AC-45 明确要求「构建期报错并禁止该列上线」）。这条把A1/A3/A5 从人工核对变成机器保证。
