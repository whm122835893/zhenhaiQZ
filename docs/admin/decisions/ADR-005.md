# ADR-005: RBAC 采用「中间件 + ACL 服务层」双层，权限点存库

## Status: Accepted (2026-07-19)

## Background

用户已锁定四类角色，必须分级：

| 角色 | 职责 | 写权限预期 |
|---|---|---|
| 平台运营 | 商品与藏品管理、二级市场监控调度 | 商品写、挂单干预 |
| 财务客服 | 用户查询、钱包只读、订单查询 | 用户写（实名审核、打标） |
| 数据观察者 | 只看板上数据 | **零写权限** |
| 内容版权审核 | `item_copyrights` 内容审核 | 版权写 |

这是标准的 **RBAC（Role-Based Access Control）**：用户 → 角色 → 权限。权限点必须**存库**而非写死在代码里，理由是四类角色的权限边界会随运营策略调整，硬编码意味着每次调整都要改代码 + 发版。

## 候选方案对比

### 方案 A：仅路由组中间件

| 维度 | 评估 |
|---|---|
| 开发成本 | 最低。复用 `->middleware()` 链 |
| 隔离性 | 一般。路由表与权限耦合 |
| 鉴权复杂度 | 低。声明即可 |
| 与 ThinkPHP 契合度 | 高。现有 `route/app.php` 就是这么用的（`->middleware(\app\middleware\AuthMiddleware::class)`） |
| 后续扩展 | **差**。权限判定只能「整组通过或整组拒绝」，做不了单端点粒度；一个 `Route::group` 里 8 个端点权限不同时只能拆成 8 个组 |
| **结论** | **否决**。粒度不够 |

### 方案 B：注解 / Gate 式（控制器方法上标 `@Permission("item:write")`）

| 维度 | 评估 |
|---|---|
| 开发成本 | 中高。PHP 需要 AOP 或注解解析机制。**ThinkPHP 8 没有内置注解路由**，要么引入 `think-annotation` 类第三方包，要么自写反射扫描——后者极易踩「静默失效」坑：注解写错键名，解析器静默跳过，权限检查**不执行**直接放行 |
| 隔离性 | 好 |
| 鉴权复杂度 | 中。权限声明离代码近，可读性好 |
| 与 ThinkPHP 契合度 | 差。项目现有代码零注解、零反射扫描，全是显式 `->middleware()` 与 `throw ApiException` |
| 后续扩展 | 中 |
| **结论** | **否决**。注解解析失败默认放行是**权限系统里最危险的失败模式**（fail-open）。且要引新依赖或自造 AOP，与「不过度设计」相悖 |

### 方案 C：中间件 + 独立 ACL 服务层（**采纳**）

分层：
```
路由（声明所需权限码）
  → AdminAuthMiddleware（认证：token + 会话有效性）
    → AdminPermissionMiddleware（授权：按权限码查 ACL 服务）
      → Controller（薄，只组装）
        → Service（业务规则，复杂判定在此显式再校验一次）
          → Model（数据读写）
```

ACL 服务 `app/admin/service/AclService.php` 是唯一读 `admin_roles` / `role_permissions` / `permissions` 的地方。`AdminPermissionMiddleware` 从路由组读声明的权限码（如 `item:write`），命中则放行，未命中抛 403 业务异常。

| 维度 | 评估 |
|---|---|
| 开发成本 | 中。1 个中间件 + 1 个服务类 + 3 张表 |
| 隔离性 | 好。权限逻辑集中在一处，不散落控制器 |
| 鉴权复杂度 | 中 |
| 与 ThinkPHP 契合度 | 高。沿用 `->middleware()` 链式声明，与既有代码风格一致；控制器内用 `$this->requirePermission('item:write')` 显式调用，**误写会在运行时报错而非静默放行**（fail-closed） |
| 后续扩展 | 好。加权限点只改数据库；将来要接 `spatie/laravel-permission` 类方案可平滑替换 ACL 服务 |

## Decision

采纳方案 C。三条设计约束：

1. **fail-closed**：所有权限判定失败一律拒绝并抛业务异常，**任何异常分支不得降级为放行**。这是 ADR-003/005 共同的红线。
2. **声明式 + 纵深防御**：路由组声明是第一道（粗粒度、挡住整组误配），控制器/服务内显式 `requirePermission()` 是第二道（细粒度、挡单点越权）。**两层都要有**，不能只有一层。
3. **权限点命名规范**：`{domain}:{action}`，domain 取自业务域（`item` / `nft` / `user` / `copyright` / `admin` / `role` / `log` / `dashboard`），action 取 `read` / `write` / `audit` / `reset` / `assign`。冒号分隔便于按前缀批量查询与按域授权。

初始权限点清单（16 个，写入 `permissions` 表种子）：

| 权限码 | 含义 | 平台运营 | 财务客服 | 数据观察者 | 内容版权审核 |
|---|---|---|---|---|---|
| `dashboard:read` | 只读看板 | 有 | 有 | 有 | 无 |
| `item:read` | 藏品列表与详情 | 有 | 有 | 有 | 有 |
| `item:write` | 藏品上下架 / 推荐位 / 价格 | 有 | 无 | 无 | 无 |
| `item:audit` | 藏品资质审核 | 有 | 无 | 无 | 有 |
| `author:read` | 作者列表与详情 | 有 | 有 | 有 | 有 |
| `author:write` | 作者资料维护 | 有 | 无 | 无 | 有 |
| `copyright:read` | 版权列表与详情 | 有 | 有 | 有 | 有 |
| `copyright:write` | 版权条目维护 | 有 | 无 | 无 | **有** |
| `nft:read` | NFT 资产与挂单列表 | 有 | 有 | 有 | 无 |
| `nft:write` | 挂单干预（下架 / 标记） | 有 | 无 | 无 | 无 |
| `trade:read` | 成交记录 | 有 | 有 | 有 | 无 |
| `user:read` | 用户列表与详情 | 有 | 有 | 有 | 无 |
| `user:write` | 用户冻结 / 解冻 | 有 | 无 | 无 | 无 |
| `user:audit` | 实名审核 | 无 | **有** | 无 | 无 |
| `admin:read` / `admin:write` / `role:write` | 账号与角色管理 | 有（仅自己） | 无 | 无 | 无 |
| `log:read` | 操作审计日志 | 有 | 无 | 无 | 无 |

补充约束：
- **「数据观察者」不挂 `AdminPermissionMiddleware` 的任何写路由组**，且角色权限集合仅 `dashboard:read` + 全部 `*:read`。双重保险。
- **禁止删除最后一个超级管理员**、**禁止管理员改自己的角色**（避免权限自降产生无法追责的状态）、**禁止角色权限集合为空的管理员登录后写入任何数据**（登录时校验：写权限集为空则只放行只读路由）。
- `admin_roles` / `role_permissions` 的变更**本身也要写审计日志**（属于 `admin_operation_logs` 的 `module='role'`）。

## Consequences

正面：
- 权限调整只改库不发版
- 控制器内显式校验，误写立即报错，不会静默放行
- 与既有 `->middleware()` 风格一致，团队零学习成本

负面：
- 每个写端点要在路由组声明 + 控制器内再声明一次，**重复但这是有意的纵深防御**，实现时须在代码评审中把"两层都写"列为检查项（否则会被后人当冗余删掉一层）
- 权限点散落在多张表的种子 SQL 里，需保持与本 ADR 表格一致；建议在 `admin_operation_logs` 之外不做额外同步，改为在 `docs/admin/ARCHITECTURE.md` 留一份权限矩阵作为唯一事实源
