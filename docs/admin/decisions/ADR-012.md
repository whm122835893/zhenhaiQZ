# ADR-012: 双端导航的权限码映射契约 + 字段集单一真源归属后端

## Status: Accepted (2026-10-22)

## Background

双端落地（ADR-010）带来两个「同一套逻辑、两套形态」的映射问题，都属于**跨端契约**，
一旦前后端各自定义就会漂移。AC-47 进一步要求「字段定义单一真源」。

## Part 1：权限码 → 导航形态的映射规则

### 问题

同一套权限码（`ARCHITECTURE.md` §6.4，共 15 个）要投影到两种导航形态：

| 形态 | 断点 | 容量约束 | 文字约束 |
|---|---|---|---|
| Rail | ≥1024px | ≤6 项 | ≤4 汉字 |
| TabBar | <1024px | **4 项（硬上限）** | ≤2 汉字 |

15 个权限码 ≫ 6 项 ≫ 4 项。必须定义**可推导的**投影规则，不能靠人工维护两张映射表。

### 候选方案

| 方案 | 描述 | 结论 |
|---|---|---|
| A. 后端下发 `navTree` 两种形态 | 后端算好 Rail / TabBar 两套结构下发 | **否决**——后端不该管「≤4 汉字」这种视觉约束 |
| B. 前端维护两份静态映射表 | 分别写死 Rail 表和 TabBar 表 | **否决**——两份表必然漂移，AC-47 精神违背 |
| C. **后端下发业务导航树 + 优先级，前端按容量裁剪**（采纳） | 后端定义业务优先级与所需权限码，前端按断点容量投影 | **采纳** |

### Decision：后端下发 `admin_nav_items` 业务导航树，前端按容量投影

后端新增 `GET /api/v1/admin/nav/items`，返回**一份**业务导航树：

```json
{
  "code": 0,
  "data": {
    "items": [
      { "key": "dashboard", "label4": "数据看板", "label2": "看板",
        "perm": "dashboard:read", "priority": 10, "path": "/admin/dashboard" },
      { "key": "item", "label4": "藏品管理", "label2": "藏品",
        "perm": "item:read", "priority": 20, "path": "/admin/item" },
      { "key": "copyright", "label4": "版权审核", "label2": "版权",
        "perm": "copyright:read", "priority": 30, "path": "/admin/copyright" },
      { "key": "user", "label4": "用户管理", "label2": "用户",
        "perm": "user:read", "priority": 40, "path": "/admin/user" },
      { "key": "trade", "label4": "成交记录", "label2": "成交",
        "perm": "trade:read", "priority": 50, "path": "/admin/trade" },
      { "key": "system", "label4": "系统设置", "label2": "系统",
        "perm": "admin:read", "priority": 90, "path": "/admin/system" }
    ]
  }
}
```

**字段契约**：

| 字段 | 含义 | 约束 |
|---|---|---|
| `key` | 稳定标识，路由与前端 state 用它，**不用 label** | 全局唯一 |
| `label4` | Rail 文案（≤4 汉字） | 后端校验长度 ≤4 |
| `label2` | TabBar 文案（≤2 汉字） | 后端校验长度 ≤2 |
| `perm` | 所需权限码 | 必须存在于权限点字典 |
| `priority` | 业务优先级，**数值小者靠前** | 整数，升序 |

**投影规则（前端执行，纯函数，两端共用一份）**：

```
1. 服务端已按当前管理员 permissions 过滤 → 前端不再重复判权
2. 按 priority 升序排序
3. <1024px：取前 4 项 → 用 label2 → 渲染 TabBar
4. ≥1024px：取全部（≤6 项）→ 用 label4 → 渲染 Rail
5. Rail 折叠态（56px）：只渲染 icon，图标须在折叠态可辨识（PM 已约束）
6. 两项都超出容量时，按 priority 保留，不做「自动隐藏低优先」
```

**关键设计点：裁剪发生在前端，后端只提供「有序全集」。**

理由：
1. 「≤4 项 / ≤2 汉字」是**视觉约束**，后端不应感知视口宽度；
2. 后端若下发裁剪后的结果，就必须知道客户端断点 → 引入设备态参数，破坏无状态；
3. 优先级 `priority` 是**业务语义**（审核 > 用户 > 成交），属后端；容量是**布局语义**，属前端。切分点正确。

**副作用（正面）**：新增业务模块时，后端加一条 `nav_items` 记录即可，
Rail 与 TabBar 自动同时生效，前端零改动——直接消灭了「加了一个页面只在一端出现」的隐患。

**路由守卫**：守卫只校验 `perm`（`meta.perm`），**不校验导航形态**。
导航形态只影响「展示哪些」，路由守卫管「能不能进」。两者正交，断点切换不涉及守卫重算。

## Part 2：字段集单一真源 —— 归属后端

### 问题

AC-45/46/47 要求：桌面列 ⊆ 移动端 L1∪L2、互为可达、唯一真源。
设计师提了前端 `listFieldDefs.js`。问题是**真源放哪**。

### 候选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A | **后端下发 field definitions**（采纳） | 派生列口径与字段定义同源；导出字段集天然对齐；权限过滤可在服务端做 | 每次列表请求都带元数据，响应体膨胀 |
| B | 前端维护单一 `listFieldDefs.js` | 零网络开销；前端改动自由 | **导出字段集要靠人工同步**；派生列口径（最近成交价等）在后端，定义在前端 → **口径必然漂移** |
| C | 独立元数据接口 | 按需拉取 | 多一次往返；缓存策略复杂 |

### Decision：后端下发字段元数据（方案 A），但**随响应内联**而非独立接口

每个列表端点的响应中，`data` 旁挂一个 `fields` 数组：

```json
{
  "code": 0,
  "data": {
    "list": [ ... ],
    "total": 36, "pageNo": 1, "pageSize": 40,
    "fields": [
      { "key": "name", "label": "藏品名", "type": "text",
        "inL1": true, "inL2": false, "inTable": true, "exportable": true,
        "formatter": "none" },
      { "key": "last_trade_amount", "label": "最近成交价", "type": "money",
        "inL1": false, "inL2": true, "inTable": true, "exportable": true,
        "formatter": "amount", "nullable": true,
        "emptyText": "无成交记录" },
      { "key": "last_trade_price", "label": "最近成交价", "type": "money",
        "inL1": false, "inL2": true, "inTable": true, "exportable": true,
        "formatter": "amount", "derived": "last_trade_price",
        "nullable": true, "emptyText": "无成交记录" }
    ]
  }
}
```

**为什么必须后端下发（三条硬理由）**：

1. **派生列的取值逻辑在后端**。最近成交价要在 `nft_trade_logs` 里按 `(iid, sold_time DESC)`
   取值（ADR-011），这不是前端能算的。若字段定义在前端、后端算值，
   「字段叫什么、什么类型、怎么格式化」与「值怎么来」就分居两处 —— AC-47 的漂移风险原样存在。

2. **导出字段集必须等于桌面可见列**（AC-53）。若定义在前端，导出接口就得多收一份
   `fields=[]` 并自行校验，白纸黑字写着「字段集与桌面可见列一致」却由客户端声明 —— 无法审计。
   定义在后端，导出接口**直接复用同一份定义**，`exportable` 标记即闸门。

3. **格式化口径必须唯一**。AC-47 举例「金额换算、时间格式化」不得两处不同。
   `formatter` 枚举由后端定义（`amount` / `datetime` / `maskPhone` / `ratio` / `none`），
   前端只做 `formatter → 渲染函数` 的查表分发，不含任何换算逻辑。
   金额单位「分→元」这类换算**只允许在后端 formatter 完成**。

**响应体膨胀的化解**：字段元数据是**静态的**（同一端点每次返回相同）。
做法：后端缓存序列化结果，前端按 `listKey + 权限组合` 缓存一份。
元数据本身约 1~2KB，相对 40 条业务数据可忽略。
**不引入独立接口**——多一次往返换不到实质收益，反而引入缓存一致性问题。

**字段集一致性由构建期校验保障（呼应 AC-45「构建期报错」）**：

后端在 `openapi.yaml` 中为每个列表端点声明 `fields`；
CI 中跑一致性检查，断言：
- 每个 `inTable: true` 的字段，其 `inL1 || inL2` 必须为 true（AC-45 桌面 ⊆ 移动）
- `exportable` 字段集 ⊆ `inTable` 字段集（AC-53）
- 同一 `key` 在两端点间 `formatter` 一致（AC-47）
任一违反 → 非零码退出，阻断构建。

### Consequences

**正面**
- 字段集真源唯一，落在**唯一拥有派生列语义的层**（后端）
- 导出字段集、桌面可见列、移动 L1/L2 三者由同一份 `fields` 投影，不可能漂移
- `formatter` 枚举化后，金额/时间/脱敏口径只有一处实现
- 新增模块只需后端加 `nav_items` + 端点 `fields`，两端自动生效

**负面**
- 响应体增加约 1~2KB 元数据
- 后端需维护 `fields` 声明与派生列实现的一致性，靠 CI 校验而非运行时
- 权限过滤下沉到后端后，前端不能再自行隐藏菜单（职责转移，需在联调文档写明）
