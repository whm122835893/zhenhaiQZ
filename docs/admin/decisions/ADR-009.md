# ADR-009: 操作审计采用「独立写路径 + 请求结束后异步落库 + 快照式请求体」

## Status: Accepted (2026-07-19)

## Background

后台是内部系统，写操作必须可追溯。审计要回答的问题：

1. 哪个管理员（`admin_id` + `username` 快照）？
2. 什么时候（精确到毫秒）？
3. 从哪个 IP、什么 User-Agent？
4. 调了哪个接口（method + path）？
5. **改了什么**（请求体与关键响应）？
6. 结果如何（成功/失败，失败原因）？

难点在于现有中间件链是**三层嵌套**（`CorsMiddleware` → `ResponseMiddleware` → `AuthMiddleware` → 控制器），且响应包络由 `ResponseMiddleware` 在**最内层之后**才封装。审计中间件插在哪一层，直接决定能不能拿到最终的 `code`（成败判定）。

## 候选方案对比

### 方案 A：复用 C 端 `ResponseMiddleware`，在里面加审计分支

| 维度 | 评估 |
|---|---|
| 开发成本 | 最低 |
| 隔离性 | **差**。C 端 93 个端点全部经过这个文件，审计逻辑一旦有 bug 影响全部 C 端响应 |
| 与 ThinkPHP 契合度 | 高 |
| **结论** | **否决**。侵入 C 端关键链路，违背「C 端零改动」的核心约束 |

### 方案 B：控制器/service 内手动调用 `AuditService::log(...)`

| 维度 | 评估 |
|---|---|
| 开发成本 | 低。每处写操作加一行 |
| 隔离性 | 中。分散在各 controller/service |
| 鉴权复杂度 | 无 |
| 与 ThinkPHP 契合度 | 高 |
| 后续扩展 | 差。**必然漏写**——新增端点时忘记加审计调用，不会有任何报错，静默丢失审计记录。这是典型的"缺失系统上下文"失效模式 |
| **结论** | **否决**。审计不能依赖开发者的自觉 |

### 方案 C：独立 `AdminAuditMiddleware`，路由组级挂载，包裹控制器执行（**采纳**）

在 `AdminAuthMiddleware` / `AdminPermissionMiddleware` **之后**、控制器之前插入审计中间件。它能同时拿到：
- 请求前的完整上下文（admin_id / IP / path / 请求体）
- `$next($request)` 的返回值——即控制器产出的业务数据

**但拿不到最终 `code`**：因为包络由更外层的 `ResponseMiddleware` 封装。本项目的解法是审计表**不存 code**，改存 `is_success`（布尔）+ `error_code`（可选，取自控制器抛出的 `ApiException` 的 `getBizCode()`，由中间件自行 catch 捕获）。

| 维度 | 评估 |
|---|---|
| 开发成本 | 中。1 个中间件 + 1 张表 |
| 隔离性 | 好。独立中间件，只挂在后台路由组，C 端链路零影响 |
| 与 ThinkPHP 契合度 | 高。沿用 `->middleware()` 链 |
| 后续扩展 | 好。新端点自动纳入审计，**不依赖开发者记得写** |

## Decision

采纳方案 C。

### 中间件位置与链路

```
CorsMiddleware            （最外，两进程共用，只读配置不改行为）
  └─ ResponseMiddleware   （两进程共用，产包络）
       └─ AdminAuthMiddleware      认证
            └─ AdminPermissionMiddleware  授权
                 └─ AdminAuditMiddleware   审计（本 ADR）
                      └─ Controller
```

**审计中间件挂载粒度**：只挂在**写路由组**（`admin/item` 的 POST/PUT/DELETE、`admin/user` 的写端点等）与**登录端点**上。只读端点不审计——否则 48 张表的操作日志会立刻淹没审计表，且只读操作无追溯价值。

### 落库时机

中间件内 `try { $result = $next($request); 写成功日志 } catch (ApiException $e) { 写失败日志; throw $e }`。

**同步写入，不用队列**：后台写操作是人工点击触发的低频操作（QPS < 1），同步写审计表的耗时（一次 INSERT，~1ms）远低于给运维排查问题时"这条操作没有日志"的代价。引入队列就意味着引入 `queue:work` 常驻进程，与「PHP built-in server 单进程」的现状不匹配。

**失败不阻断业务**：审计写入失败时，用 `Log::error()` 记录，**不抛异常**。理由：审计是旁路观察者，不能因为它坏了就让运营的正常操作失败。但这构成一个权衡——审计可能丢记录。缓解手段是 `Log::error` 会留痕，且 Spec 中把"审计写入失败"列为必须告警的条件。

### 请求体快照与脱敏

**必须记录** `request_params`（JSON 文本）。但以下字段**必须脱敏**后再存：

| 字段 | 脱敏方式 |
|---|---|
| `password` / `oldPassword` / `newPassword` | 整值替换为 `***` |
| `confirmPassword` | 整值替换为 `***` |

这是硬约束：审计表会被运营和第三方看到，明文密码落库是安全事故。

请求体超过 8KB 时截断并在末尾追加 `...[truncated]`，避免审计表被超大内容（图片 base64、长 HTML 富文本）撑爆。

## Consequences

正面：
- 审计与 C 端链路完全隔离，`app/middleware.php` 不动
- 挂载即生效，新增端点不会漏审计
- 低频场景下同步写入，逻辑简单无队列依赖

负面 / 必须注意：
- **审计表不存 `code`**，存 `is_success` + `error_code`（中间件自行 catch `ApiException` 取 `getBizCode()`）。这与 ADR-004 的错误码体系有轻微不对称，实现时需在表注释里写明，避免后人误以为漏了字段
- 审计写入失败会被吞掉（只 Log），这是有意权衡。Spec 的端到端验证必须包含"人为让审计写入失败 → 确认业务仍成功且 Log 有 error"
- `request_params` 必须脱敏。这是最容易在赶工时漏掉的一步，代码评审列为必查项
