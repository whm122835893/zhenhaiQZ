# ADR-010: 后台形态从「移动端 + PC 设备框」改为「真双端（移动 / 平板 / 桌面）」

## Status: Accepted (2026-10-21)

## Background

后台第一版设计（2026-10-20 验收）的形态是**单端 + PC 设备框**：

- 断点只有一个 768px
- `<768px` 满宽铺满
- `≥768px` 套一个 `max-width: 430px` 的居中设备框（`--admin-frame-max` + 圆角裁切 + 阴影），外侧露工作台底色

这个方案在 PC 浏览器上打开时，**呈现的仍然是手机布局**——只是套了个框。它解决的是「不失真地预览手机端」，不是「PC 上也能用」。

同期 PRD 的绝大部分硬约束（Tab ≤4 且 ≤2 汉字、列表首屏只露 3~4 字段、操作按钮不放行尾、六列表单不分页、筛选收进弹层、看板只给指标卡 + 横向条形、成交记录横向滚动表）都是**基于 390px 单端推导**的。其中**成交记录横向滚动表**与**移动端筛选形态**两项已在 v1.3 按AC-29 / AC-33 / AC-57 修正为跨端统一结论，见下节「修订记录」。

2026-10-21 总监决策变更：**后台要双端能用——PC 电脑和手机都要能正常用。**

触发这次变更的还有一条此前已记录但理由已失效的预留：`admin-tokens.css` §4 里写着「侧边 Rail 为 ≥1024px 宽屏预留，MVP 默认关闭（关闭原因：390px 内容宽下侧边栏会吃掉 200px，与『移动端形态』冲突）」。该关闭理由只对单端成立，桌面端有 1280px 宽，侧栏不吃内容宽度。

## 候选方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 维持设备框** | 保持 768px 单断点，PC 上继续套 430px 框 | 零改造成本；移动端像素级稳定 | PC 上不可用（运营在 1440px 屏幕上看一个 390px 的框）；PRD 硬约束全部合理化但等于放弃 PC 端 | **否决**——与「双端能用」的目标直接冲突 |
| **B. 真双端（采纳）** | 三断点 768 / 1024 / 1280；移动端卡片流、平板居中放宽、桌面 Rail + 两栏 + 表格 | 移动端像素级不变（不推翻已验收成果）；PC 端信息密度与操作效率达标；复用全部既有令牌组织方式 | 列表组件要两套实现；移动端硬约束需逐条重新判定（分 10 条 + PRD S1~S8 复核） | **采纳** |
| **C. 只做移动优先自适应**（不做表格，仅把卡片居中放宽） | 断点扩到 3 个，但列表仍是卡片流 | 改造量小 | 1440px 下仍是单列长卡片，字段仍只有 3 个，PC 端体验与手机无差别，只是「更宽的卡片」 | **否决**——不构成「双端」，只是把手机布局拉宽 |
| **D. 移动端一并改成响应式** | 两端同步改造，移动端也用表格 | 形态统一 | 推翻已验收的列表卡片三槽位决策（移动端表格在 390px 下不可用）；PRD S1/S3/S8 的减法全部作废 | **否决**——成本最高且损害已验收成果 |

## Decision

**采纳方案 B。形态改为双端，落地为三个断点。**

### 1. 断点

| 断点 | 视口 | 形态 | 一级导航 | 布局 |
|---|---|---|---|---|
| `<768px` | 移动 | 移动端 | 底部 TabBar | 单列满宽，卡片流 |
| `768~1023px` | 平板 | 平板 | 底部 TabBar | 单列居中，内容宽上限 640px |
| `≥1024px` | 桌面 | 桌面 | 侧边 Rail 200px（可折叠 56px） | 两栏，总宽上限 1440px，内容块上限 1216px |
| `≥1280px` | 桌面宽屏 | 桌面 | 同上 | 结构不变，只放宽内容块 |

### 2. 令牌层变更

- **删除**：`--admin-frame-max` / `--admin-frame-pad` / `--admin-frame-radius` 三条设备框令牌及 `#app` 的 `box-shadow` / `border-radius` / `overflow:hidden` 裁切。
- **新增**：断点值、容器宽上限、桌面两栏栅格、Rail 全套（折叠态宽、指示条、分组标题、折叠按钮位）、PC 表格列宽变量、PC 列表行变量、PC 筛选条变量、PC 指标卡变量、PC Dialog 变量。
- **启用**：`--admin-rail-*`（原为预留关闭）。
- **新增唯一字号**：`--admin-fs-dense: 14px`（仅 ≥1024 的密集数据位；阅读位正文仍 16px）。
- **零新增品牌色 hex**；新增的表面色全部走既有 `--admin-surface-*` 语义别名，深色主题在 §17 覆盖。
- **保留**：`@import` 单一真源、零 C 端数值字面量复制、列表卡片三槽位、审计时间线纵向 diff、全部 `--admin-*` 分层组织方式。

### 3. 移动端硬约束的处置原则：分层，不全放开

| 类别 | 处置 |
|---|---|
| 与屏宽无关的（详情页 Tab ≤4、字段三级下沉、不臆造数据、状态双重编码） | **两端不变** |
| 因屏宽而设的（首屏字段数、行尾操作、筛选形态、列表分页） | **按明确依据放宽，给出上限值** |
| 因风险而设的（高危操作必须二级确认、导出仅 ≥768、批量操作移出 MVP） | **两端不变**，不因 PC 有鼠标就放松 |

### 4. 关键裁决

1. **PC 正文 14px 不全局采纳**。改为「阅读位 16px / 密集位 14px」分档。理由：16px 中文正文在 1216px 内容宽下已接近 75 字符可读上限，缩到 14px 反而把行长推到 80+，且中文小字笔画粘连；密度问题应在密集数据位解决。
2. **折线图的数据门槛不因断点改变**。PRD §9.3 的样本量约束（成交 10 条 / 用户 36 条）在 PC 端同样成立——屏幕变宽只让「假趋势」画得更专业。折线仅在数据点 ≥30 时启用，两端同时解锁，不做端侧差异。
3. **成交记录的横向滚动表全端取消（v1.3 修订）**。本 ADR 初版结论为「桌面端撤销移动端特例」，现修正为**该特例本身被取消**：<1024 走卡片流（L1 四主字段：藏品名 / 成交价 / 买卖双方脱敏 / 成交时间），≥1024 为 6 列表格，**全端不保留横向滚动与冻结首列**（AC-29 / AC-57）。取消的真正理由不是「1216px 足以平铺 6 列」，而是**横向滚动在窄视口内容不可发现**。横向比价改由「按成交价单列排序」等价实现。
4. **批量操作双端都不做**（Q12 维持）。但 PC 端「全选当前筛选结果」的语义必须在 UI 上写明，避免运营误以为只选了当前页。
5. **看板是最需要妥协的功能**：信息量由数据决定，不由断点决定。PC 端不设「专属三栏版」，与移动端共用同一套降级后的可视化集合，只改排布。详见 `RESPONSIVE.md` §5。

## 修订记录（2026-10-22，v1.3 跨文档冲突修正）

本 ADR 初版有**两处结论以「端侧特例」措辞表述，实际应为跨端统一**，已修正：

| 项 | 初版结论 | v1.3 修正 | 依据 |
|---|---|---|---|
| 成交记录横向滚动表 | 「移动端保留、桌面端撤销」（唯一一处 PC 撤销） | **全端取消**：<1024 卡片流，≥1024 六列表格，全端无横向滚动、无冻结首列 | AC-29 / AC-57；横向滚动在窄视口内容不可发现 |
| 移动端筛选形态 | 「右侧抽屉，宽 `calc(100% - 56px)`」 | **底部弹层**（<1024，含底部固定「重置/确定」） | AC-33；拇指可达区在屏幕下半部，56px 露边在390px 下是误触区 |
| 列表分页阈值 | 「PC 25 / 移动 50」 | **跨端统一 40** | AC-27；末页 11 行 ≈ 半屏空白会被误读为「数据没加载完」（同PRD §9.2 类错误） |
| md 区间不上 Rail 的论证 | 「820 − 200 = 364px，比移动端 390px 还窄」（算术错误） | 结论不变，理由改为**内容区净收益 −20px（640 → 620）+ 旋转换形态** | PRD v1.3 §17.1 / AC-44 |

**方法论教训（写入本 ADR）**：本 ADR 初版把三处设计写成「端侧特例 = 一端成立、另一端撤销」。这类措辞会在实现阶段变成歧义来源。**判定规则**：若某设计的存废依据是「屏幕窄/宽」这一物理条件，且窄屏侧本身就是缺陷（内容不可发现、误触区、无查找能力），则该设计应**全端取消**，而不是「窄屏保留 + 宽屏撤销」。真正合法的端侧差异只有两类：**① 同一信息的不同排布**（卡片↔表格、弹层↔筛选条）；**② 指针 vs 触摸的交互物理差异**（行尾操作列、hover、44px 触摸目标）。**「因为宽所以撤销」不是合法理由，「因为窄所以不可发现」才是。**

## Consequences

正面：
- PC 端从「不可用」变为「主力工作面」，运营的审核、比价、导出生效
- 移动端零回归风险（<768px 渲染结果与改造前逐像素一致）
- 令牌体系仍然单源，新增桌面能力不引入新的颜色或间距体系
- 折线图门槛、批量操作、高危确认三条约束在双端下保持一致，审计口径不分裂

负面 / 必须注意：
- **列表组件要两套实现**（`ListCard` / `DataTable`）。必须消费同一份字段定义，否则移动端与 PC 端列口径会漂移——这是双端化最主要的工程风险。
- **PC 端表格 8 列 vs 移动端 4 字段的可见性差异不可消除**。缓解手段是「PC 列必须是 L1+L2 的子集」，保证移动端可达。
- **平板横竖屏会切换导航形态**（iPad 横屏落 lg 拿 Rail，竖屏落 md 拿 TabBar）。这是断点方案的固有代价，靠 Rail 折叠态 56px 缓解。
- **md 区间（768~1023）失去 hover 反馈**（触屏与鼠标同区间，无法可靠区分），这是取舍不是缺陷。
- **14px 中文在深色主题下的对比度需单独复核**（`--admin-fg` / `--admin-fg-2` 在 dark 下与 14px 的组合）。
- 团队需新增一条回归基线：移动端截图基线（<768px）+ 桌面端三断点截图基线。
