# ADR-007: C 端隔离用「影子覆盖表 + is_local_override 标记」，不 ALTER 现有 48 张表

## Status: Accepted (2026-07-19)

## Background

用户锁定的决策：本地库可写，但**必须与 C 端数据隔离**——运营写操作带 `is_local_override` 标记，不污染 C 端展示数据。同时约束**不改动现有 48 张表的结构**（C 端已在跑）。

这两条要求之间存在真实张力，必须先解决：

`is_local_override` 作为一个字段，最自然的落点是直接 `ALTER TABLE items ADD COLUMN is_local_override tinyint(1) NOT NULL DEFAULT 0`。但这会改动 C 端主表结构，违反约束。而且更严重的是：**即使加了字段，只要不修改 C 端的 SELECT，C 端依然读不到后台的改动**——即后台写进去了，C 端看不到，两套数据静默分叉。这比"污染"更糟：运营以为改完了，验收时发现 C 端没变。

反过来，如果改了 C 端的查询（加 `COALESCE(override.x, items.x)`），就动了 C 端 93 个端点的数据来源，回归面覆盖全部藏品/挂单/成交展示——逐像素复刻项目不允许这种风险。

## 候选方案对比

### 方案 A：ALTER 现有表加 `is_local_override` 列，C 端查询不改

| 维度 | 评估 |
|---|---|
| 开发成本 | 最低 |
| 隔离性 | **假隔离**。标记加了，但 C 端读不到，两套数据静默分叉 |
| 鉴权复杂度 | 无 |
| 与 ThinkPHP 契合度 | 高 |
| 后续扩展 | 差 |
| **结论** | **否决**。满足字面要求但违背意图——这是典型的"看起来做了隔离、实际制造了数据分叉" |

### 方案 B：ALTER 现有表 + 同步修改 C 端查询做 COALESCE 合并

| 维度 | 评估 |
|---|---|
| 开发成本 | 高。48 张表里所有需要覆盖的表都要改，且 C 端每个读这些表的端点都要改 |
| 隔离性 | **不隔离**。C 端展示数据直接被后台改动影响 |
| 与 ThinkPHP 契合度 | 中。侵入既有查询 |
| 后续扩展 | 中 |
| **结论** | **否决**。直接违反「不污染 C 端展示数据」这条硬需求，且回归面覆盖全部 C 端端点 |

### 方案 C：新增影子覆盖表，表内含 `is_local_override` 标记（**采纳**）

| 维度 | 评估 |
|---|---|
| 开发成本 | 中。新增表 + 一层合并读取服务 |
| 隔离性 | **真隔离**。C 端 SQL 一字不改，永远读不到后台数据；后台读走「基础表 + 覆盖表」合并结果 |
| 鉴权复杂度 | 无额外 |
| 与 ThinkPHP 契合度 | 高。新增 model 与 service，零框架改动 |
| 后续扩展 | 好。覆盖表是标准 overlay 模式，将来要做"灰度预览""多环境差异化"可直接扩展 |

## Decision

**采纳方案 C：影子覆盖表（Shadow Override Table）。**

核心不变式（三条，违反即退回）：

1. **C 端零改动**：现有 48 张表的 DDL 不动，C 端控制器与查询一字不改，C 端永远只读基础表
2. **覆盖表自带 `is_local_override`**：字段语义是"这一行是后台运营写入的覆盖值，不是源站数据"，恒为 1，作为后台数据血缘标记与审计锚点
3. **后台读 = 基础表 LEFT JOIN 覆盖表**，写入**只写覆盖表**，永不 UPDATE 基础表

### 落地机制

**覆盖范围（只覆盖后台 MVP 会写到的表，其余一律不覆盖）**：

| 覆盖表 | 对应基础表 | 后台可覆盖字段 | 理由 |
|---|---|---|---|
| `admin_item_overrides` | `items` | `status` / `is_recommend` / `is_popular` / `price` / `is_secondary` / `is_secondary_batch` | 后台 MVP 功能①商品与藏品管理 |
| `admin_copyright_overrides` | `item_copyrights` | `name` / `image` / `image_url` / `sort` | 后台 MVP 功能③内容版权审核 |
| `admin_author_overrides` | `item_authors` | `name` / `avatar` / `avatar_url` / `introduction` | 作者资料维护 |

**明确不覆盖的表**（后台对这些表**只读**，不做任何后台侧写操作）：

- `users` / `user_profiles` / `user_wallets`：用户与实名审核功能只改 `users.status`（冻结/解冻）与 `users.has_real_name`，这两列**是 C 端自己定义的状态字段**（C 端登录与实名流程都读它们），后台改这两个字段属于"运营行使 C 端既有业务能力"，不属于覆盖 C 端数据。**这三张表不建覆盖表**。
- `nfts` / `nft_sell_orders` / `nft_trade_logs`：二级市场监控功能在 MVP 是**只读监控 + 挂单标记**。挂单干预（下架）通过覆盖表 `admin_sell_order_overrides` 的 `admin_status` 字段实现，不改 `nft_sell_orders.status` 本身（C 端用户的下架操作会写基础表，后台标记与 C 端状态是两回事）。

### 字段类型与幂等

`is_local_override` 在三张覆盖表上统一定义：

```
is_local_override  tinyint(1)  NOT NULL DEFAULT 1  COMMENT '恒为1：后台运营写入的本地覆盖值'
```

恒为 1，不做 0/1 切换——存在即覆盖。这个设计避免了"字段存在但值为 0"的中间态（那是最容易产生静默逻辑错误的地方）。

**幂等键与冲突处理**：

| 机制 | 设计 |
|---|---|
| 幂等键 | 每张覆盖表以 `(target_id, field_key)` 建唯一索引。同一条记录的同一字段重复写入 → `INSERT ... ON DUPLICATE KEY UPDATE`，天然幂等 |
| 粒度 | **字段级**覆盖（`field_key` + `field_value`），而非整行覆盖。运营只改推荐位时，不会把价格、状态等未读字段用默认值覆盖回去 |

这里字段级粒度是必须的：整行覆盖在后台表单只提交部分字段时会静默清空未提交字段——典型的静默逻辑错误。

```
admin_item_overrides
  id              bigint unsigned PK（雪花）
  target_id       bigint unsigned NOT NULL   -- items.id
  field_key       varchar(64)   NOT NULL     -- 'status' | 'is_recommend' | ...
  field_value     varchar(512)  NOT NULL     -- 覆盖后的值（统一字符串，按 field_key 转型）
  is_local_override tinyint(1)   NOT NULL DEFAULT 1
  admin_id        bigint unsigned NOT NULL   -- 最后写入的 admin
  op_log_id       bigint unsigned NOT NULL DEFAULT 0  -- 关联 admin_operation_logs.id
  created_at / updated_at datetime
  UNIQUE KEY uk_item_override (target_id, field_key)
```

**冲突处理规则**：

| 场景 | 处理 |
|---|---|
| 同一 admin 重复提交同一字段 | 幂等，`updated_at` 刷新，不产生第二条记录 |
| 不同 admin 先后改同一字段 | 后写覆盖（last-write-wins），**但 `admin_operation_logs` 保留两条记录**，可追溯谁在什么时候改的 |
| 运营清除某字段的覆盖（恢复源站值） | `DELETE` 该 `(target_id, field_key)` 记录，不是写入空值。避免"覆盖为空"和"未覆盖"两种状态无法区分 |
| 后台读到的覆盖记录指向已删除的基础行 | 读时过滤 `NOT EXISTS` 基础行；覆盖记录由后台写时校验基础行存在，不产生孤儿 |

**并发控制**：覆盖表更新带 `WHERE id = ?` 的乐观锁（`version` 列或用 `updated_at` 比对）。冲突返回 `14009`（ADR-004 新增的 `CODE_CONFLICT`），前端提示刷新。**不使用数据库行锁**——覆盖表写入是低频操作（人工点击），行锁的收益不抵其带来的死锁风险。

## Consequences

正面：
- C 端 48 张表 DDL 零改动，93 个端点的回归基线完整保留
- 隔离是**结构性的**（不同表），不是靠约定维持的纪律
- 字段级粒度 + 唯一索引，天然幂等
- 覆盖表带 `admin_id` + `op_log_id`，每次写入的来源可直接追到审计日志

负面 / 必须注意：
- 后台读列表需要 LEFT JOIN 或「先查覆盖表再在应用层合并」两种策略。数据量小时（`items` 仅 5 行、`item_copyrights` 6 行）采用**应用层合并**：一次查基础表 + 一次查当前页涉及的覆盖记录，在内存里按 `(target_id, field_key)` 覆盖。避免 N+1 与复杂 SQL
- 覆盖表会持续增长（每个字段一行）。后台提供"清除覆盖"操作，`item_copyrights` 有 6 条脏数据（`1`、`1` 重名）需要清理，会产生较多覆盖行——需后台提供批量清除入口
- **`op_log_id` 形成循环依赖**：审计日志要记"改了 items.status"，覆盖表要记"对应哪条日志"。解法是**先写日志拿到 id，再写覆盖表**（日志表主键为雪花 ID，由应用生成，写入时即已知），不构成事务循环。这条必须在实现时按此顺序，否则会出现日志 id 为 0 的空引用
