# ADR-003: 后台鉴权采用 Access Token + 服务端会话表（Session Table），不用纯无状态 JWT

## Status: Accepted (2026-07-19)

## Background

后台是内部系统，两条硬需求与 C 端截然不同：

1. **登出即失效**：C 端 token 是 7 天无状态 JWT（`config/shengtai.php` 的 `jwt.ttl = 604800`），用户登出后 token 在有效期内**仍然可用**——这对公开商城可以接受，对后台不行。后台管理员误登出、或怀疑账号泄露时，必须能立即断掉会话。
2. **操作审计可追溯**：写操作必须能回答"哪个 admin、什么时候、从哪个 IP、调了哪个接口、改了什么"。这要求 token 之外还必须有一份服务端可查询的会话记录。

现有 `app/helper/Jwt.php` 是零依赖手写 HS256 实现（`Jwt::encode` / `Jwt::decode` / `Jwt::uid`），已用于 C 端 `AuthMiddleware`。`Jwt::decode` 只验签名与 `exp`，**无 `jti` 黑名单机制**，注释里也写明"若要防重放需在 payload 加 jti 并落库，这里当前场景够用"。后台不能用这个假设。

## 候选方案对比

### 方案 A：纯无状态 JWT（沿用 C 端 Jwt.php + 独立 secret）

| 维度 | 评估 |
|---|---|
| 开发成本 | 最低。直接复用现成 helper，零新表 |
| 隔离性 | 好。独立 `admin.jwt_secret`，与 C 端 `JWT_SECRET` 不同值，跨端 token 互相无法验签 |
| 鉴权复杂度 | 低。无状态，多实例天然可扩 |
| 与 ThinkPHP 契合度 | 高。零改动 |
| 后续扩展 | 差。**无法登出即失效**（除非加黑名单表，那就退化成方案 B）；无法直接查询"当前在线的管理员" |
| **结论** | **否决**。直接违反「登出即失效」这条硬需求 |

### 方案 B：服务端 Session（PHP 数组 / 文件 / Redis）

| 维度 | 评估 |
|---|---|
| 开发成本 | 低。TP 有 Session 组件 |
| 隔离性 | 好 |
| 鉴权复杂度 | 低。查一次即得会话 |
| 与 ThinkPHP 契合度 | 高 |
| 后续扩展 | **差**。PHP 内置 server 单进程下 Session 落文件尚可，但一旦后台迁 php-fpm 多 worker，需改 Redis；且 Session ID 走 Cookie，与后台"用 Authorization 头"的既有前端约定不一致（`AuthMiddleware::extractToken` 已支持 `token` query 参数兜底，但把长期凭证放 query 会进 access log，是安全反模式） |
| **结论** | **否决**。Cookie 承载凭证 + 需要额外 Session 存储，是用一个新问题换掉旧问题 |

### 方案 C：Access Token + 服务端会话表（**采纳**）

Token 仍是无状态 JWT（复用 `Jwt::encode`），但 payload 里加 `jti`（会话 ID）与 `aid`（管理员 ID）；每次鉴权**除验签外还要查一次 `admin_sessions`** 判断该 jti 是否仍有效（未登出、未被顶号、未过期）。会话记录本身就是审计的第一手材料。

| 维度 | 评估 |
|---|---|
| 开发成本 | 中。新增 1 张表 + 1 个中间件；`Jwt.php` 需新增 `encodeWithJti()` 与 `decodePayload()` 两个静态方法（**不改动现有 `encode/decode/uid` 的签名**，C 端 93 个端点依赖它们） |
| 隔离性 | 好。独立 secret + 独立会话表 + 独立中间件 |
| 鉴权复杂度 | 中。每次请求多一次 `admin_sessions` 查询。**必须加索引** `idx_sessions_jti(jti)`，否则后台每请求全表扫 |
| 与 ThinkPHP 契合度 | 高。TP 的中间件机制与现有 `AuthMiddleware` 完全同构，只是多一步查表 |
| 后续扩展 | 好。`admin_sessions` 表天然支撑"踢人下线""登录设备列表""异地登录提醒"；将来要接 Redis 只需把这一处查询换成 Redis |

## Decision

采纳方案 C，具体参数：

| 项 | 值 | 理由 |
|---|---|---|
| 算法 | HS256（复用 `app/helper/Jwt.php`） | 与 C 端一致，零新依赖 |
| secret | `env('ADMIN_JWT_SECRET')`，与 `JWT_SECRET` **必须不同值** | 跨端 token 隔离 |
| Access Token TTL | 2 小时 | 后台不需要 7 天长会话；缩短泄露窗口 |
| 会话绝对有效期 | 8 小时（`admin_sessions.expire_at`） | 跨过夜必须重新登录 |
| Refresh Token | **MVP 不做** | 见下方"明确不做" |
| 传输 | `Authorization: Bearer {token}` | 复用 `AuthMiddleware::extractToken` 已验证的三种兼容写法 |
| 登出 | `POST /admin/auth/signout` → `admin_sessions.status=1` + `revoke_at` 落库 | 登出即失效 |
| 顶号 | 同账号新登录时，把该 admin 其他活跃会话置 `status=1`，`revoke_reason='new_login'` | 可解释的强制下线 |
| 密码 | `password_hash` + 独立 `salt`，算法与 C 端一致（TP 内置 `password_hash`/`password_verify`） | 不引入新依赖 |

权限点校验：**在 `AdminAuthMiddleware` 之后独立一层 `AdminPermissionMiddleware`**，由路由分组声明所需权限码（如 `item:write`），中间件查 `admin_sessions` 已挂的 `permissions` 集合（登录时一次性载入并挂 request，避免每请求三表 join）。**只读角色（数据观察者）** 走独立路由组，只挂 `AdminAuthMiddleware`，其权限集合为空即可天然只读——不给它挂 `AdminPermissionMiddleware` 的写端点，是比"在控制器里判权限"更可靠的第一道防线（第二道才是控制器/service 内的显式校验）。

## 明确不做（out-of-scope）

- **不做 Refresh Token 轮换**：JWT helper 无 jti 黑名单，引入 refresh 会显著扩大攻击面；MVP 阶段 Access Token 2h + 会话表 8h 已覆盖内部系统需求，重新登录成本可接受
- **不做多因子认证**：内部系统 + MVP，不做
- **不做密码策略强度校验器**：只做最小长度 8 位（与 C 端一致），不做复杂度正则堆砌
- **不引入 `firebase/php-jwt` 等第三方 JWT 库**：现有零依赖实现够用，引入新依赖需过存在性核验

## Consequences

正面：
- 登出即刻生效，满足内部系统硬需求
- `admin_sessions` 天然支撑审计查询与在线管理员列表
- 复用现有 `Jwt.php`，C 端零改动

负面 / 必须注意：
- 每请求多一次 DB 查询——**这是为「登出即失效」付的必要成本**，必须在 `admin_sessions.jti` 上建唯一索引，否则是隐性性能坑
- **`Jwt.php` 是 C 端与后台的共享文件**，任何修改都需双向回归。本次新增方法必须**只增不改**：现有 `encode`/`decode`/`uid` 的签名与行为一字不动
- `admin_sessions` 只在后台 8922 进程被访问；**若将来后台横向扩容需换共享存储**（Redis 或独立库），这是已知边界，MVP 单进程不触发
