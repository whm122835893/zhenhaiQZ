# ADR-002: 后台 API 独立 8922 端口，与 C 端 8921 并行进程

## Status: Accepted (2026-07-19)

## Background

现状（实测确认）：

- C 端后端 = ThinkPHP 8.1.4，`php -S 0.0.0.0:8921 -t public`，`pid=92891` 在跑
- 路由表 `route/app.php` 共 93 个端点，**无 `/api` 前缀**（严格对齐源站 `api.shengtai.cyou` 真实路径，如 `/item`、`/nft/secondary/:iid`）
- C 端 `vite.config.js` proxy：`'/api' → http://127.0.0.1:8921`，rewrite 掉 `^/api`
- 全局中间件只有两个：`CorsMiddleware`（最外）→ `ResponseMiddleware`（包络）

C 端路由表是**照着源站真实路径逐条对齐**的产物，任何后台路由混进 `route/app.php` 都会引入两个真实故障：

1. **路由抢占**：`route/app.php` 已因 `nft/secondary/sell` 与 `nft/secondary/:iid` 的顺序问题打过补丁（见文件内注释第 43-54 行），后台路由继续加进同一张表会持续放大这类首匹配命中的维护成本
2. **包络污染**：后台若不用 C 端包络，会被 `ResponseMiddleware` 二次包装；`isEnvelope()` 判定要求恰好含 `status/code/message/data` 四键且 `status` 为 bool，业务数据里出现这四键即误判

另外 `App::$runtimePath` 在框架内被**硬编码**为 `rootPath/runtime`（`vendor/topthink/framework/src/think/App.php:183`），单进程单入口下若后台与 C 端共用同一入口，日志与缓存文件会互相覆盖。

## 候选方案对比

### 方案 A：同进程 8921，后台路由挂在 `route/admin.php`，由 `Route::group('/admin', ...)` 挂载

| 维度 | 评估 |
|---|---|
| 开发成本 | 最低。零启动配置，controlller 目录同级新增 `controller/admin/` |
| 隔离性 | 差。共享 `CorsMiddleware` 全局中间件；共享 `runtime/`；后台若要返回非包络响应需改 `ResponseMiddleware`，这是 C 端全链路依赖文件，改动波及 93 个端点 |
| 鉴权复杂度 | 中。`AuthMiddleware` 挂在 group 上，后台要新挂一个 `AdminAuthMiddleware`，两个 group 各挂一个，ThinkPHP 支持，无额外成本 |
| 与 ThinkPHP 契合度 | 高。路由表热加载，改完即生效，调试无需重启进程 |
| 后续扩展 | 差。后台要做文件上传、导出 Excel、长耗时报表，与 C 端共用 PHP built-in server 的**单进程单线程**模型必然互相拖累；built-in server 本来就不适合生产，后台内网直连后压力会直接打到 C 端 |
| **结论** | **否决** |

### 方案 B：独立 8922 端口，同一份 ThinkPHP 代码，第二份入口 + 第二份运行时目录（**采纳**）

| 维度 | 评估 |
|---|---|
| 开发成本 | 中。新增 `public/admin.php`（约 40 行样板）+ `route/admin.php`，无新依赖、无 composer 变更 |
| 隔离性 | 好。独立进程、独立 `runtime/admin/`、独立路由表。`CorsMiddleware` 通过 `Config::get('shengtai.cors')` 读配置，两进程读同一份配置，但后台进程可用 `CORS_ORIGINS` 环境变量收窄白名单 |
| 鉴权复杂度 | 中。后台独立 `AdminAuthMiddleware`，与 C 端 `AuthMiddleware` 无共享状态 |
| 与 ThinkPHP 契合度 | 高。`App::setRuntimePath()` 是框架公开方法（`App.php:384`），入口里显式调用即可 |
| 后续扩展 | 好。后台可随时切 php-fpm / nginx 而不动 C 端进程；C 端零感知 |
| **结论** | **采纳** |

### 方案 C：后台后端另起独立技术栈（如 Node/Nest.js）

| 维度 | 评估 |
|---|---|
| 开发成本 | 高。新增一整套运行时、两套 ORM、两套连接池、跨语言类型对齐 |
| 隔离性 | 最好（进程级 + 语言级） |
| 鉴权复杂度 | 低（JWT 中间件生态成熟） |
| 与 ThinkPHP 契合度 | 差。后台要读写 `shengtai` 库的 48 张 C 端表，等于在 Node 侧重建一遍 ORM 映射与全部字段语义（尤其 `sold_price` / `price` 这类单位不一致的列），幻觉风险高 |
| 后续扩展 | 好 |
| **结论** | **否决**。违反"不过度设计"：MVP 阶段引入第二种后端语言，只为隔离一个进程边界，用两个入口文件就能解决的事不该付这个代价 |

## Decision

**采纳方案 B**。启动方式与既有约定完全对齐（同样是 php built-in server）：

```bash
# 示例：C 端（现状，不动）
php -S 0.0.0.0:8921 -t public

# 示例：后台（新增）
php -S 0.0.0.0:8922 -t public public/admin.php
```

`public/admin.php` 职责**只有三件**，不做任何业务（对齐 `code-organization.md` 硬规则 4「入口文件只装配」）：

1. `require __DIR__ . '/../vendor/autoload.php'`
2. `$app = new \think\App(); $app->setRuntimePath(rootPath . 'runtime/admin/');`
3. 加载 `route/admin.php` 后 `$http->run()`，收尾 `ob_end_flush()` 兜底

同理复制 `public/router.php` 为 `public/router-admin.php`，使 `php -S` 的静态文件短路逻辑一致。

C 端 `/api` 与后台 `/admin-api` 的关系：两套完全独立的前端 proxy，不共享 rewrite 逻辑。`admin-web/vite.config.js` 里 `/admin-api → http://127.0.0.1:8922`，rewrite 掉 `^/admin-api`（后台路由表**自带** `/admin` 前缀，见 ADR-004），因此后台实际路径是 `/admin/xxx`。

## Consequences

正面：
- C 端 8921 进程与 `route/app.php` 零改动，93 个端点的回归基线完整保留
- 后台可随时换 php-fpm，C 端不受牵连
- `runtime/admin/` 独立，后台日志与 C 端日志不互相覆盖

负面 / 必须注意：
- **`App::setRuntimePath()` 必须在 `$http->run()` 之前调用**，否则后台日志写入 `runtime/log/` 与 C 端混文件，事后无法区分是谁产生的
- 两个 php built-in server 进程是**两个 OS 进程**，前台启停要成对管理
- **开发期跨域**：两个进程不同端口，若 `admin-web` 跑在 5174 而后台在 8922，浏览器会发 OPTIONS 预检。后台进程必须设置 `CORS_ORIGINS=http://127.0.0.1:5174`（**不能用默认的 `null`**，后台是内部系统，回显任意 Origin 等于把审计接口暴露给任何站点）
- **生产期**：建议后台用独立子域名（如 `admin.shengtai.cyou`）+ nginx 反代到 8922 的 php-fpm，从根上消除跨域；此时 `CORS_ORIGINS` 可留空（同源不发预检）
