# ADR-008: 两个 PHP built-in server 进程，runtime 目录显式隔离

## Status: Accepted (2026-07-19)

## Background

现状：C 端后端以 `php -S 0.0.0.0:8921 -t public` 运行，`pid=92891`，长期在线运行中。

后台需要第二个监听端口（ADR-002）。两个 PHP built-in server 进程指向**同一份代码目录** `/workspace/server/shengtai-api`，因此共享：

- `vendor/`（同一份依赖，无法也不必隔离）
- `app/`（同一份代码——这是 ADR-002 方案 B 的代价，见该 ADR）
- **`runtime/`（风险点）**

## 关键风险：runtime 目录共享

框架源码 `vendor/topthink/framework/src/think/App.php:183` 实测：

```php
$this->runtimePath = $this->rootPath . 'runtime' . DIRECTORY_SEPARATOR;
```

`rootPath` 相同 → **两个进程 runtime 路径完全相同**，未做任何隔离。以下内容会互相覆盖：

| runtime 子目录 | 内容 | 冲突后果 |
|---|---|---|
| `runtime/log/` | 按日期分文件的日志 | 后台日志写入与 C 端日志混在同一文件，无法区分来源；两进程同时写有并发追加风险 |
| `runtime/cache/` | 路由缓存、配置缓存、模板缓存 | 若开启路由缓存，后台新加的路由不生效（缓存被 C 端进程先写入且不含后台路由） |
| `runtime/temp/` | 模板与中间文件 | 清理逻辑互相影响 |
| `runtime/config.php` | 运行时生成的配置缓存 | 后台进程可能读到 C 端进程写入的版本 |

框架提供了公开方法 `App::setRuntimePath(string $path)`（`App.php:384`），可在 `$http->run()` 之前改写。

## Decision

**新增 `public/admin.php` 作为后台入口，在其中显式调用 `$app->setRuntimePath()` 把后台的 runtime 目录指向 `runtime/admin/`。**

`public/admin.php` 的完整职责（对齐 `code-organization.md` 硬规则 4「入口文件只装配」，全文只做装配，无任何业务）：

1. `require __DIR__ . '/../vendor/autoload.php'`
2. `$app = new \think\App();`
3. `$app->setRuntimePath(dirname(__DIR__) . '/runtime/admin/');`  ← 必须在 run() 之前
4. 加载 `route/admin.php`
5. `$http->run()` → `$response->send()` → `$http->end($response)`
6. `while (ob_get_level() > 0) { ob_end_flush(); }` 兜底（沿用 C 端 `index.php` 已踩坑得出的结论：`cli-server` SAPI 不会自动 flush）

**路由缓存硬约束**：本项目**不启用路由缓存**（ThinkPHP 默认即不缓存路由，除非显式调用 `Route::setCache()`）。若将来有人开启，必须为两个进程配置不同的缓存键，或干脆保持不缓存——后台路由表在开发期频繁变更，缓存带来的排查成本高于收益。

## Consequences

正面：
- 后台日志、缓存、临时文件与 C 端物理分离，问题定位时能直接按目录判来源
- 框架原生支持，不需改任何框架代码、不需新依赖

负面 / 必须注意：
- **启动顺序无关**，两进程都可独立启停
- `runtime/admin/` 目录**不会被框架自动创建**。`setRuntimePath` 只是改字符串，实际建目录由写入方（Log/Config 等组件）负责，因此**首次启动时若目录不存在，日志写入会失败**。解法：启动前 `mkdir -p runtime/admin`，写进启动脚本。这是实现时最容易漏的一步，必须写进 Spec 的验收标准
- `public/router.php` 需复制一份为 `public/router-admin.php`（`php -S` 的静态文件短路 + ob flush 逻辑），两份文件必须同步维护——这是代码重复，已知且接受（改动频率极低）
- 两进程共享 `app/`，因此**任何 `app/` 下的改动会同时影响两个服务**。这是 ADR-002 方案 B 的固有代价：新增后台代码时必须严格限制在 `app/admin/` 子目录内，不得修改 `app/controller/` 下的 C 端控制器与 `app/middleware/` 下的 C 端中间件（`CorsMiddleware` / `ResponseMiddleware` 是例外，后台需要共用，但只允许后台侧读配置，不允许修改其行为）
