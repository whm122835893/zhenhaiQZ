# ADR-011: 桌面派生列的 JOIN 路径与字段选型（Q16 裁决）

## Status: Accepted (2026-10-22)

## Background

PRD v1.3 §17.5.2 锁定 6 组桌面派生列的**业务语义**，但实现方式未定。本 ADR 只定**技术实现**，不改业务口径。

派单时总监复验了 PM 指出的字段缺失，全部属实：

| 表 | 缺失字段 |
|---|---|
| `nft_trade_logs` | 无买家/卖家 |
| `item_copyrights` | 无审核状态/审核人/审核时间 |
| `users` | 无录入时间/录入人 |
| `items` | 5 个相近数量字段（issue/buy/nft/sell/trade）语义易混 |

PM 特别警告：「最近成交价若错用挂单价顶替，桌面端的异常低价预警会直接失效」——
这关系到 AC-28「规则上线首日必须能复现命中」。

**硬约束**：不得改动 C 端 48 张表的既有字段语义（C 端已跑通）。
新增字段只能落在 `admin_*` 侧。

## 决策依据：实际读库核对（`shengtai` 库，2026-10-22）

### 核对 1：五个数量字段的真实语义

`SHOW FULL COLUMNS FROM items` 的 COMMENT + `docs/api.md` 实测字段 + C 端代码三条交叉验证：

| 字段 | COMMENT | api.md 实测 | C 端实际展示 | 语义 |
|---|---|---|---|---|
| `issue_quantity` | 发行总量 | `issueQuantity: 888888` | `MarketPage.vue:427` → `quantity`（进度条分母）、`InfoPage.vue:50` → 「发行 X 份」 | **发行总量** |
| `buy_quantity` | 已购数量 | `buyQuantity: 100` | 未在 C 端展示 | 一级市场已购 |
| `nft_quantity` | 已铸造NFT数 | `nftQuantity: 95824` | `MarketPage.vue:428` → `soldQty` | **已铸造**（C 端当已售用，但语义是铸造） |
| `sell_quantity` | 在售数量 | `sellQuantity: 7207` | `MarketPage.vue:420` → `isOut` 售罄判定 | **在售**（挂单中未售出） |
| `trade_quantity` | 成交数量 | `tradeQuantity: 327215` | `MarketPage.vue:429` → `sellCount`（进度条分子） | **已售**（累计成交） |

**结论：「已售」= `items.trade_quantity`，「库存」= `items.issue_quantity`。与 AC-48 ⑥ 一致，判定通过。**

关键区分：`trade_quantity`（已售 327215）> `nft_quantity`（已铸造 95824）> `sell_quantity`（在售 7207）。
同一 NFT 可多次转手，故成交数可大于铸造数。三者语义互斥，**取错列会让「已售」与「在售」互相矛盾**。

### 核对 2：最近成交价的两个候选源（发现口径冲突）

| 来源 | iid=2111310949005721602 的值 | 说明 |
|---|---|---|
| `nft_trade_logs` 按 `sold_time DESC` 取 `sold_price` | **105100.00**（10 条，103000~105100） | PRD §17.5.2 指定口径 |
| `items.last_trade_amount` | **100000.00** | COMMENT「最新成交价(分)」 |

**两者不一致（105100 vs 100000）。** 实测数据：

```
iid                    items.last_trade_amount   成交表最新 sold_price
2111310949005721602    100000.00                 105100.00
```

**采纳 PRD §17.5.2 口径（`nft_trade_logs`），理由**：
1. `last_trade_amount` 是源站冗余字段，其快照时机与源站同步周期绑定，本地不可控；
2. AC-48 ① 已明确「必须取同 `iid` 的 `nft_trade_logs` 中 `sold_time` 最新一条」；
3. 成交表是**明细事实表**，可复算、可审计；`last_trade_amount` 是**派生缓存**，无法追溯。

**风险登记**：两个源不一致时，以成交表为准。若未来发现 `last_trade_amount` 更准，那是 PRD 变更，不是实现变更。

### 核对 3：AC-28 复现路径的可行性（发现数据缺口，须登记 OPEN）

```
nft_sell_orders  10 条挂单 → iid 全为 2109928427009183745（臻海蓝卡），price 全为 500.00
nft_trade_logs   10 条成交 → iid 全为 2111310949005721602（韩湘子），sold_price 103000~105100
```

**10 条挂单与 10 条成交分属两个不同藏品。** 按 PRD 口径以 `iid` 关联反查，
臻海蓝卡的 `nft_trade_logs` 记录数为 **0** → 「最近成交价」应显示「无成交记录」。

另：`nft_trade_logs.order_id` 实测**全部为 0**，`orders` 表仅 2 条且 `seller_uid` 全为 0。

**这意味着 AC-28「上线首日必须能复现命中」在当前种子数据下无法成立**——
挂单与成交数据不同源，异常低价预警首日必然全部落空。

处理：登记为 **OPEN-04**，交 PM 与总监裁决（补种子数据 or 调整 AC-28 措辞）。
**架构侧不自行修改种子数据**（种子数据是 C 端已验收的资产）。

架构侧确保：**规则与判定逻辑必须实现且可配置**，一旦有同 iid 的成交数据即可命中。
另需交叉验证：`items.last_trade_amount` 臻海蓝卡 = 500.00（分），恰等于挂单价，
若误用此字段作「最近成交价」会得价差比 0%，**更加不会命中**——
这从反面印证了 PM 警告的严重性。

### 核对 4：买家/卖家反查路径

`nft_trade_logs` 无买家/卖家字段。可选路径：

| 方案 | JOIN 路径 | 结论 |
|---|---|---|
| A | `nft_trade_logs.order_id → orders.id` 取 `uid`/`seller_uid` | **不可用**：`order_id` 实测全 0 |
| B | `nft_trade_logs.nft_id → nfts.nft_id → nfts.uid` | 可用，但只有**当前持有人**，非成交时点的买家 |
| C | `nft_trade_logs.iid → items` | 无用户字段 |

**决策：采用方案 B 作为降级方案，并明确其语义为「当前持有人」而非「成交买家」。**
脱敏复用 `User::maskPhone()`（`server/shengtai-api/app/model/User.php:85`），
与 C 端 `Passport` / `User` controller 共用同一实现，满足 AC-48 ③「复用移动端同一套反查与脱敏逻辑」。

买家（`orders.uid`）因 `order_id=0` 无法反查，**显示「—」而非猜测**。
补齐依赖订单归因，登记 **OPEN-05**（需源站回填 `order_id`，非本地可解）。

### 核对 5：审核三元组与录入二元组

| 需求 | C 端表 | 结论 |
|---|---|---|
| 审核状态/审核人/审核时间 | `item_copyrights` 无任何审核字段 | 需 admin 侧承载 |
| 录入时间/录入人 | `users` 无录入字段 | 可从审计日志派生 |

**审核三元组**：新增 `admin_audit_records`（见下）。
**不塞进 `admin_copyright_overrides`** —— 该表是 KV 结构（`field_key`/`field_value`），
适合存「覆盖值」，不适合存「带独立生命周期的审核事件」。审核是**事件**（有状态迁移、审核人、驳回理由），
override 是**当前值**。混用会导致无法回答「谁在什么时候驳回过、驳回理由是什么」。

**录入二元组**：**从 `admin_operation_logs` 派生，不新增字段。**
该表已有 `target_type`/`target_id`/`admin_id`/`admin_username`/`created_at(3)`，
且有索引 `idx_logs_target (target_type, target_id)`——正是查询所需。
取该对象**最早一条** `action='write' AND is_success=1` 的记录即「录入」。

**注意**：AC-48 ⑤ 要求「不得以 `users.updated_at` 冒充录入时间」。
审计日志表当前 0 条（尚无后台操作），首条登录后即产生，符合预期。

### 表结构（新增 1 张 admin 表）

```sql
-- 审核记录表（admin 侧，不改 C 端 item_copyrights）
CREATE TABLE `admin_audit_records` (
  `id` bigint(20) unsigned NOT NULL COMMENT '雪花ID',
  `target_type` varchar(32) NOT NULL DEFAULT '' COMMENT '审核对象类型: copyright/item/author',
  `target_id` bigint(20) unsigned NOT NULL DEFAULT 0 COMMENT '对象ID(item_copyrights.id)',
  `audit_status` varchar(16) NOT NULL DEFAULT 'pending' COMMENT 'pending/approved/rejected',
  `auditor_id` bigint(20) unsigned NOT NULL DEFAULT 0 COMMENT '审核人admin_id',
  `auditor_name` varchar(64) NOT NULL DEFAULT '' COMMENT '审核人账号快照(账号被删仍可追溯)',
  `audited_at` datetime(3) DEFAULT NULL COMMENT '审核时间(毫秒精度)',
  `reason` varchar(512) NOT NULL DEFAULT '' COMMENT '驳回理由',
  `op_log_id` bigint(20) unsigned NOT NULL DEFAULT 0 COMMENT '关联admin_operation_logs.id',
  `created_at` datetime(3) NOT NULL DEFAULT current_timestamp(3),
  `updated_at` datetime(3) NOT NULL DEFAULT current_timestamp(3) ON UPDATE current_timestamp(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_audit_target` (`target_type`,`target_id`),
  KEY `idx_audit_status_time` (`audit_status`,`audited_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='后台审核记录(C端不读)';
```

`uk_audit_target` 保证一个对象只有一条**当前**审核状态（覆盖式更新），
`idx_audit_status_time` 支撑「按状态筛选待审列表」。

### 6 组派生列 JOIN 汇总

| # | 派生列 | 数据来源 | 类型 |
|---|---|---|---|
| 1 | 最近成交价 | `nft_trade_logs` 按 `(iid, sold_time DESC)` 取 `sold_price` | 现有表 JOIN |
| 2 | 价差比 | `(最近成交价 − 挂单价) ÷ 最近成交价`，**计算列**，无存储 | 纯计算 |
| 3 | 买家 / 卖家 | 卖家：`nfts.nft_id → nfts.uid`；买家：`orders`（`order_id=0` 不可用，显示「—」） | 现有表 JOIN + 降级 |
| 4 | 审核三元组 | `admin_audit_records`（新增表） | **新增 admin 表** |
| 5 | 录入二元组 | `admin_operation_logs` 取最早成功 write | 现有 admin 表派生 |
| 6 | 库存 / 已售 | `items.issue_quantity` / `items.trade_quantity` | 直读，**零 JOIN** |

第 6 组零 JOIN——已确认 `items` 单表直读，是性能最优路径。

### 索引需求

现有索引已满足，**无需新增**：

| 查询 | 索引 | 状态 |
|---|---|---|
| 最近成交价 | `idx_trade_iid_time (iid, sold_time)` | 已存在，完美覆盖 |
| 挂单列表 | `idx_sell_iid_status (iid, status, price)` | 已存在 |
| NFT 反查 | `uk_nfts_nft_id (nft_id)` | 已存在 |
| 录入二元组 | `idx_logs_target (target_type, target_id)` | 已存在 |

派生列 1/3 在列表场景为**逐行相关子查询**。当前数据量（挂单 10 / 成交 10 / NFT 16）
无性能问题。按项目「避免过早优化」原则，**MVP 不加冗余列、不做物化缓存**。
数据量增长后按 `iid` 分组预聚合即可，属后续迭代。

## Consequences

**正面**
- 6 组派生列全部锁定字段来源，移动/桌面两端取同一函数，不可能漂移
- 「已售/库存」零 JOIN，成本最低
- 审核三元组与录入二元组均落在 admin 侧，C 端 48 表零改动，硬约束守住
- 「最近成交价」口径唯一，杜绝 PM 警告的顶替事故

**负面**
- 新增 1 张表 `admin_audit_records`（11 → 12 张 admin 表）
- 「最近成交价」与 `items.last_trade_amount` 口径不同，两值并存需在文档说明
- 买家字段在当前数据下不可用，显示「—」

**OPEN（不自行拍板）**
- **OPEN-04**：AC-28 首日复现不成立（挂单与成交数据不同源），待 PM / 总监裁决
- **OPEN-05**：买家反查依赖 `nft_trade_logs.order_id` 回填，源站侧问题
