# ADR-013: 导出接口（后端流式）与跨端统一分页

## Status: Accepted (2026-10-22)

## Background

Q11 已裁决：移动端不提供导出，≥768px 显示入口。
PRD v1.3 第 9 条 + AC-53 追加：≥1024px 在同一导出按钮下拉中额外提供
「导出全部结果」与「选择导出字段」，字段集 = 桌面表格可见列（≤8 列）。

PM 约束明确：**禁止前端生成**。

当前数据量（`items` 5 / `nft_sell_orders` 10 / `nft_trade_logs` 10 / `users` 38）
下流式的性能收益近乎为零，但字段集一致性收益是实打实的。

## Part 1：导出接口设计

### 决策一：字段选择参数的传参方式

`GET /api/v1/admin/{module}/export`（沿用 v1，导出属既有资源操作）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `scope` | `current` \| `all` | 否，缺省 `current` | `all` = 全部筛选结果（**非**当前页），对应 ≥1024「导出全部」 |
| `fields` | CSV 字符串 | 否 | `name,last_trade_price,status`；缺省 = `exportable` 全集 |
| 筛选参数 | — | 否 | 与列表端点**完全同名同义**（`q`/`status`/…），保证「导出的就是筛选出的」 |

**关键设计：筛选参数与列表端点同名同义。**

AC-53 要求「导出全部结果 = 全部筛选结果而非当前页」。
实现上把导出理解为**「同查询、忽略分页」**——
因此 `pageNo`/`pageSize` 在导出端点**不接受**，其余参数全部复用。
这样「列表筛出什么，导出就是什么」成为结构性保证，而非人工对齐。

**`fields` 的校验位置：服务端。**

```
1. 按逗号 split，逐项比对该端点 fields 定义中 exportable == true 的 key
2. 命中任何不在 exportable 集合内的 key → 400 / 业务码 11020（参数非法）
3. 拒绝空 fields（[] 或空串）→ 视为缺省，取 exportable 全集
```

**服务端校验是硬闸门，不可省。** 因为 AC-53 明文要求
「导出字段集必须等于桌面表格可见列，不得包含移动端 L1 ∪ L2 之外的字段」。
若信任客户端传参，一个手工构造的 `?fields=password_hash` 就会击穿该约束。
前端只负责**提供勾选 UI**，不负责**保证边界**。

### 决策二：后端流式实现

**采纳 `fputcsv` + `php://output` 直出 CSV**，理由如下：

| 方案 | 内存 | 实施成本 | 结论 |
|---|---|---|---|
| 内存数组全量拼装后 `echo` | O(行数 × 列数)，38 行无感，10 万行即 OOM | 最低 | **否决**——PM 明确「大数据量须后端流式」 |
| **CSV 直出流**（采纳） | O(1)，逐行 flush | 低 | **采纳** |
| PHPExcel / PhpSpreadsheet | 高（整表对象化） | 高，且大数据必崩 | **否决**——为「导出一张表」引入重型依赖不划算 |

CSV 而非 XLSX：AC-53 场景是「导出数据做外部分析」（PRD 5.3 观察者诉求），
分析工具（Excel / pandas / SQL）全部原生吃 CSV。
引入 PhpSpreadsheet 只为 xlsx 后缀，不值。

**流式实现骨架**（ThinkPHP，`server/shengtai-api/app/controller/`）：

```php
// 1. 关闭输出缓冲，避免全量累积
ob_end_clean();
header('Content-Type: text/csv; charset=utf-8');
header('Content-Disposition: attachment; filename="items_20261022.csv"');

// 2. BOM：Excel 打开中文 CSV 需要 BOM，否则乱码
fwrite($this->output, "\xEF\xBB\xBF");

// 3. 表头行：字段集即导出字段集，单一真源（ADR-012）
fputcsv($this->output, $headers);

// 4. 逐行游标读取，禁止 ->select() 全量载入
foreach ($rows as $row) {
    fputcsv($this->output, $values);
    // 让出内存，防止超时
}
// 5. 记入 admin_operation_logs（含导出人、时间、数据区间、行数、字段集）
//    —— AC-53 强制要求，注意：日志须在流式输出后仍能写入，
//    故先统计行数并写入日志，再关闭输出。
```

**两个实现坑（必须提前规避）**：

1. **AC-23 要求导出计入 `admin_operation_logs`，但流式输出后连接可能已断**。
   处理：先执行一遍 `SELECT COUNT(*)` 得出行数并写日志，再开流式输出。
   多一次计数查询，换取日志必达。38 行数据下开销可忽略。

2. **ThinkPHP 的 `export` 可能与框架自身的导出方法撞名**。
   端点命名与控制器方法名须显式核对，避免调用到框架基类方法。

### 决策三：≥1024 的「导出全部 + 字段选择」入口

- `scope=all` + `fields=<csv>` 两个参数**同时**支持即可，
  UI 上是同一个下拉菜单的两个选项，**不需要两个端点**。
- 768~1023px：只渲染 `scope=current` 入口，不渲染字段选择（AC-53）。

## Part 2：跨端分页统一 40

### 确认结论：后端分页参数在双端行为一致，无需区分

PM 主张、总监已裁决（Q14），架构侧复核如下。

**核对**：`docs/admin/openapi.yaml` 中六个列表端点的 `pageSize` 定义，
当前统一为 `default: 20, maximum: 100`。**契约本身已是端无关的**——
分页参数在 URL 层没有任何视口相关语义，因此**双端行为必然一致**，无需任何代码分叉。

需做的两项收敛（收在 openapi，不改运行时逻辑）：

1. `default` 由 **20 改为 40**，与 PM 裁决的双端默认阈值对齐；
2. 六个列表端点 `pageSize` 的 `default`/`maximum` 收敛为完全相同的字面量，
   杜绝逐端点漂移（当前已是 20/100，但无强制约束）。

**为什么不需要区分**：

| 理由 | 说明 |
|---|---|
| 后端无状态 | 分页是纯查询参数，不含视口语义，AC-49 天然满足 |
| 断点切换不重置 | 筛选与分页条件存于 URL / store，两端同源；AC-49/50 只要求前端保持，与后端无关 |
| 当前无分页 | 六个列表最大 36 条 < 40，「全不分页」结论不变，`pageSize` 在 MVP 几乎不被使用 |
| 提前优化无收益 | 为一个尚不触发的阈值做端差异化，属无依据的复杂度 |

**登记观察项（非阻塞）**：`users` 表已有 38 条，且后台用户会随运营增长。
当 `users` 突破 40 条的那天，需要复核的是**列表是否真的要分页**，
而不是分页阈值取多少——两者不应混为一谈。

## Consequences

**正面**
- 导出为后端流式，内存 O(1)，数据量增长不炸
- 「导出的就是筛选出的」成为结构性保证，AC-53 一致性要求自动满足
- 字段集由服务端校验，AC-53 的「不得含 PC 专属字段」是硬闸门而非自觉
- 分页契约端无关，双端零分叉；AC-49 天然成立

**负面**
- 导出需一次额外的 `COUNT(*)` 查询以保证日志必达
- 响应式导出需处理 ThinkPHP 框架方法命名冲突
- 元数据/字段校验逻辑对新增模块是**重复工作量**——但这是「新增端点须声明 fields」规则的固有成本

**OPEN**
- 无（导出与分页部分未产生待裁决项；字段集归属见 ADR-012）

**Related ADRs**：ADR-012（字段集单一真源）、ADR-011（派生列选型）、ADR-005（权限点字典）
